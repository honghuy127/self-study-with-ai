## Purpose and role in the harness

- Codex keeps the model-visible conversation in an in-memory `ContextManager` transcript (`items: Arc<Vec<ResponseItemEnvelope>>`) plus a `history_version` bumped on rewrites, `token_info`, a `reference_context_item`, and a `world_state_baseline` (`codex-rs/core/src/context_manager/history.rs:44-65`). Every recorded item is a `ResponseItem` envelope optionally carrying `CodexHarnessMetadata` (`history.rs:178-195`).
- Request-context assembly is split into a server-side "system prompt" (`base_instructions`, sent as the Responses API `instructions` field) and in-history "initial context" developer/user fragments (AGENTS.md, environment, permissions, model-specific instructions). Only when `base_instructions.text` is non-empty does the client attach `instructions` to the request (`codex-rs/core/src/client.rs:879`).
- Compaction is the mechanism that keeps `get_total_token_usage()` under the model's auto-compact limit or full context window. It has four runtime-selected implementations: a summarization-free window reset (`TokenBudget` feature), remote v2 (`CompactionTrigger` item over the streaming Responses API), remote v1 (unary `/responses/compact`), and local summarization by the same model (`codex-rs/core/src/session/turn.rs:1160-1240`, `codex-rs/core/src/tasks/compact.rs:36-77`, `codex-rs/model-provider/src/provider.rs:327-340`).
- Compaction checkpoints are persisted to the rollout as `RolloutItem::Compacted` with the full `replacement_history` and context-window ids, so resume rebuilds the exact post-compaction transcript (`codex-rs/core/src/session/mod.rs:3338-3387`).

## Mechanism

### Context assembly (steady state)

1. At the start of each user turn, `run_turn` calls `record_context_updates_and_set_reference_context_item` (`codex-rs/core/src/session/turn.rs:224-228`). If the stored `reference_context_item` is `None`, it fully rebuilds and records initial context via `build_initial_context_with_world_state` and sets the world-state baseline; otherwise it records only the world-state **diff** fragments (`codex-rs/core/src/session/mod.rs:3810-3849`). It persists `RolloutItem::WorldState` and one `RolloutItem::TurnContext` per real turn and advances the baseline (`mod.rs:3856-3883`).
2. `build_initial_context_with_world_state` composes up to four message bundles (`codex-rs/core/src/session/mod.rs:3490-3695`): one aggregated `developer` bundle (developer instructions, extension prompt fragments, world-state developer fragments; model-switch instructions are force-prepended, `mod.rs:3633-3637`), separate developer messages (token-budget window context, multi-agent role instructions, `mod.rs:3615-3627`, `mod.rs:3641-3650`), the multi-agent mode block (`mod.rs:3670-3672`), and one aggregated contextual `user` bundle (recommended plugins, world-state user fragments such as AGENTS.md and environment context, `mod.rs:3545`, `mod.rs:3652`, `mod.rs:3673-3677`). Bundles are built by `build_developer_update_item` / `build_contextual_user_message`, which just wrap sections as `ContentItem::InputText` items of the given role (`codex-rs/core/src/context_manager/updates.rs:11-17`, `48-65`); consecutive same-role fragments merge in `merge_contextual_fragments` (`updates.rs:19-46`).
3. World state is a registry of typed sections keyed by stable IDs (`codex-rs/core/src/context/world_state/mod.rs:268-272`). Sections added per step: `model`, personality, token-budget context window ids, realtime state, `agents_md`, permissions (full or compact), collaboration mode, `environments`, environments instructions, apps instructions, plugins instructions, deferred tools, extension sections, multi-agent usage hint and mode (`codex-rs/core/src/session/world_state.rs:77-296`). Each section renders against `PreviousSectionState::{Absent,Unknown,Known}` and emits a diff fragment only when it changed (`world_state/mod.rs:192-245`, `404-419`). Snapshots persist to rollouts as RFC 7386 merge patches (`world_state/mod.rs:297-332`).
4. AGENTS.md is section `agents_md` (`codex-rs/core/src/context/world_state/agents_md.rs:34-36`). It renders a `user`-role `UserInstructions` fragment with header `# AGENTS.md instructions` and `<INSTRUCTIONS>...</INSTRUCTIONS>` markers (`codex-rs/core/src/context/user_instructions.rs:18-29`). On change it re-emits with prefix "These AGENTS.md instructions replace all previously provided AGENTS.md instructions."; on removal it emits "The previously provided AGENTS.md instructions no longer apply." (`agents_md.rs:9-11`, `66-77`).
5. The environment section renders `<environment_context>` user fragments (tags defined at `codex-rs/protocol/src/protocol.rs:113-114`; fragment role/marker wiring at `codex-rs/core/src/context/world_state/environment.rs:156-172`) containing `<environments>`/`current_date`/`timezone`/`<network>`/`<filesystem>`/`<subagents>` XML (`environment.rs:203-259`, `codex-rs/core/src/context/environment_context.rs:63-75`, `230-236`).
6. Fragments implement the shared `ContextualUserFragment` trait from `codex-rs/context-fragments`: `render()` concatenates open marker, body, close marker; unmarked fragments render body only (`codex-rs/context-fragments/src/fragment.rs:14-46`). Extension "additional context" fragments use `<external_<key>...>` markers and are middle-truncated to 1_000 tokens (`codex-rs/context-fragments/src/additional_context.rs:5-88`).
7. Base instructions (the system prompt) resolve with documented precedence: 1. `config.base_instructions` override, 2. resumed conversation history session metadata, 3. the model's rendered `instructions_template` (`codex-rs/core/src/session/mod.rs:641-659`); `get_base_instructions` returns the stored session value with provenance (`mod.rs:1292-1298`). Reminder-style developer fragments are injected per sampling request: current-time reminder (`<current_time_reminder>` body "It is ...", `codex-rs/core/src/context/current_time_reminder.rs:22-37`; hook at `codex-rs/core/src/session/turn.rs:338-343`) and rollout-budget/remaining-token developer fragments (`codex-rs/core/src/context/rollout_budget.rs:8-27`; calls at `session/turn.rs:306-311`).
8. Before each request, `for_prompt` normalizes the cloned transcript: every tool call must have an output (missing pairs get synthetic `"aborted"` outputs inserted, with stable v5-UUID ids for prompt-cache friendliness, `codex-rs/core/src/context_manager/normalize.rs:21-146`), orphan outputs are removed (`normalize.rs:148-217`), and images/audio are replaced by placeholder text when the model lacks the modality (`normalize.rs:14-17`, `317-408`). Recording filters out non-API items (`role == "system"` messages and `CompactionTrigger` are never stored) and truncates tool outputs on ingest with the model's `truncation_policy` multiplied by a 1.2 serialization budget (`history.rs:178-195`, `460-471`, `575-595`).

### Token budgeting

- `get_total_token_usage` = last server-reported `total_tokens` + locally estimated items recorded after the last model-generated item + (when the server does not account for reasoning) estimated bytes of retained non-last-turn encrypted reasoning items (`history.rs:374-432`).
- Estimation is byte-based, not a tokenizer: JSON-serialize each item and divide by `APPROX_BYTES_PER_TOKEN = 4` with the code calling it "a coarse lower bound" (`history.rs:245-246`, `613-616`; `codex-rs/utils/string/src/truncate.rs:4`, `71-84`). Inline base64 images, audio, and encrypted payloads are replaced by modality-specific byte estimates, e.g. `RESIZED_IMAGE_BYTES_ESTIMATE: i64 = 7373` (about 1,844 tokens) (`history.rs:618-631`, `640-676`).
- Trigger status is computed by `context_window_token_status` (`codex-rs/core/src/session/context_window.rs:23-91`). `token_limit_reached` is true when scope tokens reach the auto-compact limit plus any `auto_compact_fallback_buffer_tokens`, or when active tokens reach the full context window (`context_window.rs:71-79`).
- Scope defaults to counting the full active context: `AutoCompactTokenLimitScope::Total` is the serde `#[default]` (`codex-rs/protocol/src/config_types.rs:26-37`); `BodyAfterPrefix` subtracts the window's `prefill_input_tokens` baseline, which is server-observed when available and otherwise estimated (`codex-rs/core/src/state/auto_compact_window.rs:27-43`, `108-130`; scope math at `context_window.rs:30-51`).
- Limits: the auto-compact limit per model defaults to 90% of its resolved context window, `(context_window * 9) / 10`, and is clamped to that when model metadata supplies its own value (`codex-rs/protocol/src/openai_models.rs:488-499`). The full context window limit is `model_context_window` = `context_window` or `max_context_window` scaled by `effective_context_window_percent / 100`, default 95 (`codex-rs/core/src/session/turn_context.rs:310-317`; `openai_models.rs:376-378`, `484-486`). Config `model_context_window` overrides model metadata, clamped to `max_context_window` (`codex-rs/models-manager/src/model_info.rs:26-31`).

### When compaction triggers

- Pre-turn: `run_turn` first runs `run_pre_sampling_compact` (`codex-rs/core/src/session/turn.rs:169-190`, `994-1023`). It first handles model switches, then compacts when `token_status.token_limit_reached` with `CompactionReason::ContextLimit`, `CompactionPhase::PreTurn`, and `InitialContextInjection::DoNotInject` (`turn.rs:1002-1021`).
- Model-switch compactions (same pre-turn hook): if both previous and current models declare a compaction compatibility hash (`comp_hash`, "Opaque identifier for compaction-compatible model configurations", `openai_models.rs:436-443`) and the hashes differ, compaction runs on the **previous** model with `CompactionReason::CompHashChanged` (`turn.rs:1025-1031`, `1071-1104`); otherwise, if switching to a model with a smaller context window would put the current thread over its limit, compaction runs with `CompactionReason::ModelDownshift` (`turn.rs:1106-1151`).
- Mid-turn: after every completed sampling request, if follow-up work is needed and either the model requested a new context window (via the `new_context` tool) or `token_limit_reached`, the loop compacts and continues: `should_roll_over = needs_follow_up && (sess.take_new_context_window_request().await || token_limit_reached)` (`turn.rs:440-441`, `452-479`) with `CompactionPhase::MidTurn` and `InitialContextInjection::BeforeLastUserMessage` carrying the frozen world state (`turn.rs:452-465`).
- Manual: `CompactTask` (`TaskKind::Compact`) handles user-initiated compaction (`codex-rs/core/src/tasks/compact.rs:19-85`).
- The `new_context` model tool (gated on `Feature::TokenBudget`) just sets the window-request flag and tells the model "A new context window will start without summarizing conversation history." (`codex-rs/core/src/tools/spec_plan.rs:1079-1082`; `codex-rs/core/src/tools/handlers/new_context_window.rs:13-14`, `27-43`).

### Path selection

`run_auto_compact` (auto) and `CompactTask::run` (manual) select the implementation in the same shape (`codex-rs/core/src/session/turn.rs:1160-1240`; `codex-rs/core/src/tasks/compact.rs:36-77`):

1. `Feature::TokenBudget` enabled: summarization-free reset via `compact_token_budget::run_*` (`turn.rs:1171-1181`, `tasks/compact.rs:36-39`).
2. Else provider capability `RemoteCompactionSupport::V2` + `Feature::RemoteCompactionV2` enabled: remote v2 (`turn.rs:1183-1205`).
3. Else `V1` or `V2` capability: remote v1 (`turn.rs:1206-1222`).
4. Else `Unsupported`: local summarization (`turn.rs:1223-1237`).
- Provider capabilities: `ConfiguredModelProvider` reports `V2` for OpenAI or Azure Responses providers and `Unsupported` otherwise (`codex-rs/model-provider/src/provider.rs:327-340`); the struct default is `V2` (`provider.rs:56-66`); Amazon Bedrock declares `V1` (`codex-rs/model-provider/src/amazon_bedrock/mod.rs:185`). Feature defaults: `remote_compaction_v2` is `Stage::Stable`, `default_enabled: true` (`codex-rs/features/src/lib.rs:1517-1522`); `token_budget` is `Stage::UnderDevelopment`, `default_enabled: false` (`lib.rs:1403-1408`); `retain_client_developer_messages` is `UnderDevelopment`, `default_enabled: false` (`lib.rs:1523-1528`). Telemetry tags `"remote_v2"` / `"remote"` / `"local"` are emitted per path (`turn.rs:1190-1236`).

### Local summarization path (`compact.rs`)

- Appends the compaction prompt as a synthesized user message to a clone of history and streams it to the same model: prompt = `config.compact_prompt` if set, else `SUMMARIZATION_PROMPT` (`codex-rs/core/src/compact.rs:111-141`, `169-238`, `250-289`). The default template reads "You are performing a CONTEXT CHECKPOINT COMPACTION. Create a handoff summary for another LLM that will resume the task." plus four bullets (progress/decisions, context/constraints/preferences, remaining work, critical data) (`codex-rs/prompts/templates/compact/prompt.md:1-9`, via `codex-rs/prompts/src/compact.rs:1`).
- On `ContextWindowExceeded` during the summarization request it removes the oldest history item and retries with the retry counter reset, i.e., it shrinks the compaction input itself ("removing oldest history item", `compact.rs:309-324`); other transient errors retry with backoff up to `stream_max_retries` (`compact.rs:325-344`).
- The replacement history = initial context (if injecting) + the most recent real user messages capped at `COMPACT_USER_MESSAGE_MAX_TOKENS: usize = 20_000` (walking backwards, middle-truncating the one message that straddles the budget) + the summary appended as a **user-role** message (`compact.rs:57`, `346-354`, `639-717`). Summary text is `SUMMARY_PREFIX` ("\n" + last assistant message); empty summaries become `"(no summary available)"` (`compact.rs:349-351`, `702-706`; prefix template at `codex-rs/prompts/templates/compact/summary_prefix.md:1`). Assistant turns, tool calls/outputs, reasoning, and old context fragments are dropped; they are only carried insofar as the model restated them in the summary.
- Summary messages are recognized later by the prefix check `is_summary_message` (`compact.rs:567-569`).
- After installing, the local path emits the warning "Heads up: Long threads and multiple compactions can cause the model to be less accurate. Start a new thread when possible to keep threads small and targeted." (`compact.rs:389-392`).

### Remote v1 path (`compact_remote.rs`, `compact_remote_request.rs`, `compact_remote_history.rs`)

- Before sending, `trim_function_call_history_to_fit_context_window` walks history from newest to oldest and replaces tool outputs (`FunctionCallOutput`, `CustomToolCallOutput`, `ToolSearchOutput`) with the constant body "Output exceeded the available model context and was truncated" until the estimated total fits the model's context window (`compact_remote.rs:399-455`, constant at `compact_remote.rs:50-51`).
- The attempt POSTs the full prompt (history + tools + base instructions) to the unary endpoint `RESPONSES_COMPACT_ENDPOINT: &str = "/responses/compact"` (`compact_remote_request.rs:32-97`; `codex-rs/core/src/client.rs:163-164`, `553-652`). The server returns the compacted transcript; the client does not control the server's summary.
- Server output is filtered client-side by `should_keep_compacted_history_item`: drop `developer` messages (stale/duplicated instruction content), drop `user`-role items unless they parse as `TurnItem::UserMessage` or `HookPrompt` (this keeps real user messages and persisted hook prompts while dropping session-prefix wrappers), keep `assistant` and `AgentMessage`, keep `Compaction`/`ContextCompaction` items, drop `CompactionTrigger`, `Reasoning`, all tool calls/outputs, and `Other` (`compact_remote.rs:354-397`). Image-resize developer notices ride along with their source item as "attached notices" grouped by `history_item_groups` so filtering never separates them (`codex-rs/core/src/compact_remote_history.rs:29-56`).
- Legacy `/responses/compact` output loses harness envelope metadata ("returns provider-normalized items without a stable link to their original envelopes", `compact_remote.rs:287-292`).

### Remote v2 path (`compact_remote_v2.rs`, `compact_remote_v2_attempt.rs`)

- V2 does not use the compact endpoint. It appends one synthetic `ResponseItem::CompactionTrigger {}` to the normal streaming Responses request (`compact_remote_v2_attempt.rs:71-85`) and expects **exactly one** `ResponseItem::Compaction` output item; any other count is `CodexErr::Fatal` (`compact_remote_v2.rs:400-457`). Max stream retries are capped at `MAX_REMOTE_COMPACTION_V2_STREAM_RETRIES: u64 = 2` (`compact_remote_v2.rs:67-69`, `357-361`).
- The server returns an encrypted `Compaction` item (opaque resume token, not a readable summary) which is appended last to the replacement history (`compact_remote_v2.rs:459-488`; struct fields `encrypted_content` visible in tests at `compact_remote_v2.rs:791-801`).
- Client-side retention before sending: `is_retained_for_remote_compaction_v2` keeps `user`/`developer`/`system` messages and `AgentMessage`s that are neither descendant progress messages (`"Message Type: MESSAGE\n"`) nor completion messages (`"Message Type: FINAL_ANSWER\n"`) and are at most `MAX_RETAINED_AGENT_MESSAGE_TOKENS: i64 = 10_000` tokens (`compact_remote_v2.rs:512-543`, constant at line 66). Retained messages are then filtered by the same `should_keep_compacted_history_item` (plus client-authored developer messages when `Feature::RetainClientDeveloperMessages` is on, `compact_remote_v2.rs:471-481`, `490-495`) and truncated oldest-first to `RETAINED_MESSAGE_TOKEN_BUDGET: usize = 64_000`, with the comment "Mirror the current /responses/compact retained-message default while the server-side path remains the reference implementation" (`compact_remote_v2.rs:63-65`, `556-632`). Retained input images are counted for analytics (`compact_remote_v2.rs:480-488`, `545-554`).
- Retention budget math is text-only (`message_text_token_count` counts text; images/audio count 0) and middle-truncation uses the shared `truncate_text` marker format ("midd…1 tokens truncated…1234" in the test at `compact_remote_v2.rs:946-964`).

### Shared post-compaction install

- All paths converge on `Session::replace_compacted_history`, which assigns missing item ids, installs the replacement history, swaps `reference_context_item`, and persists `RolloutItem::Compacted` (with `replacement_history`, MCP resource origins, and window ids) plus, when the caller supplied a world-state baseline (the mid-turn path), a full `WorldStateItem` baseline; it also queues a `SessionStartSource::Compact` hook (`codex-rs/core/src/session/mod.rs:3338-3387`).
- Initial-context re-injection policy is set by the `InitialContextInjection` enum whose doc comment explains the training contract: pre-turn/manual compaction uses `DoNotInject` and lets the next regular turn fully reinject initial context; mid-turn compaction uses `BeforeLastUserMessage` because "the model is trained to see the compaction summary as the last item in history" (`compact.rs:59-74`, `86-109`). Insertion point resolution prefers the last real user message, else before the summary, else before the last compaction item, else append (`compact.rs:571-637`). A `FINAL_ANSWER` agent message does not count as a real user insertion point (`compact.rs:588-597`).
- Each compaction advances the context window: `advance_auto_compact_window` bumps `window_number`, rotates the UUIDv7 `window_id` keeping `first_window_id` and `previous_window_id`, and resets the once-per-window reminder/fallback flags (`codex-rs/core/src/state/auto_compact_window.rs:77-85`); `current_window_id` renders as `"{thread_id}:{window_number}"` (`session/mod.rs:3718-3723`).
- After install, `recompute_token_usage` re-estimates usage locally from the new history and base instructions (`session/mod.rs:3934-3969`), and `BodyAfterPrefix` windows update their prefill baseline (`session/mod.rs:1538-1551`).
- Hooks: `run_pre_compact_hooks` may veto with `PreCompactHookOutcome::Stopped` (aborting with `CodexErr::TurnAborted`), and `run_post_compact_hooks` runs only on success and can also abort (`compact.rs:189-228`; `codex-rs/core/src/hook_runtime.rs:408-463`).
- Analytics: every attempt is tracked as `CodexCompactionEvent` with trigger (`Auto`/`Manual`), reason (`UserRequested`/`ContextLimit`/`ModelDownshift`/`CompHashChanged`), implementation (`Responses`/`ResponsesCompactionV2`/`ResponsesCompact`), phase (`StandaloneTurn`/`PreTurn`/`MidTurn`), status, and before/after token counts (`codex-rs/analytics/src/facts.rs:377-443`); the strategy field is hardcoded `CompactionStrategy::Memento` (`compact.rs:466`).

### Token-budget mode (summarization-free)

- With `Feature::TokenBudget`, compaction calls `Session::start_new_context_window`, which drops all message history and installs a fresh initial-context bundle (optionally retaining client-authored developer messages under `Feature::RetainClientDeveloperMessages`, truncated to the same 64_000 token budget), then replaces history and recomputes usage (`codex-rs/core/src/compact_token_budget.rs:21-93`, doc: "Token-budget compaction skips model/server summarization and installs a fresh context window instead"; `session/mod.rs:3740-3789`).
- Token-budget also adds model-visible nudges: a `TokenBudgetReminder` when remaining tokens fall to a threshold and a one-shot `AutoCompactFallbackPrompt` when the remaining window hits zero and no compaction will run (`codex-rs/core/src/session/token_budget.rs:58-113`; defaults may come from model-owned metadata, `token_budget.rs:23-56`). The default reminder template is "Your context window is nearly exhausted (only {n_remaining} tokens remaining) and will be automatically reset for you soon. ..." (`codex-rs/core/src/config/mod.rs:1072-1075`).

### Failure behavior and model fallback

- If a remote compaction attempt fails with a model-specific-looking error (`InvalidRequest`, `UnexpectedStatus`, `ContextWindowExceeded`, `UsageLimitReached`, `ServerOverloaded`, `InternalServerError`, `RetryLimit`), the harness retries the whole compaction against the **current** model's step context and records counter `codex.compaction.model_fallback` with outcome `succeeded`/`failed` (`codex-rs/core/src/compact_model_fallback.rs:9-63`; call sites `compact_remote.rs:224-263`, `compact_remote_v2.rs:242-281`). The fallback step context exists only for Codex-backend OpenAI auth when models differ (`turn.rs:1037-1056`).
- A failed **auto** compaction at pre-turn emits an error lifecycle event and ends the turn with no assistant response (`return Ok(None)` after `error!("Failed to run pre-sampling compact")`, `turn.rs:176-190`); a failed mid-turn compaction likewise ends the turn (`turn.rs:466-474`). Only `TurnAborted` (hook veto, user interrupt) propagates as an error in both cases.

## Key facts with anchors

- The transcript never stores system-role messages or `CompactionTrigger` items (`context_manager/history.rs:575-595`).
- `record_items` truncates every recorded `FunctionCallOutput`/`CustomToolCallOutput` with the model-configured `truncation_policy` scaled by 1.2x serialization budget (`history.rs:178-195`, `460-471`).
- History token accounting mixes server truth with local heuristics: `total_tokens` from the last response plus `approx_token_count` (bytes/4) for items added since and for retained reasoning blobs (`history.rs:374-432`; `codex-rs/utils/string/src/truncate.rs:4`, `71-84`).
- Auto-compaction fires at 90% of the model context window by default: `(context_window * 9) / 10`, with metadata-supplied limits clamped to that (`codex-rs/protocol/src/openai_models.rs:488-499`); the effective context window is `context_window * effective_context_window_percent / 100` with 95 as the default percent (`turn_context.rs:310-317`; `openai_models.rs:376-378`).
- There are three compaction phases (`StandaloneTurn`, `PreTurn`, `MidTurn`) and four reasons (`UserRequested`, `ContextLimit`, `ModelDownshift`, `CompHashChanged`) (`analytics/src/facts.rs:384-405`).
- Mid-turn compaction keeps the summary last by re-injecting initial context immediately before the last real user message; pre-turn/manual compaction clears the baseline so the next turn fully reinjects context (`compact.rs:59-74`, `571-637`).
- Local compaction retains newest user messages up to `COMPACT_USER_MESSAGE_MAX_TOKENS: usize = 20_000` and appends the summary as a user message (`compact.rs:57`, `639-717`).
- Remote v1 replaces old tool outputs with the fixed string "Output exceeded the available model context and was truncated" before asking the server to compact, then drops developer/wrapper/tool items from the returned transcript (`compact_remote.rs:50-51`, `354-397`, `399-455`).
- Remote v2 triggers compaction by appending a `CompactionTrigger` item to a normal streaming request and demanding exactly one `Compaction` output; it retains user/developer/system messages plus small agent messages under a 64_000-token budget (`compact_remote_v2.rs:65-66`, `400-457`, `512-543`, `556-632`; `compact_remote_v2_attempt.rs:71-85`).
- OpenAI and Azure-Responses providers report `RemoteCompactionSupport::V2`; everything else `Unsupported` (Bedrock explicitly `V1`), so non-OpenAI providers fall back to local summarization (`model-provider/src/provider.rs:327-340`; `model-provider/src/amazon_bedrock/mod.rs:185`).
- Post-compaction history is persisted to the rollout with the full `replacement_history` plus window ids (`session/mod.rs:3338-3387`), which the codexStateRollout component can cross-check.
- AGENTS.md is diffed through world-state section `agents_md` and rendered as `<INSTRUCTIONS>`-marked user content, never as part of the system prompt (`context/world_state/agents_md.rs:9-50`; `context/user_instructions.rs:9-29`).

Inferences about the brief are separated in the Relevance section below; everything above describes code at the pinned commit.

## Limitations and unknowns

- The remote summarizers are server-side black boxes. The client sends the transcript (v1: to `/responses/compact`; v2: as a streamed request ending in `CompactionTrigger`) and trusts the returned items; the code contains no visibility into what the server drops or rewrites (`compact_remote_request.rs:77-97`; `compact_remote_v2.rs:400-457`). The comment at `compact_remote_v2.rs:63-64` admits the client's 64_000 retention budget only "mirrors" the server default.
- Production auto-compact limits and context windows are delivered by the `/models` endpoint and are not pinned in the repository; only the 90% clamp and 95% effective-window default are visible in code (`openai_models.rs:436-447`, `488-499`). Any claim about a specific model's trigger point needs live metadata.
- Token accounting is deliberately coarse ("a coarse lower bound", `history.rs:245-246`; bytes/4, `utils/string/src/truncate.rs:4`). Trigger accuracy therefore depends on server-reported `total_tokens` for the bulk of usage and on heuristics only for items recorded after the last response (`history.rs:415-432`).
- Local compaction summarizes while the history is already over budget; its mitigation is dropping the oldest items until the request fits (`compact.rs:309-324`), which can lose exactly the early-turn context the summary is supposed to capture. Whether this matters in practice is not observable from code.
- `SUMMARIZATION_PROMPT` content quality is a judgment call; I transcribed it but did not evaluate it. The analytics strategy label `Memento` (`compact.rs:466`) is a name only; no strategy selection logic exists in the tree I inspected.
- Mid-turn injection ("the model is trained to see the compaction summary as the last item", `compact.rs:66-67`) references model training conventions that cannot be verified from the repository.
- I did not trace every world-state section's diff output (plugins/apps/environments-instructions internals beyond their registration at `session/world_state.rs:220-256`), nor the rollout-reconstruction consumer of `replacement_history` (covered by the codexStateRollout component). Snapshot tests under `core/tests/suite/snapshots/` confirm shapes like `<ENVIRONMENT_CONTEXT:cwd=<CWD>>` exist but were not audited exhaustively.
- `turn_state: Option<Arc<OnceLock<String>>>` threading through remote v1 (`compact_remote_request.rs:83`, `client.rs:619-620`) appears to carry server turn state headers; I did not verify the header semantics beyond passing it through.

## Relevance to the brief

This is central evidence for RQ1/RQ2 on the "context management and compaction" dimension for Codex. Inferences (mine, not code claims):

- Codex's distinctive design, versus what I expect the comparison matrix will show, is the **diff-based world state**: system-context pieces (AGENTS.md, environment, permissions, model identity) are typed sections with stable IDs whose changes are injected as small user/developer fragments, with full reinjection only after compaction, rollback, or baseline loss (`session/mod.rs:3810-3849`; `context/world_state/mod.rs:192-245`). This is a prompt-cache-conscious alternative to re-prepending a large static system prompt every turn; the stable synthetic-output UUIDs (`normalize.rs:133-146`) show cache reuse is an explicit goal. I infer this is the main "genuine difference" axis against OpenCode's session compaction module and Claude Code's closed compaction.
- The remote/local split maps directly onto the provider question: with the default OpenAI provider, compaction is server-side by default (`remote_compaction_v2` stable and enabled, provider capability `V2`, `features/src/lib.rs:1517-1522`, `model-provider/src/provider.rs:327-340`). Local summarization with the shipped `SUMMARIZATION_PROMPT` is effectively the path for third-party providers. Any cross-system comparison of "what compaction preserves" must therefore distinguish Codex-by-OpenAI (opaque encrypted `Compaction` item) from Codex-by-other-provider (20k-token user-message + readable summary).
- The token-budget mode previewed behind `Feature::TokenBudget` (default off) is a different compaction philosophy entirely: no summary, hard window resets, model-visible window ids, and a `new_context` model tool (`compact_token_budget.rs:21-25`; `session/world_state.rs:106-129`; `tools/handlers/new_context_window.rs:27-43`). Worth flagging in the report as "Codex is mid-migration between compaction designs" rather than treating the summarization path as canonical.
- Left open for synthesis: Claude Code's compaction is closed (`claudeCodePluginSurface` notes will only show hook surfaces), so this note anchors the Codex side of any compaction comparison; OpenCode's `session/compaction.ts`/`overflow.ts` (opencodeContextCompaction note) will be the other code-verifiable side.
