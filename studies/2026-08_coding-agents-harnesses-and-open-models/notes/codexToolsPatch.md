## Purpose and role in the harness

This component is Codex's effecting layer: it defines which tools the model can call, converts model response items into tool invocations, and executes file edits and shell commands under approval and sandbox control.

- `ToolRegistry` holds one runtime per tool name keyed by `ToolName` (namespace + name) (`codex-rs/core/src/tools/registry.rs:269-273`). `ToolRouter` pairs that registry with the model-visible specs for the current step (`codex-rs/core/src/tools/router.rs:68-71`).
- The per-step tool surface is assembled by `build_tool_router` in `spec_plan.rs`, which registers core handlers, MCP tools, extension tools, and dynamic tools, then finalizes model-visible specs (`codex-rs/core/src/tools/spec_plan.rs:121-176`, `488-523`).
- apply-patch is a custom ("freeform") tool exposed to the model with an embedded Lark grammar, plus a shell-command interception path that lets `bash -lc 'apply_patch <<EOF...EOF'` calls be handled in-process instead of spawning a process (`codex-rs/core/src/tools/handlers/apply_patch_spec.rs:5-28`, `codex-rs/core/src/tools/handlers/apply_patch.rs:500-545`).
- Shell execution has two model-facing surfaces: `shell_command` (fire-and-forget, pipes) and `exec_command`/`write_stdin` (PTY-based "unified exec" sessions), selected per model and feature flags (`codex-rs/core/src/tools/spec_plan.rs:962-1011`).
- Execution routing for exec-like tools and patches goes through a shared orchestrator that sequences approval, sandbox selection, and escalation retry (`codex-rs/core/src/tools/orchestrator.rs:1-8`, `135-512`).

## Mechanism

### Tool registration and the model-visible surface

- Every local tool implements `ToolExecutor<ToolInvocation>`: `tool_name()`, `spec()`, `exposure()` (default `Direct`), `supports_parallel_tool_calls()` (default `false`), `handle()` (`codex-rs/tools/src/tool_executor.rs:106-127`). Core layers `CoreToolRuntime` on top, adding hook payloads, telemetry tags, diff consumers, and code-mode definitions (`codex-rs/core/src/tools/registry.rs:53-170`).
- `ToolExposure` controls per-surface visibility: `Direct`, `Deferred` (tool-search discoverable), `DeferredModelOnly`, `DirectModelOnly`, `CodeModeOnly`, `Hidden` (`codex-rs/tools/src/tool_executor.rs:49-99`).
- Registration: trusted duplicates abort via `error_or_panic("tool {tool_name} already registered")` (`codex-rs/core/src/tools/registry.rs:306-321`). External (MCP) duplicates are skipped with a warning and record the first collision (`codex-rs/core/src/tools/registry.rs:340-369`). The default-namespace name `shell_command` is reserved: external registration is rejected with "skipping external tool with reserved name" (`codex-rs/core/src/tools/registry.rs:346-352`).
- `ToolName` carries an optional namespace; the default namespace constant is `"functions"` (`codex-rs/protocol/src/tool_name.rs:7`, `39-51`). `flat_tool_name` flattens to a single string only for legacy boundaries such as hook payloads and Responses tool names (`codex-rs/core/src/tools/mod.rs:41-58`).
- `ToolSpec` serializes as Responses API tools: `function`, `namespace`, `tool_search`, `web_search`, and `custom` (freeform) (`codex-rs/tools/src/tool_spec.rs:18-68`).
- `build_model_visible_specs` includes only tools whose exposure `is_direct()`, then merges hosted specs and, when namespace tools are enabled, folds specs into namespaces (`codex-rs/core/src/tools/spec_plan.rs:487-523`).

### Default tool set assembly (per step)

- `add_core_tool_sources` special-cases guardian reviewer sessions (only `exec_command`, `write_stdin`, `view_image`, and only under a `Managed` permission profile); otherwise it calls `add_shell_tools`, `add_mcp_resource_tools`, `add_core_utility_tools`, `add_collaboration_tools` (`codex-rs/core/src/tools/spec_plan.rs:892-938`).
- Shell tool selection (`spec_plan.rs:962-1011`): `shell_type_for_model_and_features` picks `UnifiedExec` (registers `ExecCommandHandler` + `WriteStdinHandler`, and registers `ShellCommandHandler` with `ToolExposure::Hidden` "while unified exec is model-visible", `spec_plan.rs:993-1000), `ShellCommand` (registers `ShellCommandHandler`), or `Disabled` (nothing).
- The selection policy (`codex-rs/tools/src/tool_config.rs:81-116`): everything gated by `Feature::ShellTool`; model `shell_type` `Default` or `Local` map to `ShellCommand`; unified exec requires `Feature::UnifiedExec` plus conpty support (`codex_utils_pty::conpty_supported()`), else falls back to `ShellCommand`; zsh-fork variants require `Feature::ShellZshFork` and `Feature::UnifiedExecZshFork` composition (`tool_config.rs:49-79`).
- `apply_patch` is registered only when `turn_context.model_info.apply_patch_tool_type.is_some()` and an environment exists (`codex-rs/core/src/tools/spec_plan.rs:1112-1116`). `ApplyPatchToolType` has a single variant, `Freeform` (`codex-rs/protocol/src/openai_models.rs:307-311`). `ModelInfo` is backend `/models` metadata (`codex-rs/protocol/src/openai_models.rs:389-390`), so which models get the freeform patch tool is server-decided (see Limitations).

### Tool call dispatch

- `ToolRouter::build_tool_call` converts protocol items: `ResponseItem::FunctionCall` → `ToolPayload::Function`, client-side `ToolSearchCall` (`execution == "client"`) → `tool_search`, `CustomToolCall` → `ToolPayload::Custom`; other items return `None` (`codex-rs/core/src/tools/router.rs:153-206`).
- Dispatch path `ToolRegistry::dispatch_any_with_terminal_outcome` (`codex-rs/core/src/tools/registry.rs:481-763`): increments the turn's `tool_calls` counter (`510-516`); unknown tool → `FunctionCallError::RespondToModel("unsupported call: {tool_name}")` (`519-537`, `825-830`); incompatible payload kind → `FunctionCallError::Fatal("tool {tool_name} invoked with incompatible payload")` (`551-567`); PreToolUse hooks may block (message becomes the model-visible error) or rewrite tool input (`569-613`); tool runs with otel tracing and a telemetry "command_category" tag derived from parsing shell-like commands into read/list_files/search/unknown (`617-631`); on success, PostToolUse hooks may block the result (returns error to model) or replace the model-visible output with a feedback string (`691-748`).
- `FunctionCallError` has exactly two variants, `RespondToModel(String)` and `Fatal(String)` (`codex-rs/tools/src/function_call_error.rs:4-10`; re-exported by `codex-rs/core/src/function_tool.rs:1`).
- Parallelism: `ToolCallRuntime` (per step) runs tool calls concurrently (`codex-rs/core/src/tools/parallel.rs:40-89`). `shell_command` and `exec_command` opt into parallel calls (`codex-rs/core/src/tools/handlers/shell/shell_command.rs:165-167`, `codex-rs/core/src/tools/handlers/unified_exec/exec_command.rs:97-99`).
- Tool outputs carrying external context mark the thread's memory mode as polluted when `memories.disable_on_external_context` is set (`codex-rs/core/src/tools/registry.rs:786-795`); details belong to the memory/state notes.
- Hook-facing names: `apply_patch` uses matcher aliases `Write` and `Edit` ("compatibility with hook configurations that describe edits using Claude Code-style names"), `spawn_agent` aliases `Agent`, and shell-like tools use hook name `Bash` (`codex-rs/core/src/tools/hook_names.rs:34-56`; unified exec post-tool payload uses `HookToolName::bash()` at `codex-rs/core/src/tools/handlers/unified_exec.rs:89-94`).

### apply-patch: format

- Model-visible definition: freeform tool `name: "apply_patch"`, `description: "The `apply_patch` tool can be used to edit files. This is a FREEFORM tool, so do not wrap the patch in JSON."`, `format: { type: "grammar", syntax: "lark", definition: <grammar> }` (`codex-rs/core/src/tools/handlers/apply_patch_spec.rs:9-28`). The grammar is embedded from `apply_patch.lark` via `include_str!` (`apply_patch_spec.rs:5`).
- Grammar (`codex-rs/core/src/tools/handlers/apply_patch.lark:1-19`): `start: begin_patch hunk+ end_patch`; markers `"*** Begin Patch"`, `"*** End Patch"` (trailing LF optional), hunk headers `"*** Add File: "` with `+` lines, `"*** Delete File: "`, `"*** Update File: "` with optional `"*** Move to: "`, change blocks with `@@`/`@@ <context>` headers, lines prefixed `+`, `-`, or space, and optional `"*** End of File"`. For multi-environment turns the spec injects an optional `"*** Environment ID: "` line after `*** Begin Patch` (`apply_patch_spec.rs:10-17`).
- Parser constants mirror the grammar: `BEGIN_PATCH_MARKER "*** Begin Patch"`, `END_PATCH_MARKER "*** End Patch"`, `ADD_FILE_MARKER "*** Add File: "`, `DELETE_FILE_MARKER "*** Delete File: "`, `UPDATE_FILE_MARKER "*** Update File: "`, `MOVE_TO_MARKER "*** Move to: "`, `EOF_MARKER "*** End of File"`, `CHANGE_CONTEXT_MARKER "@@ "`, `EMPTY_CHANGE_CONTEXT_MARKER "@@"` (`codex-rs/apply-patch/src/parser.rs:37-45`). The environment ID marker in the streaming parser is `"*** Environment ID:"` (`codex-rs/apply-patch/src/streaming_parser.rs:19`).
- Strict mode is compiled out: `const PARSE_IN_STRICT_MODE: bool = false`, with a comment that gpt-4.1 is "the only OpenAI model that knowingly requires lenient parsing" (`codex-rs/apply-patch/src/parser.rs:47-53`). Lenient mode strips a heredoc wrapper (`<<EOF`, `<<'EOF'`, `<<"EOF"` ... final line ending `EOF`, at least 4 lines) and tolerates leading/trailing whitespace around markers (`parser.rs:193-274`; module doc `parser.rs:24-25`).
- Core parsing: `parse_patch` checks boundary lines, then drives a `StreamingPatchParser` state machine over the joined text (`parser.rs:145-152`, `193-211`; `streaming_parser.rs:21-46`). The same streaming parser powers live argument-diff events while the model streams a patch (below).

### apply-patch: invocation detection and interception

- Command names accepted: `const APPLY_PATCH_COMMANDS: [&str; 2] = ["apply_patch", "applypatch"]` (`codex-rs/apply-patch/src/invocation.rs:28`).
- Three invocation shapes recognized by `maybe_parse_apply_patch`: direct `["apply_patch", <body>]` (`invocation.rs:114-119`); and shell-script form for `bash|zsh|sh` with `-lc`/`-c`, `pwsh|powershell` with `-Command` (optionally after `-NoProfile`), `cmd` with `/c` (`invocation.rs:63-98`).
- Heredoc extraction uses a Tree-sitter Bash query that requires the heredoc-redirected statement to be the only top-level statement, optionally prefixed by `cd <path> && ` (connector must be `&&`, exactly one positional arg to `cd`); other prefixes/suffixes like `echo foo;` or `&& echo done` do not match (`invocation.rs:291-441`). The `cd` path becomes the patch `workdir` (`invocation.rs:227-231`).
- Verification wrapper `maybe_parse_apply_patch_verified_with_mode` first rejects implicit invocations: a raw patch body passed as the entire command (or as the entire shell script) returns `CorrectnessError(ApplyPatchError::ImplicitInvocation)` (`invocation.rs:167-178`), whose message is `"patch detected without explicit call to apply_patch. Rerun as [\"apply_patch\", \"<patch>\"]"` (`codex-rs/apply-patch/src/lib.rs:90-94`).
- The shell tool handler intercepts before spawning: `run_exec_like` calls `intercept_apply_patch`; `NotApplyPatch` and `ShellParseError` fall through to normal exec, a verified body is applied in-process, and `CorrectnessError` becomes a model-visible error (`codex-rs/core/src/tools/handlers/shell.rs:140-156`, `codex-rs/core/src/tools/handlers/apply_patch.rs:500-545`). The freeform handler likewise parses `ToolPayload::Custom { input }` and reports parse failures as `RespondToModel("apply_patch verification failed: {err}")` (`apply_patch.rs:345-357`, `375-387`, `430-445`).
- A standalone executable path exists: the Codex binary self-invoked with argv[1] flag `--codex-run-as-apply-patch` (`CODEX_CORE_APPLY_PATCH_ARG1`, `codex-rs/apply-patch/src/lib.rs:45-52`) runs `apply_patch` with the patch as argv[1] or from stdin, refusing extra args with exit code 2 (`standalone_executable.rs:11-47`).

### apply-patch: verification, matching, application, failure behavior

- Verification (`try_verify_apply_patch_args`, `invocation.rs:214-289`): paths resolve against the effective cwd (patch workdir joined to cwd); multiple hunks targeting one path fail with `"multiple operations target {path}"` (`235-241`); `Delete File` reads the file (missing file → IoError) so the deleted content is known (`246-253`); `Update File` hunks are compiled immediately against the current file contents into a unified diff plus the full new content (`255-279`). The result is an `ApplyPatchAction` keyed by absolute `PathUri` (`lib.rs:170-185`).
- Line matching (`compute_replacements`, `codex-rs/apply-patch/src/file_update.rs:82-216`): each chunk's optional `change_context` line is located with `seek_sequence` starting after the previous chunk; miss → `ApplyPatchError::ComputeReplacements("Failed to find context '{ctx_line}' in {path}")` (`94-108`). Each `old_lines` block is matched verbatim; on failure with a trailing empty line, it retries without that line (`139-165`); total miss → `"Failed to find expected lines in {path}:\n{lines}"` (`204-210`).
- `seek_sequence` matches with decreasing strictness in four passes: exact, `trim_end`, `trim`, then normalization of Unicode punctuation and spaces to ASCII (dash code points U+2010..U+2015 and U+2212 to `-`, curly quotes to `'`/`"`, non-breaking and exotic spaces to space) (`codex-rs/apply-patch/src/seek_sequence.rs:1-115`). Patterns longer than the file return `None` instead of panicking (a pre-2025-04-12 bug, per comment at `seek_sequence.rs:23-29`).
- Application (`apply_hunks_to_files`, `codex-rs/apply-patch/src/lib.rs:450-663`): empty patch bails `"No files were modified."` (`458-460`). `AddFile` records any overwritten content then writes, creating missing parent directories on `NotFound` and retrying once (`484-505`, `726-762`). `DeleteFile` refuses directories (`512-519`, `665-678`) and removes non-recursively, non-force (`520-545`). `UpdateFile` writes derived contents; with `Move to:`, it writes the destination first, then removes the source, recording the intermediate state if removal fails (`569-633`). Success prints `"Success. Updated the following files:"` with `A`/`M`/`D` lines (`766-781`).
- Failure atomicity: application is sequential per hunk with no rollback; instead a failure returns `ApplyPatchFailure { error, delta }` where `delta` lists committed changes and an `exact` flag (`lib.rs:226-316`). A failed write sets `exact = false` (a truncated file may have changed before the error), and unreadable/symlinked paths also degrade exactness (`465-478`, `507-511`, `695-724`). The runtime accumulates `committed_delta` across orchestrator attempts (`codex-rs/core/src/tools/runtimes/apply_patch.rs:190-194`).
- File update mode: default `NormalizeToLf`; feature flag `Feature::ApplyPatchPreserveLineEndings` switches to `PreserveLineEndings` (`codex-rs/core/src/tools/handlers/apply_patch.rs:60-70`; `codex-rs/apply-patch/src/lib.rs:59-76`). The standalone/arg0 path reads env var `CODEX_APPLY_PATCH_PRESERVE_LINE_ENDINGS` (`"1"` enables) (`lib.rs:54-57`, `69-76`), which the shell exec plumbing injects into child environments (`codex-rs/core/src/exec_env.rs:70-74`) and unified exec scrubs from env-policy inheritance (`codex-rs/core/src/unified_exec/process_manager.rs:125-148`).
- Safety gate before execution (`codex-rs/core/src/apply_patch.rs:22-61` calling `codex-rs/core/src/safety.rs:26-98`): empty patch → `Reject { reason: "empty patch" }`; `AskForApproval::UnlessTrusted` → `AskUser`; patches constrained to writable paths (`is_write_patch_constrained_to_writable_paths`, `safety.rs:123-191`) auto-approve under `Disabled`/`External` profiles, or when a platform sandbox exists; otherwise `AskUser`, or `Reject` when approvals are configured to refuse, with constants `"writing outside of the project; rejected by user approval settings"` and `"writing is blocked by read-only sandbox; rejected by user approval settings"` (`safety.rs:14-17`). The rejection surfaces to the model as `"patch rejected: {reason}"` (`apply_patch.rs:57-59`).
- Execution under orchestrator: `ApplyPatchRuntime` rebuilds the patch from `ApplyPatchAction.patch`, writes through the environment's `ExecutorFileSystem` with a `FileSystemSandboxContext`, maps failures to an `ExecToolCallOutput` with exit code 1, and detects likely sandbox denials to convert them into `SandboxErr::Denied` so the orchestrator can offer escalation (`codex-rs/core/src/tools/runtimes/apply_patch.rs:165-224`).
- Streaming UX: the handler provides a `ToolArgumentDiffConsumer` that incrementally parses streamed patch arguments and emits `PatchApplyUpdated` events, buffered at `APPLY_PATCH_ARGUMENT_DIFF_BUFFER_INTERVAL = Duration::from_millis(500)`, gated by `Feature::ApplyPatchStreamingEvents` (`codex-rs/core/src/tools/handlers/apply_patch.rs:58`, `85-154`, `455-457`).

### Shell execution plumbing

- `shell_command` spec: function tool, name `"shell_command"`; non-Windows description is `"Runs a shell command and returns its output.\n- Always set the `workdir` param when using the shell_command function. Do not use `cd` unless absolutely necessary."`; required param `command`, optional `workdir`, `timeout_ms` described as `"Maximum command runtime. - Handler: parses `ShellCommandToolCallParams`, resolves `workdir` against the environment cwd (`codex-rs/core/src/tools/handlers/mod.rs:159-169`; `shell/shell_command.rs:174-250`), builds argv via `Shell::derive_exec_args`: zsh/bash/sh → `[shell, -lc|-c, command]` (login flag decides), PowerShell → `[shell, (-NoProfile)?, -Command, command]`, cmd → `[shell, /c, command]` (`codex-rs/core/src/shell.rs:22-49`). - `run_exec_like` (shared by shell and unified-exec handlers): strips output-env, merges granted turn permissions, validates `additional_permissions` (errors like `"`justification` requires an explicit `sandbox_permissions`..."` at `handlers/mod.rs:94-105`), intercepts apply_patch, computes the exec approval requirement from the exec policy, then runs `ShellRuntime` under `ToolOrchestrator` (`codex-rs/core/src/tools/handlers/shell.rs:64-248`, `175-192`).
- Orchestrator sequence (`codex-rs/core/src/tools/orchestrator.rs:135-512`): 1) approval per `ExecApprovalRequirement` (`Skip` records a config approval; `Forbidden` rejects; `NeedsApproval` requests, with cached session approvals via `with_cached_approval`, `codex-rs/core/src/tools/sandboxing.rs:64-116`); 2) first attempt under the selected sandbox (network approval wired around the attempt, `65-133`); 3) on `SandboxErr::Denied`, optionally re-approve and retry without the sandbox when policy allows (`344-497`). Retry denial reason shown to the user: `"command failed; retry without sandbox?"` (`527-531`). `ShellRuntime` and `ApplyPatchRuntime` both set `escalate_on_failure() = true` (`codex-rs/core/src/tools/runtimes/shell.rs:115-122`, `runtimes/apply_patch.rs:113-120`).
- Low-level exec (`codex-rs/core/src/exec.rs`): `DEFAULT_EXEC_COMMAND_TIMEOUT_MS: u64 = 10_000` (`:61`); output retention cap `EXEC_OUTPUT_MAX_BYTES = DEFAULT_OUTPUT_BYTES_CAP` where `DEFAULT_OUTPUT_BYTES_CAP: usize = 1024 * 1024` (`exec.rs:75-79`; `codex-rs/utils/pty/src/lib.rs:12`); live delta events capped at `MAX_EXEC_OUTPUT_DELTAS_PER_CALL: usize = 10_000` (`exec.rs:83`); stdout/stderr drain guarded by `IO_DRAIN_TIMEOUT_MS: u64 = 2_000` (`exec.rs:92`). On timeout the process group is killed and a synthetic exit status `128 + 64 = 192` is reported (`:65-67`, `994-1003`); cancellation sends SIGTERM to the process group with a `CANCELLATION_TERMINATION_GRACE_PERIOD = Duration::from_millis(50)` before kill (`:69`, `1004-1035`). `process_exec_tool_call` builds an `ExecRequest` and routes through `crate::sandboxing::execute_env` (`298-318`).
- Model-facing output formatting for shell tools: `format_exec_output_for_model` emits `Exit code: {}`, `Wall time: {n} seconds`, optional `Total output lines: {}`, then `Output:` followed by truncated text (`codex-rs/core/src/tools/mod.rs:96-123`); timed-out output is prefixed `"command timed out after {} milliseconds"` (`136-146`). Truncation uses the model's `truncation_policy` with a middle-truncation algorithm and a `"Warning: truncated output (original token count: {n})"` header (`codex-rs/utils/output-truncation/src/lib.rs:12-30`).
- Unified exec (`exec_command`/`write_stdin`): spec name `"exec_command"`, described `"Runs a command in a PTY, returning output or a session ID for ongoing interaction."`; required `cmd`; optional `workdir`, `tty`, `yield_time_ms`, `max_output_tokens` (`"Defaults to 10000 tokens; larger requests may be capped by policy."`), `shell`, `login`, `environment_id`, approval params; structured `output_schema` requiring `wall_time_seconds` and `output` (`shell_spec.rs:21-111`, `264-296`). Argument defaults: `yield_time_ms` 10_000, `tty` false (`codex-rs/core/src/tools/handlers/unified_exec.rs:60-70`); `write_stdin` default yield is 250 ms (`:64-66`; spec text at `shell_spec.rs:128-131`). Runtime bounds: `MIN_YIELD_TIME_MS: u64 = 250`, `MIN_EMPTY_YIELD_TIME_MS: u64 = 5_000`, `MAX_YIELD_TIME_MS: u64 = 30_000`, `DEFAULT_MAX_BACKGROUND_TERMINAL_TIMEOUT_MS: u64 = 300_000`, `DEFAULT_MAX_OUTPUT_TOKENS: usize = 10_000`, `UNIFIED_EXEC_OUTPUT_MAX_BYTES: usize = 1024 * 1024`, `UNIFIED_EXEC_OUTPUT_MAX_TOKENS: usize = UNIFIED_EXEC_OUTPUT_MAX_BYTES / 4`, `MAX_UNIFIED_EXEC_PROCESSES: usize = 64` (`codex-rs/core/src/unified_exec/mod.rs:66-75`). Spawned sessions get fixed env `NO_COLOR=1`, `TERM=dumb`, `LANG/LC_CTYPE/LC_ALL=C.UTF-8`, `COLORTERM=` (empty), `PAGER/GIT_PAGER/GH_PAGER=cat`, `CODEX_CI=1` (`codex-rs/core/src/unified_exec/process_manager.rs:83-94`).
- `codex-rs/tools/` (`codex-tools`) is an extraction crate: host-facing tool models (`ToolSpec`, `ToolExecutor`, `ToolExposure`, shell-type selection) with orchestration deliberately kept in `codex-core` (`codex-rs/tools/README.md:1-43`). `codex-rs/shell-command/` provides shell detection, tree-sitter-bash command parsing for safety checks (`try_parse_word_only_commands_sequence` whitelists `program/list/pipeline/command/word/string/...` node kinds and operators `&& || ; |`, `codex-rs/shell-command/src/bash.rs:29-98`), and PowerShell equivalents (`shell-command/src/lib.rs:1-12`).

## Key facts with anchors

- The model-visible apply_patch tool is a Responses API `custom` tool whose schema is a Lark grammar, not JSON (`codex-rs/core/src/tools/handlers/apply_patch_spec.rs:9-28`; `codex-rs/tools/src/tool_spec.rs:54-56`).
- Parser strict mode is off globally: `PARSE_IN_STRICT_MODE = false` because gpt-4.1 wraps patches in heredocs (`codex-rs/apply-patch/src/parser.rs:47-53`).
- `apply_patch` invocations are accepted both as a freeform tool call and as intercepted shell commands (`bash|zsh|sh -lc|-c`, `pwsh|powershell [-NoProfile] -Command`, `cmd /c`), with the command names `apply_patch` or `applypatch` (`codex-rs/apply-patch/src/invocation.rs:28`, `63-98`, `114-119`; `codex-rs/core/src/tools/handlers/shell.rs:140-156`).
- Implicit raw patches are refused with a rerun instruction rather than applied (`codex-rs/apply-patch/src/lib.rs:90-94`; `invocation.rs:167-178`).
- Update-hunk matching is four-pass fuzzy (exact, rstrip, trim, Unicode-normalized) (`codex-rs/apply-patch/src/seek_sequence.rs:12-115`).
- Failed multi-hunk patches are not rolled back; callers get a committed-delta record plus an exactness flag (`codex-rs/apply-patch/src/lib.rs:226-316`, `465-478`, `569-633`).
- The registry reserves `shell_command` against external (MCP) registration (`codex-rs/core/src/tools/registry.rs:346-352`).

## Limitations and unknowns

- Which models receive `apply_patch`, which shell tool, and which truncation budget are decided by backend-served `ModelInfo` (`codex-rs/protocol/src/openai_models.rs:389-428`); the pinned tree shows only code-side fallbacks and test fixtures, not production values. A literature-gate verdict on "what tool surface a typical Codex CLI session sees" must hedge accordingly.
- Freeform grammar-constrained tool calls require the Responses API `custom` tool type; non-OpenAI providers get whatever their `ToolSpec` serialization supports. I did not trace provider-specific capability checks for freeform tools beyond `apply_patch_tool_type.is_some()` gating (`codex-rs/core/src/tools/spec_plan.rs:1112-1116`).
- The zsh-fork backend is only observed at its entry points (`codex-rs/core/src/tools/runtimes/shell.rs:264-284`); the escalation adapter itself lives in `shell-escalation/` and belongs to the sandboxing note.
- Sandbox selection internals (`SandboxManager::select_initial`, seatbelt/landlock/bwrap transforms) are in `codex-rs/sandboxing/` and out of scope for this note; the orchestrator note stops at the `SandboxAttempt` boundary.
- MCP tool-call execution (`codex-rs/core/src/mcp_tool_call.rs`, 2263 lines) was read only for imports and registration surface; its approval and elicitation flow is covered by the extensibility component.
- Code-mode (ToolMode::CodeMode) reshapes the tool surface and augments specs (`spec_plan.rs:324-338`, `525-547`); I did not trace the code-mode runtime, which is a separate mechanism.
- Timeout exit-code handling returns synthetic status 192 to the aggregation layer; I did not verify how downstream consumers translate it for the model beyond the `timed_out` flag formatting (`codex-rs/core/src/tools/mod.rs:136-146`).
- No runtime behavior was observed; all claims are static reads at the pinned commit. The `.lark` file documents the grammar given to the model, but model compliance with it is runtime/server behavior and is not verifiable here.

## Relevance to the brief

Inference, clearly separated from the code facts above:

- RQ1/RQ2 (harness architecture, tools dimension): Codex's tool layer is unusual in three ways worth contrasting with Claude Code and OpenCode. First, apply-patch is a grammar-constrained freeform tool, not a JSON-schema function, and the same patch format is also sniffed and intercepted out of plain shell calls; this makes "the edit tool" partly a model-facing DSL and partly a shell shim. Second, tools are registered per step from features plus server model metadata rather than from a static built-in list, so the tool surface itself is a runtime negotiation. Third, both file edits and shell exec route through one orchestrator (approval, sandbox attempt, escalation retry), which is Codex's concrete answer to the capability-vs-safety question (RQ3): the safety envelope is per-invocation and policy-driven, not per-tool.
- RQ3: the escalation retry pattern (sandboxed attempt, then approval-gated unsandboxed retry, `orchestrator.rs:334-421`) plus implicit-patch refusal and reserved tool names shows Codex treating sandbox denial as a recoverable, user-mediated state. Compare against whatever permission-ruleset mechanism the OpenCode note finds.
- The Claude-Code-style hook aliases (`Write`, `Edit`, `Bash`, `Agent`) are a small but real interoperability fact for the comparison matrix: Codex hook configs intentionally accept Claude Code naming (`hook_names.rs:28-56`).
- Open: how `ask_for_approval`/permission profiles default in shipped configs (config/providers note), and how the TUI renders the orchestrator's escalations (interfaces note).
