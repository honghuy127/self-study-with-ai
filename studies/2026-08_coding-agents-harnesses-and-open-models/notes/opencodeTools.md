## Purpose and role in the harness

The tool subsystem is what the model can act with per turn. It defines a uniform tool contract (id, description, parameter schema, Effect-based `execute`), a registry that instantiates the built-in tools plus plugin and filesystem custom tools (`packages/opencode/src/tool/registry.ts:101-119`, `209-252`), a per-model tool-set filter (`registry.ts:291-308`), and the patch application machinery (`packages/opencode/src/patch/index.ts`). Every tool call passes through schema decode, permission asks, execution, and output truncation in the shared wrapper (`packages/opencode/src/tool/tool.ts:99-149`). The registry's output is converted to Vercel AI SDK tools with JSON Schemas in `packages/opencode/src/session/tools.ts:92-133`, which is the exact surface the LLM sees.

## Mechanism

### Tool contract and wrapper

A tool is `Def`: `id`, `description`, `parameters` (Effect `Schema` decoder), optional `jsonSchema` (JSONSchema7), and `execute(args, ctx): Effect<ExecuteResult>` where `ExecuteResult` is `{ title, metadata, output, attachments? }` (`tool.ts:48-65`). `Tool.define(id, init)` wraps every `execute`: arguments are decoded once with a hoisted `Schema.decodeUnknownEffect` closure (`tool.ts:108-111`); decode failure raises `InvalidArgumentsError`, whose `message` getter is the model-facing text "The {tool} tool was called with invalid arguments: {detail}." followed by "Please rewrite the input so it satisfies the expected schema." (`tool.ts:24-34`). Successful output is auto-truncated by the Truncate service unless the tool already set `metadata.truncated` (`tool.ts:131-144`). `ctx` carries `sessionID`, `messageID`, `agent`, `abort` signal, `messages`, a `metadata()` progress callback, and `ask()` for permissions (`tool.ts:36-46`).

### Registry build and per-model selection

The registry layer resolves all built-in tools (`registry.ts:101-119`) and builds state with 13 unconditional built-ins (invalid, bash, read, glob, grep, edit, write, task, webfetch, todowrite, websearch, skill, apply_patch) plus up to 4 conditional ones, in this order: question, then after apply_patch the execute (code mode), lsp, and plan_exit entries (`registry.ts:229-249`). Custom tools load from `{tool,tools}/*.{js,ts}` in each config directory (`registry.ts:183-197`) and from plugins' `tool` exports (`registry.ts:199-204`); plugin tools bridge Zod args to JSON Schema at the boundary (`registry.ts:125-141`). `tools(model)` filters per request (`registry.ts:291-308`):

- `websearch` only if the provider is `opencode` or `opencode-go`, or the exa/parallel flags are on (`registry.ts:58-65`, `293-295`).
- `apply_patch` only if `modelID.includes("gpt-")` and not `"oss"` and not `"gpt-4"`; `edit` and `write` are shown exactly when `apply_patch` is hidden (`registry.ts:297-300`).
- `plan_exit` only if `experimentalPlanMode` and `client === "cli"` (`registry.ts:248`); `lsp` only if `experimentalLspTool` (`registry.ts:247`); `execute` only if `experimentalCodeMode` and a non-empty MCP catalog (`registry.ts:118-119`, `226`, `305-308`).
- `question` is in the built-in list when the client is `app`, `cli`, or `desktop`, or `OPENCODE_ENABLE_QUESTION_TOOL` is set (`registry.ts:207`).
- The `task` tool's description is extended at request time with the list of permitted subagents, sorted by name, each as `- {name}: {description}` (`registry.ts:265-278`, `327`).
- A plugin hook `tool.definition` may rewrite description, parameters, or jsonSchema before the tool is exposed (`registry.ts:318-322`).

### Schema exposed to the model

`packages/opencode/src/session/tools.ts:92-101` iterates `registry.tools(...)` and wraps each def in AI SDK `tool({ description, inputSchema: jsonSchema(schema) })` where `schema = ProviderTransform.schema(input.model, ToolJsonSchema.fromTool(item))`. `ToolJsonSchema.fromSchema` converts the Effect Schema to a Draft 2020-12 JSON Schema, normalizes optional unions, flattens `allOf`, inlines local `$ref`s, and caches per schema (`packages/opencode/src/tool/json-schema.ts:8-22`). Built-in tools rely on this conversion; plugin tools ship their own `jsonSchema` (`registry.ts:138-141`).

### Permission ask channel

Tools gate side effects through `ctx.ask({ permission, patterns, always, metadata })` (`tool.ts:45`), implemented in `session/tools.ts:81-90` as `Permission.ask` over the merged agent+session ruleset. Evaluation: the last matching rule wins; if no rule matches, the default action is `ask` (`packages/opencode/src/permission/index.ts:28-38`). `deny` fails the call immediately (`permission/index.ts:75-79`); `ask` publishes an event and blocks on a deferred until the UI replies (`permission/index.ts:96-106`). Reply `always` appends allow rules for every pattern in the request's `always` list (`permission/index.ts:143-151`); reply `reject` raises `RejectedError` and also force-rejects all other pending asks in the same session (`permission/index.ts:121-138`). The session processor marks the tool part `status: "error"` and, for `RejectedError`, may break the loop (`packages/opencode/src/session/processor.ts:186-203`). Permission keys used by these tools: `read` (`read.ts:255-260`), `glob` (`glob.ts:28-36`), `grep` (`grep.ts:39-48`), `edit` (`edit.ts:145-153`, `write.ts:54-62`, `apply_patch.ts:206-215`), `bash` (`shell.ts:283-291`), `external_directory` (`shell.ts:270-280`, `external-directory.ts:35-43`), `webfetch` (`webfetch.ts:39-48`), `websearch` (`websearch.ts:119-131`), `todowrite` (`todo.ts:24-29`), `skill` (`skill.ts:27-32`), `task` (`task.ts:120-128`), `lsp` (`lsp.ts:56-61`). `edit`, `write`, and `apply_patch` all map to the `edit` permission key for rule matching (`packages/opencode/src/permission/index.ts:205-209`).

### bash tool

The shell tool is registered under `ToolID = "bash"` for backward compatibility even though it drives bash, pwsh, powershell, or cmd (`packages/opencode/src/tool/shell/id.ts:14-17`, comment: "Keep the exposed tool ID and permission key as \"bash\" ... Rename with opencode 2.0."). Parameters: `command` (string, required), `timeout` (optional positive int, milliseconds), `workdir` (optional) (`shell/prompt.ts:15-23`). Default timeout is `flags.bashDefaultTimeoutMs ?? 2 * 60 * 1000` (`shell.ts:347`). Shell selection: `Shell.acceptable(cfg.shell)` (`shell.ts:600`) resolves the configured shell or `$SHELL`, rejecting denied shells (`fish`, `nu`), with fallbacks `/bin/zsh` on darwin, then `bash` on PATH, then `/bin/sh` (`packages/core/src/shell.ts:13-23`, `114-121`, `132-137`, `214-221`).

Before running anything, the command is parsed with tree-sitter (bash or PowerShell grammar, wasm loaded lazily) (`shell.ts:257-261`, `311-336`). The scan walks every `command` node (`shell.ts:392-411`): path-bearing arguments of commands in the `FILES` set (`cd`, `chdir`, `popd`, `pushd`, `push-location`, `set-location`, `rm`, `cp`, `mv`, `mkdir`, `touch`, `chmod`, `chown`, `cat`, plus PowerShell `get-content`/`set-content`/... and cmd `copy`/`del`/... sets) (`shell.ts:28-64`) are resolved and, if outside the project instance, collected into an `external_directory` permission ask with `<dir>/*` globs (`shell.ts:263-280`, `401-404`); each command's source text goes into `patterns` and a `BashArity.prefix(tokens).join(" ") + " *"` string into `always` (`shell.ts:407-410`), where `BashArity` is a command-prefix arity table (`git` 2, `npm run` 3, etc.) generated by an LLM prompt recorded in the comment (`packages/opencode/src/permission/arity.ts:1-9`, `11-24`, `83`, `114`). So a bash ask always shows the exact command and, on "always" approval, remembers a wildcard like `git status *`.

Execution spawns `ChildProcess.make(command, [], { shell, cwd, env, stdin: "ignore", detached: process.platform !== "win32" })` (`shell.ts:303-309`); PowerShell instead gets `["-NoLogo", "-NoProfile", "-NonInteractive", "-Command", command]` (`shell.ts:295`). Env is `process.env` merged with the `shell.env` plugin hook (`shell.ts:416-426`). Output handling: chunks accumulate in a ring capped at `limits.maxBytes * 2` bytes (`shell.ts:438-439`, `486-496`); when the running total exceeds `maxBytes`, full output spools to a truncation file and streaming appends continue (`shell.ts:500-522`); metadata streams a rolling preview capped at `MAX_METADATA_LENGTH = 30_000` chars of the tail (`shell.ts:27`, `220-223`). The race of exit/abort/timeout kills the process with `forceKillAfter: "3 seconds"` on abort or timeout (`shell.ts:542-555`); timeout appends "shell tool terminated command after exceeding timeout {n} ms..." guidance (`shell.ts:562-566`). Returned output is `tail(raw, maxLines, maxBytes)` (shell.ts:225-255, 569), prefixed with `"...output truncated...\n\nFull output saved to: {file}"` when cut (`shell.ts:578-580`).

The description is assembled per shell from the `shell.txt` template (`shell/shell.txt:1-21`) plus per-shell command sections (`shell/prompt.ts:273-291`). It instructs the model to prefer dedicated tools over `find`, `grep`, `cat`, `head`, `tail`, `sed`, `awk`, `echo` (`shell/prompt.ts:100-106`), to use `workdir` instead of `cd` (`shell/prompt.ts:112-118`), to issue independent commands as parallel tool calls and chain dependent ones with `&&` (`shell/prompt.ts:107-110`), and carries a Git/GitHub section: commit only when asked, never commit secrets, no force-push or `--no-verify` style escapes, use `gh` for PRs (`shell/shell.txt:13-21`).

### read tool

Parameters `filePath`, optional `offset` (1-indexed), `limit` (`read.ts:28-36`). Constants: `DEFAULT_READ_LIMIT = 2000`, `MAX_LINE_LENGTH = 2000`, `MAX_BYTES = 50 * 1024`, `SAMPLE_BYTES = 4096` (`read.ts:13-18`). Output is wrapped in `<path>`, `<type>`, `<content>` tags with each line numbered `{i}: {line}` (`read.ts:338-351`); lines over 2000 chars are cut with a `... (line truncated to 2000 chars)` suffix (`read.ts:15`, `162`); paging hints are appended (`read.ts:345-349`). Directories list entries with trailing `/` and the same offset/limit paging (`read.ts:264-298`). Binary detection is an extension blocklist plus a heuristic over the 4096-byte sample (any NUL byte or >30% non-printable bytes) (`read.ts:182-227`, `18`). Images (`image/jpeg|png|gif|webp`) and PDFs are returned as base64 data-URL attachments instead of text (`read.ts:19`, `303-325`). On a miss it suggests up to 3 similarly named entries ("Did you mean one of these?") (`read.ts:76-99`). Reads ask permission `read` with the worktree-relative path (`read.ts:255-260`), resolve instruction files (AGENTS.md-style) and append them in a `<system-reminder>` block (`read.ts:300`, `355-357`), and fire a background LSP warm-up (`read.ts:117-120`, `353`).

### edit tool

Parameters `filePath`, `oldString`, `newString`, optional `replaceAll` (`edit.ts:47-56`). `oldString === newString` errors ("No changes to apply..."); empty `oldString` creates a new file and errors if the file already exists ("oldString cannot be empty when editing an existing file... use write for an intentional full-file replacement.") (`edit.ts:75-77`, `90-96`). File mutations are serialized per file through a global semaphore map (`edit.ts:35-45`, `88`). The replacement pipeline tries exact match first, then a cascade of eight fuzzy replacers in order: SimpleReplacer, LineTrimmedReplacer, BlockAnchorReplacer, WhitespaceNormalizedReplacer, IndentationFlexibleReplacer, EscapeNormalizedReplacer, TrimmedBoundaryReplacer, ContextAwareReplacer, MultiOccurrenceReplacer (`edit.ts:694-704`). BlockAnchorReplacer anchors on first/last lines with a size tolerance `maxLineDelta = max(1, floor(blockSize * 0.25))` and Levenshtein-based line similarity at thresholds `SINGLE_CANDIDATE_SIMILARITY_THRESHOLD = 0.65` and `MULTIPLE_CANDIDATES_SIMILARITY_THRESHOLD = 0.65` (`edit.ts:220-221`, `303`). Guards: a fuzzy match whose span is much larger than `oldString` is refused ("Refusing replacement because the matched span is much larger than oldString...") (`edit.ts:709-713`, `731-737`); without `replaceAll` the match must be unique ("Found multiple matches for oldString. Provide more surrounding context to make the match unique.") (`edit.ts:717-718`, `728`); no match yields "Could not find oldString in the file. It must match exactly, including whitespace, indentation, and line endings." (`edit.ts:724-726`). Line endings of the replacement are normalized to the file's detected ending (`edit.ts:22-33`, `129-131`) and a BOM is preserved (`edit.ts:126`, `133-134`). Before writing, `ctx.ask` carries a unified diff (`createTwoFilesPatch` + `trimDiff`) for the permission UI (`edit.ts:137-153`, `646-680`). After writing: an optional formatter pass (`edit.ts:156-158`), `Edited`/`Updated` events, LSP diagnostics appended to output as "LSP errors detected in this file, please fix:" (`edit.ts:196-201`). The approaches are credited to Cline's diff-apply evals and gemini-cli's editCorrector in the file header (`edit.ts:1-4`).

### write tool

Parameters `content`, `filePath` (`write.ts:20-25`). Overwrites the whole file; asks permission `edit` with a unified diff of old vs new (`write.ts:53-62`); preserves BOM (`write.ts:47-49`); formats, publishes events, then reports LSP errors for the written file plus up to `MAX_PROJECT_DIAGNOSTICS_FILES = 5` other files (`write.ts:18`, `79-90`).

### apply_patch tool and the patch machinery

The `apply_patch` tool takes a single `patchText` parameter (`apply_patch.ts:18-20`) and is only offered to GPT-family models (see selection above). It parses the OpenAI-style patch envelope: `*** Begin Patch` / `*** End Patch`, headers `*** Add File: <path>`, `*** Delete File: <path>`, `*** Update File: <path>` with optional `*** Move to: <path>`, context markers `@@ <context>`, lines prefixed ` ` / `-` / `+`, and `*** End of File` (`packages/opencode/src/patch/index.ts:70-101`, `103-155`, `185-241`; the model-facing format is documented in `apply_patch.txt:1-33`). A leading heredoc (`cat <<'EOF' ... EOF`) is stripped first (`patch/index.ts:176-183`). An empty patch (`*** Begin Patch\n*** End Patch`) is rejected (`apply_patch.ts:47-53`). Update hunks are applied by `deriveNewContentsFromChunks`, which locates each chunk's old lines with `seekSequence`: a four-pass match (exact, rstrip, both-end trim, Unicode punctuation normalization) with optional EOF anchoring, and retries after dropping a trailing empty line (`patch/index.ts:342-396`, `429-484`); `@@ <context>` lines reposition the search cursor (`patch/index.ts:350-358`). The file header comment says the types mirror "the Rust implementation" (`patch/index.ts:12`), and the module reuses Codex-style enum names `MaybeApplyPatch` / `MaybeApplyPatchVerified` (`patch/index.ts:55-67`). The tool validates every file path against external-directory rules (`apply_patch.ts:73-74`, `142-143`), then issues one `edit` permission ask covering all relative paths with per-file diffs (`apply_patch.ts:204-215`), applies add/update/move/delete (`apply_patch.ts:220-250`), formats touched files, touches LSP, and summarizes with `A`/`D`/`M` lines (`apply_patch.ts:260-293`).

Shell-interception helpers also exist: `maybeParseApplyPatch` recognizes `apply_patch <patch>` and `bash -lc 'apply_patch <<"EOF"...'` argv forms, and `maybeParseApplyPatchVerified` computes verified file changes (`patch/index.ts:244-298`, `575-684`). In the pinned tree these are only referenced by the module itself and tests (`packages/opencode/test/patch/patch.test.ts:104-138`); the `bash` tool does not import the patch module (`shell.ts:1-25`).

### Truncation service

`MAX_LINES = 2000`, `MAX_BYTES = 50 * 1024` (`truncate.ts:14-15`), overridable per config `tool_output.max_lines` / `tool_output.max_bytes` (`truncate.ts:75-83`). Overflow writes the full text to `Global.Path.data/tool-output` (directory constant, `truncation-dir.ts:4`) with an ascending `tool_` filename (`truncate.ts:68-73`, `schema.ts:6-13`), returns a head (default) or tail preview plus `...{n} {unit} truncated...` and a hint (`truncate.ts:97-141`). When the calling agent has the `task` tool, the hint instead says to delegate the saved file to an explore subagent rather than read it directly (`truncate.ts:27-30`, `129-131`). Cleanup removes `tool_*` files older than `RETENTION = Duration.days(7)` on an hourly schedule (`truncate.ts:12`, `53-66`, `143-148`).

## Key facts with anchors

- Tool contract is Effect Schema in, `ExecuteResult` out; decode failures become a typed, model-facing rewrite prompt (`tool.ts:48-65`, `24-34`).
- Output truncation is centralized: every wrapped tool's output passes through `truncate.output` unless it opts out via `metadata.truncated` (`tool.ts:131-144`; `truncate.ts:85-141`); truncation defaults are 2000 lines / 51200 bytes (`truncate.ts:14-15`; `packages/core/src/v1/config/config.ts:139`, `142`).
- Tool surface is model-conditional: `apply_patch` is exclusive to `gpt-*` model IDs (minus `oss`, `gpt-4`) and replaces `edit`+`write` for those models (`registry.ts:297-300`).
- The shell tool is named `bash` for compatibility while actually supporting bash/pwsh/powershell/cmd (`shell/id.ts:14-17`); every command is tree-sitter parsed before execution to derive permission asks and external-directory checks (`shell.ts:257-261`, `378-414`).
- Bash permission asks record the exact command as `patterns` and an arity-wildcarded form (e.g. `git status *`) as `always`, using an LLM-generated arity table (`shell.ts:407-410`; `permission/arity.ts:11-24`, `83`).
- Edit matching cascades through nine replacers with similarity thresholds 0.65/0.65 credited to Cline and gemini-cli (`edit.ts:220-221`, `694-704`, `1-4`).
- The patch format is a port of the OpenAI Codex envelope (`*** Begin Patch`, `*** Add File:`, `*** Move to:`, `@@ context`), with comment "Core types matching the Rust implementation" (`patch/index.ts:12`, `185-241`; `apply_patch.txt:3-28`).
- Patch line matching is fuzzy by design: four passes from exact to Unicode-normalized, with EOF anchoring and trailing-empty-line retry (`patch/index.ts:460-484`, `376-382`).
- File mutations ask permission with a computed unified diff attached (`edit.ts:137-153`; `write.ts:53-62`; `apply_patch.ts:204-215`) and then run LSP diagnostics into the tool output ("LSP errors detected in this file, please fix:") (`edit.ts:196-201`; `write.ts:84-89`; `apply_patch.ts:286-293`).
- Read returns line-numbered `<line>: <content>` output, 2000-line default cap, 2000-char line cap, 50 KiB byte cap, 4096-byte sniff sample, image/PDF attachments, and `<system-reminder>` instruction injection (`read.ts:13-18`, `338-351`, `303-325`, `355-357`).
- Read/edit/write descriptions instruct "read before you write" behavior that is not enforced in this component's code (see Limitations) (`edit.txt:4`; `write.txt:5`; grep found no enforcement in `packages/opencode/src`).
- The shell-interception APIs `maybeParseApplyPatch`/`maybeParseApplyPatchVerified` exist but have no runtime callers at this commit outside tests (`patch/index.ts:244-298`, `575-684`; only test usage at `packages/opencode/test/patch/patch.test.ts:104-138`).
- A near-duplicate tool implementation exists in `packages/core/src/tool/` (e.g. `apply-patch.ts:17` `name = "apply_patch"`, `builtins.ts:6`), but nothing in `packages/opencode/src` imports `@opencode-ai/core`'s tool modules (grep), so the `packages/opencode/src/tool` tree is the active one here.

## Configuration and defaults

- `OPENCODE_CLIENT`: client identity, default `"cli"` (`runtime-flags.ts:56`).
- `OPENCODE_ENABLE_EXA` / `OPENCODE_ENABLE_PARALLEL` (with legacy `OPENCODE_EXPERIMENTAL_EXA` / `OPENCODE_EXPERIMENTAL_PARALLEL`) gate `websearch` and its provider (`runtime-flags.ts:31-39`; `registry.ts:58-65`).

## Limitations and unknowns

- **Tooling for reading this source was itself OpenCode.** Not a code fact: the descriptions in `read.txt`, `edit.txt`, `write.txt` match the tool descriptions of the harness running this study, which cross-checks that the pinned tree is representative of shipped behavior. No benchmark or evaluation data exists in the component for edit-matcher success rates; the 0.65 thresholds are imported from Cline/gemini-cli evals (`edit.ts:1-4`, `220-221`) without evaluation artifacts in this tree.
- **Description claims not enforced in code.** `edit.txt:4` ("This tool will error if you attempt an edit without reading the file") and `write.txt:5` ("This tool will fail if you did not read the file first") have no corresponding check anywhere I searched in `packages/opencode/src` (grep over the package). The read tracking that exists (`metadata.loaded`, `read.ts:355-366`) feeds instruction injection, not enforcement. Enforcement may live in a non-default plugin or be unimplemented; I mark this `[EVIDENCE NEEDED]` for the report.
- **Dead or vestigial patch surface.** `maybeParseApplyPatch`/`maybeParseApplyPatchVerified` (the Codex-style `apply_patch <<EOF` shell interception) have no production callers at this commit, and the `bash` tool does not hook them (`patch/index.ts:244-298`, `575-684`; `shell.ts` has no patch import). Whether this is migration debris from the Codex port or a pending feature is not determinable from the tree. Similarly `plan-enter.txt` is unused.
- **Naive diff generator.** `generateUnifiedDiff` is line-by-line, with the comment "in a real implementation you'd use a proper diff algorithm" (`patch/index.ts:490`); it feeds only the unused verified-parse path, since the live `apply_patch` tool builds diffs with the npm `diff` package `createTwoFilesPatch` (`apply_patch.ts:8`, `82`, `133`, `172`).
- **Duplicate tool stack in packages/core.** `packages/core/src/tool/apply-patch.ts` and `builtins.ts` implement a parallel registry that this component does not import; which surface future builds use is not verifiable from the pinned tree (grep only, no wiring trace).
- **Runtime-dependent behavior.** Shell choice depends on `$SHELL` and platform (`core/src/shell.ts:205-221`); LSP feedback depends on which language servers are installed; websearch availability depends on provider and hosted endpoints. None of these states are observable statically.
- **Fuzzy matching risk.** The edit cascade (BlockAnchor with 0.65 similarity, ContextAware with 50% middle-line match, `edit.ts:220-221`, `635`) and the patch matcher's Unicode normalization (`patch/index.ts:418-425`, `476-483`) can substitute at unintended spans; only gross-oversize matches are refused (`edit.ts:709-713`, `731-737`). Whether permission diffs shown to the user catch this reliably is a UI question outside this component.
- **Registry component list drift.** The registry entry omits `todo.ts`, `invalid.ts`, `external-directory.ts`, `json-schema.ts`, `code-mode.ts`, `mcp-websearch.ts`, and the `*.txt` description files that exist in the tree; I covered them anyway, but the orchestrator may want to refresh the component string.

## Relevance to the brief

My inference, separate from the code facts above.

- **RQ1 (where the harnesses genuinely differ):** OpenCode's tool layer is an open implementation of a Claude-Code-shaped toolset (line-numbered Read with 2000/2000/50KiB caps, oldString/newString Edit, "read before write" prose, dedicated glob/grep, one bash tool), while simultaneously shipping the Codex apply_patch format as a model-specific tool (`registry.ts:297-300`). That makes OpenCode the natural hinge system for the report: it demonstrates both apply-patch strategies (Codex-style `*** Begin Patch` for GPT models, search/replace edit for everyone else) in one harness.
- **RQ2 (what makes a harness):** the tool registry plus wrapper isolates cross-cutting concerns (schema decode, permission ask, output truncation with spill-to-file, LSP feedback, formatter pass) in roughly 250 lines (`tool.ts:99-149`), which is a clean reference design for the components list. Truncation-as-context-management (2000/51200 defaults, task-agent delegation hint) is a distinctive OpenCode move compared to a harness that just clips output.
- **RQ3 (capability vs safety):** the trade is permission-ask plus static command scanning rather than OS sandboxing: tree-sitter parse of every bash command, argument-level external-directory detection, exact-command-plus-wildcard approval memory (`shell.ts:257-261`, `378-414`; `shell.ts:263-291`). There is no exec policy or syscall filter in this component, consistent with the opencodePermissions coverage note in the registry.
- **Open for synthesis:** the `apply_patch` gating heuristic is a string check on the model ID (`registry.ts:297-298`), which is brittle for renamed models; the companion Codex note should confirm whether Codex applies the same format to all models, and the Claude Code note (docs only) should state whether Edit remains its sole apply path.
