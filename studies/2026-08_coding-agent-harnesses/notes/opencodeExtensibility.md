## Purpose and role in the harness

This component is OpenCode's extension machinery: everything that lets a user or third party add behavior without forking the core. It has five surfaces:

1. Server plugins: JavaScript/TypeScript modules that run in the server process and return a `Hooks` object (`packages/plugin/src/index.ts:74-80`). The host loads them at instance startup, then calls named hooks at fixed points in the session loop (`packages/opencode/src/plugin/index.ts:282-295`).
2. MCP integration: a client-only MCP subsystem that connects configured stdio/HTTP/SSE servers, caches their tool/prompt/resource catalogs, converts them into AI SDK tools, and completes remote OAuth (`packages/opencode/src/mcp/index.ts`).
3. Skills: `SKILL.md` documents discovered from OpenCode, Anthropic (`.claude`), and `.agents` directory layouts, or pulled from remote URLs, exposed to the model through a `skill` tool and the system prompt (`packages/opencode/src/skill/index.ts`).
4. Custom commands: `/`-commands assembled from two built-ins, config entries, markdown files, MCP prompts, and skills (`packages/opencode/src/command/index.ts`).
5. Agents and subagents: a fixed set of built-in agents plus config- and markdown-defined agents that the `task` tool can dispatch (`packages/opencode/src/agent/agent.ts:140-294`).

All five surfaces are config- and permission-gated, and all five have environment-variable kill switches (`packages/opencode/src/effect/runtime-flags.ts:18-30`).

## Mechanism

### Server plugin loading

Plugin loading is staged per instance. The `Plugin` service builds `PluginInput` (`client`, `project`, `worktree`, `directory`, `experimental_workspace`, `serverUrl`, `$`) and first instantiates built-in "internal plugins" as plain function calls: CodexAuthPlugin, CopilotAuthPlugin, ModalPlugin, GitlabAuthPlugin, PoeAuthPlugin, CloudflareWorkersAuthPlugin, CloudflareAIGatewayAuthPlugin, AzureAuthPlugin, DigitalOceanAuthPlugin, SnowflakeCortexAuthPlugin, XaiAuthPlugin (`packages/opencode/src/plugin/index.ts:66-84`). Internal plugin init failures are logged and skipped, not fatal (`index.ts:169-177`). The internal set is disabled wholesale by `OPENCODE_DISABLE_DEFAULT_PLUGINS` (`index.ts:168`, `effect/runtime-flags.ts:19`).

External plugins come from `cfg.plugin_origins` unless `OPENCODE_PURE` is set (`index.ts:179`, `effect/runtime-flags.ts:18`). `plugin_origins` is derived state: every config source contributes a `plugin` array of specs, and the merge keeps the winning origin per plugin identity while deduplicating on package name or exact file URL (`packages/opencode/src/config/config.ts:330-354`, `config/plugin.ts:64-77`). Auto-discovery adds local plugins: every config directory is scanned for `{plugin,plugins}/*.{ts,js}` (`config/plugin.ts:21-28`), and config directories are the global config dir plus any `.opencode` directory walking up from the working directory to the worktree root, plus `$HOME/.opencode` and `OPENCODE_CONFIG_DIR` (`config/paths.ts:23-41`). The config loader also background-installs `@opencode-ai/plugin` pinned to `InstallationVersion` into each `.opencode` directory (`config/config.ts:438-457`).

The loader normalizes each entry into a `Plan`, resolves it to a filesystem target and entrypoint, imports it, and reports failures by stage, `install` | `entry` | `compatibility` | `load` (`plugin/loader.ts:17-58`, `86-145`). Specs are either npm package specifiers or path specs (`file://`, `./`, absolute) (`plugin/shared.ts:171-173`). npm specs are installed on demand via `Npm.add` into `<XDG cache>/packages/<sanitized name>` using `@npmcli/arborist` with `ignoreScripts: true` (`plugin/shared.ts:207-213`, `packages/core/src/npm.ts:79-137`). Entrypoint resolution prefers `package.json` `exports["./server"]` (or `"./tui"`), falls back to `main` for the server kind (`plugin/shared.ts:103-114`), and uses index files `index.ts`, `index.tsx`, `index.js`, `index.mjs`, `index.cjs` for directories (`plugin/shared.ts:54`). npm plugins pass a compatibility gate matching `package.json` `engines.opencode` against the running version, skipped when the version is invalid or major 0, and skipped entirely for file plugins, which are treated as local development code (`plugin/shared.ts:194-205`, `plugin/loader.ts:123-131`).

Module shape: a v1 plugin default-exports an object with `id?` and exactly one of `server()` or `tui()` (`plugin/shared.ts:272-304`). Legacy modules whose exports are bare functions are also accepted (`plugin/index.ts:86-110`). Path plugins must export `id`; npm plugins fall back to the package name (`plugin/shared.ts:306-323`). Deprecated npm packages `opencode-openai-codex-auth` and `opencode-copilot-auth` are silently ignored because they are now built in (`plugin/shared.ts:10-14`, `plugin/loader.ts:160-161`).

Plugins are applied sequentially "so hook registration and execution order remains deterministic across plugin runs" (`plugin/index.ts:220-223`). After loading, the host calls each hook's `config` hook with the current config (`index.ts:243-251`), subscribes all hooks' `event` handlers to instance events filtered by directory (`index.ts:253-261`), and registers a finalizer that calls `dispose` (`index.ts:263-276`).

### Hook dispatch

`Plugin.trigger` iterates `s.hooks` in registration order, awaits each implementation of the named hook, and returns the mutated output object (`plugin/index.ts:282-295`). Only hooks typed as `(input, output) => Promise<void>` are triggerable (the `TriggerName` mapped type, `index.ts:40-43`). The SDK `Hooks` interface declares these triggerable hooks: `chat.message`, `chat.params`, `chat.headers`, `permission.ask`, `command.execute.before`, `tool.execute.before`, `tool.execute.after`, `shell.env`, `experimental.chat.messages.transform`, `experimental.chat.system.transform`, `experimental.provider.small_model`, `experimental.session.compacting`, `experimental.compaction.autocontinue`, `experimental.text.complete`, `tool.definition`, plus the non-trigger surfaces `dispose`, `event`, `config`, `tool` (a map of custom tools), `auth` (provider auth flows), and `provider` (model listing) (`packages/plugin/src/index.ts:222-335`).

Call sites found in the pinned tree (all via `plugin.trigger`): `tool.execute.before`/`tool.execute.after` around every tool execution (`session/tools.ts:106-125`) and around MCP tool calls (`session/tools.ts:402-424`) and task invocations (`session/prompt.ts:307-311`, `389-393`); `tool.definition` when building the tool list for the LLM (`tool/registry.ts:318-322`); `chat.message` on user message intake (`session/prompt.ts:999-1009`); `command.execute.before` before a command runs (`session/prompt.ts:1460-1464`); `shell.env` for shell and PTY environment merging (`session/prompt.ts:554-562`, `plugin/pty-environment.ts:18`, `server/routes/instance/httpapi/handlers/pty.ts:71`); `chat.params` and `chat.headers` in request construction (`session/llm/request.ts:114`, `134-135`); `experimental.chat.system.transform` in agent generation (`agent/agent.ts:381`) and in request construction (`session/llm/request.ts:69`); `experimental.session.compacting` and `experimental.chat.messages.transform` during compaction (`session/compaction.ts:373-379`); `experimental.compaction.autocontinue` (`session/compaction.ts:500`); `experimental.text.complete` at text-part end (`session/processor.ts:516-524`); `experimental.provider.small_model` in provider selection (`provider/provider.ts:1923-1924`). `permission.ask` is declared in the SDK type (`packages/plugin/src/index.ts:261`) but no trigger call site was found anywhere in `packages/opencode/src` (see Limitations).

### Custom tools

Tools enter the registry from two sources beyond built-ins. First, files matching `{tool,tools}/*.{js,ts}` in every config directory are dynamically imported, and each export shaped like a plugin tool becomes a tool named after the export: a `default` export takes the file's basename, other exports get `${basename}_${exportName}` (`tool/registry.ts:183-197`). Second, each loaded plugin's `tool` map is added under its hook keys (`tool/registry.ts:199-204`). The adapter `fromPlugin` converts Zod `args` into JSON Schema for the LLM while keeping Zod validation, bridges the Effect-based permission `ask` into a Promise function for the plugin, injects `directory` and `worktree`, and truncates output through the shared truncation service (`tool/registry.ts:125-181`). The SDK helper is minimal: `tool({description, args, execute})` returns its input, and `tool.schema` is `zod` (`packages/plugin/src/tool.ts:45-52`). `ToolContext` gives the plugin `sessionID`, `messageID`, `agent`, `directory`, `worktree`, `abort`, `metadata()`, and `ask()` (`packages/plugin/src/tool.ts:3-27`).

### MCP client

The MCP service builds one client per configured server at instance start with unbounded concurrency (`mcp/index.ts:492-529`). The client identifies itself as `{ name: "opencode", version: InstallationVersion }` and advertises only the `roots` capability; `sampling`, `elicitation`, and `tasks` are commented out with issue links (`mcp/index.ts:39-50`). It answers `ListRoots` with the project directory as a `file://` root (`mcp/index.ts:75-81`).

Local servers spawn via `StdioClientTransport` with `stderr: "pipe"`, environment merged as `process.env` plus `BUN_BE_BUN: "1"` when the command is literally `opencode`, plus the configured `environment` last (`mcp/index.ts:340-357`). Remote servers try `StreamableHTTPClientTransport` first, then `SSEClientTransport`, both with optional headers and OAuth provider (`mcp/index.ts:269-284`). Connect uses `DEFAULT_TIMEOUT = 30_000` unless the entry sets `timeout` (`mcp/index.ts:38`, `286`, `359`). Per-server status is one of `connected`, `disabled`, `failed`, `needs_auth`, `needs_client_registration` (`mcp/index.ts:83-106`). `enabled: false` yields `disabled` without connecting (`mcp/index.ts:514-516`); `connect`/`disconnect`/`add` mutate state at runtime (`mcp/index.ts:641-659`).

Tool discovery happens only when the server advertises a tools capability (`mcp/index.ts:391`). Listing paginates with `MAX_LIST_PAGES = 1_000` and rejects duplicate cursors (`mcp/catalog.ts:12-36`), and falls back to a tolerant schema that drops `outputSchema` validation when the strict schema fails with reference-related errors (`mcp/catalog.ts:14-16`, `145-168`). Each server's tool list is cached; `notifications/tools/list_changed` re-lists and publishes `ToolsChanged` (`mcp/index.ts:461-472`); `onclose` marks the server failed with "Connection closed" (`mcp/index.ts:443-455`). Logging notifications map MCP levels to host log levels (`mcp/index.ts:457-459`, `474-490`).

Tool identity: `toolName(clientName, name)` is `sanitize(clientName) + "_" + sanitize(name)` where `sanitize` replaces `/[^a-zA-Z0-9_-]/g` with `_` (`mcp/catalog.ts:117-119`). `McpCatalog.convertTool` wraps `client.callTool` as a Vercel AI SDK `dynamicTool`, forces `additionalProperties: false` on the input schema, sets `resetTimeoutOnProgress: true` with a no-op `onprogress` so the SDK sends a progress token, throws on `isError` with the concatenated text content, and synthesizes a text content item from `structuredContent` when content is empty (`mcp/catalog.ts:42-83`). At session-tool resolution, MCP tools are merged in after a permission ask whose key is the sanitized tool key and whose patterns are `["*"]` (`session/tools.ts:390-409`), unless experimental code mode is on, in which case MCP tools are instead exposed through the confined interpreter (`session/tools.ts:388`, `tool/registry.ts:280-289`). If any server advertises resources, three extra tools appear: `list_mcp_resources`, `list_mcp_resource_templates`, `read_mcp_resource` (`session/tools.ts:27-31`, `136-386`). Resource blobs attach only for `application/pdf`, `image/gif`, `image/jpeg`, `image/png`, `image/webp`, capped at `MAX_MCP_RESOURCE_BLOB_BYTES = 10 * 1024 * 1024` (`session/tools.ts:32-39`).

Connected servers' `instructions` strings are injected into the system prompt in an `<mcp_instructions>` XML block, filtered by whether the agent's permission ruleset still allows at least one of the server's tools (`session/system.ts:119-135`, `mcp/index.ts:615-625`). MCP prompts also become slash commands (below). On shutdown, the finalizer collects descendant PIDs of stdio servers via `pgrep -P` (non-Windows only) and SIGTERMs them before closing clients (`mcp/index.ts:418-440`, `531-556`).

OAuth for remote servers implements `OAuthClientProvider` (`mcp/oauth-provider.ts:26-181`). Defaults: callback `http://127.0.0.1:19876/mcp/oauth/callback` (`OAUTH_CALLBACK_PORT = 19876`, `OAUTH_CALLBACK_PATH = "/mcp/oauth/callback"`, `mcp/oauth-provider.ts:11-12`, `35-41`); client metadata names the client "OpenCode" and requests `authorization_code` and `refresh_token` grants; `token_endpoint_auth_method` is `client_secret_post` when a secret is configured, else `none` (`oauth-provider.ts:43-53`). Without a configured `clientId`, stored client info is reused if its `serverUrl` matches, otherwise dynamic client registration is attempted (`oauth-provider.ts:55-79`). The callback listener binds `127.0.0.1` only, enforces a `state` parameter against stored pending state (400 "potential CSRF attack" on mismatch/absence), and times out after `CALLBACK_TIMEOUT_MS = 5 * 60 * 1000` (`mcp/oauth-callback.ts:6`, `24`, `57-62`, `86-91`, `126`). Tokens and client info persist to `<data dir>/mcp-auth.json` written with mode `0o600` under a flock (`mcp/auth.ts:37-38`, `76-82`). The browser is opened via the `open` package with failure surfaced as a `BrowserOpenFailed` event and a TUI toast (`mcp/index.ts:901-905`, `mcp/browser.ts:14-31`). A pending-flow map keyed by server name carries the transport across the browser round trip (`mcp/index.ts:111`, `312`, `864`, `918-942`).

Negative finding on "built-in server": there is no MCP-server-side code in the pinned tree. Grepping all of `packages/opencode/src` for `@modelcontextprotocol/sdk/server` or any `@modelcontextprotocol` import returns only client imports and shared types (`mcp/index.ts:6-17`, `mcp/catalog.ts:1-7`, `mcp/oauth-provider.ts:1-9`, `cli/cmd/mcp.ts:5-8`, `tool/code-mode.ts:2`); server transports appear only under `packages/opencode/test/`. The only server OpenCode exposes to plugins is its own HTTP/SDK server, handed to plugins as `PluginInput.client`/`serverUrl` with a default base URL of `http://localhost:4096` (`plugin/index.ts:141-163`).

CLI surface: `opencode mcp` has subcommands `add`, `list` (alias `ls`), `auth`, `logout`, `debug` (`cli/cmd/mcp.ts:95-107`).

### Skill loading

Skill discovery scans four sources, deduplicated into a match set (`skill/index.ts:173-233`):

1. External layouts, unless `OPENCODE_DISABLE_EXTERNAL_SKILLS`: `~/.claude` and `~/.agents` (and the same directories walking up from the working directory to the worktree root) with pattern `skills/**/SKILL.md`; `~/.claude` is additionally gated by the Claude Code flags (`skill/index.ts:21-23`, `186-203`, `effect/runtime-flags.ts:21-30`).
2. OpenCode config directories with pattern `{skill,skills}/**/SKILL.md` (`skill/index.ts:24`, `205-208`).
3. Extra local paths from config `skills.paths`, `~/` expanded, relative paths resolved from the working directory (`skill/index.ts:210-220`).
4. Remote skill indexes from config `skills.urls`, each fetched as `<url>/index.json` (`skill/index.ts:222-227`, `skill/discovery.ts:49-66`).

Each match is parsed for frontmatter requiring `name: string` and optional `description: string`; files without valid frontmatter are skipped (`skill/index.ts:53-59`, `105-140`). Parse errors are surfaced as `Session.Event.Error` events (`skill/index.ts:110-118`). Duplicate names log a warning and the later match overwrites (`skill/index.ts:125-131`). One built-in skill, `customize-opencode`, is registered before disk discovery so a same-named disk skill overrides it; its body is embedded at build time from `packages/core/src/plugin/skill/customize-opencode.md` (`skill/index.ts:27-35`, `276-283`, `packages/core/src/plugin/skill.ts:9-11`).

Remote discovery caches under `<cache>/skills/<name>` with a `.opencode-version` stamp; when the index declares a new `version`, files download to a staging dir and are swapped atomically with a backup/rollback (`skill/discovery.ts:35`, `75-129`). Skills whose index entry lacks `SKILL.md` are skipped with a warning (`skill/discovery.ts:67-73`). Concurrency: 4 skills, 8 files (`skill/discovery.ts:10-11`).

Model exposure is threefold. (a) The system prompt includes the verbose `<available_skills>` listing of every skill whose `skill` permission is not denied for the agent (`session/system.ts:105-117`, `skill/index.ts:310-315`, `321-346`). (b) The `skill` tool loads one skill on demand: it asks the `skill` permission for the skill name, then returns the skill body in a `<skill_content name=...>` block plus a ripgrep-sampled list of up to 10 sibling files (`tool/skill.ts:12-70`). (c) Every skill also becomes a slash command (below), with the skill body plus a "Base directory for this skill" footer (`command/index.ts:134-152`).

### Commands

The command registry merges, in order: two built-ins, config `command` entries, MCP prompts, then skills (skills never shadow an existing name) (`command/index.ts:65-152`). Built-ins are `init` ("guided AGENTS.md setup") and `review` ("review changes [commit|branch|pr], defaults to uncommitted", `subtask: true`), rendered from `template/initialize.txt` and `template/review.txt` with `${path}` replaced by the worktree (`command/index.ts:46-88`, `10-11`). Config-defined commands carry `agent`, `model`, `description`, `template`, `subtask` fields; the `command` config key and markdown files under `{command,commands}/**/*.md` in every config directory both feed it (`command/index.ts:90-103`, `config/command.ts:13-39`). MCP prompts appear with `source: "mcp"` and a lazy template that resolves `getPrompt` at use time, mapping prompt arguments to `$1..$n` hints (`command/index.ts:105-132`). Command `Info` records `source: "command" | "mcp" | "skill"` and `hints` derived from `$N`/`$ARGUMENTS` placeholders (`command/index.ts:22-44`).

Execution (`session/prompt.ts:1370-1481`): quoted arguments are parsed; `$1..$n` placeholders are replaced positionally with the last placeholder absorbing all remaining arguments; `$ARGUMENTS` is replaced with the raw argument string; if the template uses neither and arguments were given, they are appended at the end (`prompt.ts:1372-1395`). Inline `` !`cmd` `` shell blocks in the template are executed via the configured shell before sending (`prompt.ts:1397-1408`, through `ConfigMarkdown.shell`). A command runs as a subtask when `(agent.mode === "subagent" && cmd.subtask !== false) || cmd.subtask === true` (`prompt.ts:1439`), in which case the rendered template becomes the prompt of a `task` tool invocation (`prompt.ts:1440-1451`). The `command.execute.before` hook fires before dispatch and `Command.Event.Executed` publishes after (`prompt.ts:1460-1479`).

### Agents and subagents

Built-in agents are defined in code: `build` (primary default), `plan` (primary, edit tools denied except plan files), `general` (subagent), `explore` (subagent with a read-only permission allowlist of `grep`, `glob`, `list`, `bash`, `webfetch`, `websearch`, `read`), and hidden utility agents `compaction`, `title`, `summary` (`agent/agent.ts:140-265`). The default permission ruleset allows `"*"`, asks on `doom_loop`, asks on `external_directory` except whitelisted dirs (truncation glob, global tmp, skill dirs, reference dirs), denies `question`, `plan_enter`, `plan_exit`, and asks on reads matching `*.env` and `*.env.*` while allowing `*.env.example` (`agent/agent.ts:119-136`). Config `agent` entries can disable an agent (deleting it), override fields (`model`, `variant`, `prompt`, `description`, `temperature`, `top_p`, `mode`, `color`, `hidden`, `name`, `steps`, `options` deep-merged), or define new agents defaulting to `mode: "all"`, `native: false`; permissions merge onto the agent's ruleset (`agent/agent.ts:267-294`). Agent `mode` is `"subagent" | "primary" | "all"` (`agent/agent.ts:38`). Markdown agents load from `{agent,agents}/**/*.md` in config directories (frontmatter plus body as `prompt`), and `{mode,modes}/*.md` load as agents forced to `mode: "primary"` (`config/agent.ts:11-59`, merged at `config/config.ts:459-461`). The default agent is `cfg.default_agent` if valid, else the first non-subagent non-hidden agent, with `build` as the fallback name in sorting (`agent/agent.ts:316-344`). There is also an LLM-driven `generate` path that produces a `{identifier, whenToUse, systemPrompt}` object from `PROMPT_GENERATE` at `temperature: 0.3` (`agent/agent.ts:58-62`, `368-435`). Subagents are dispatched through the `task` tool, whose description is dynamically built from non-primary agents filtered by the caller's `task` permission (`tool/registry.ts:265-278`).

### TUI plugins (secondary surface)

The SDK has a separate `TuiPlugin` shape, `(api, options, meta) => Promise<void>`, with an API covering routes, dialogs, slots, theming, keymaps, attention notifications, KV storage, and plugin management (`packages/plugin/src/tui.ts:581-634`). TUI plugins load through the same `PluginLoader` with `kind: "tui"`, share `readV1Plugin` shape validation (`tui()` XOR `server()`), and are tracked in a `plugin-meta.json` store recording `first_time`, `last_time`, `load_count`, and a fingerprint for `first`/`updated`/`same` state transitions (`plugin/tui/runtime.ts:21-78`, `plugin/meta.ts:20-140`). Package-level theme files can ship under `package.json` `oc-themes` without any code entrypoint (`plugin/shared.ts:238-262`, `plugin/install.ts:161-163`). The TUI runtime is large (1131 lines) and is summarized here at entrypoint level only.

### Install flow

`opencode`-side plugin installation resolves the target, reads the package manifest for `server`/`tui` entrypoints, then patches config JSONC via `jsonc-parser`, adding the spec to the `plugin` array of the global config dir or of `./.opencode` (worktree-based when VCS is git, else the working directory), deduplicating by package name unless forced, under a `plug-config:` flock (`plugin/install.ts:333-344`, `181-257`, `345-419`). Plugin packages can ship options under `exports["./server"].config`, which are written as `[spec, options]` array items (`plugin/install.ts:121-137`, `388`).

## Key facts with anchors

- A plugin is `(input: PluginInput, options?: PluginOptions) => Promise<Hooks>` and a module default-exports `{ id?, server }` or `{ id?, tui }`, never both (`packages/plugin/src/index.ts:74-80`, `packages/opencode/src/plugin/shared.ts:293-295`).
- Ten of eleven internal plugins are provider auth bundles; GitLab and Poe auth come from external npm packages `opencode-gitlab-auth` and `opencode-poe-auth` imported directly into the core (`packages/opencode/src/plugin/index.ts:17-18`, `66-84`). (Interpretation: OpenCode dogfoods its own plugin API for provider auth.)
- Hook dispatch is sequential and deterministic by registration order; the code comment states this is intentional (`packages/opencode/src/plugin/index.ts:220-223`, `282-295`).
- `TriggerName` restricts `trigger` to hooks with the `(input, output) => Promise<void>` signature (`packages/opencode/src/plugin/index.ts:40-43`).
- npm plugins are version-gated via `engines.opencode`; file plugins skip the gate as "local development code" (`packages/opencode/src/plugin/shared.ts:194-205`, `plugin/loader.ts:123-131`).
- Plugin entry resolution: `exports["./server"]`/`exports["./tui"]`, then `main` (server only); index files `index.ts`, `index.tsx`, `index.js`, `index.mjs`, `index.cjs` (`packages/opencode/src/plugin/shared.ts:54`, `103-114`).
- Only `roots` is advertised as an MCP client capability; `sampling`, `elicitation`, and `tasks` are disabled with links to issues 11948, 23066, 28567 (`packages/opencode/src/mcp/index.ts:39-50`).
- MCP tool naming is `sanitize(client) + "_" + sanitize(tool)` with `sanitize = value.replace(/[^a-zA-Z0-9_-]/g, "_")` (`packages/opencode/src/mcp/catalog.ts:117-119`).
- MCP resources expose three injected tools (`list_mcp_resources`, `list_mcp_resource_templates`, `read_mcp_resource`) only when some connected server advertises resources (`packages/opencode/src/session/tools.ts:27-31`, `136-139`).
- OAuth callback server binds `127.0.0.1:19876` at path `/mcp/oauth/callback`, validates `state` (CSRF checks at `oauth-callback.ts:57-62`, `86-91`), 5-minute timeout (`mcp/oauth-provider.ts:11-12`, `mcp/oauth-callback.ts:24`, `126`).
- MCP credentials persist to `mcp-auth.json` in the data dir with file mode `0o600` (`packages/opencode/src/mcp/auth.ts:37-38`, `80`).
- Skills are discovered from `.claude`/`.agents` external layouts, `.opencode`-style `{skill,skills}` dirs, config `skills.paths`, and remote `skills.urls` index.json feeds (`packages/opencode/src/skill/index.ts:21-25`, `186-227`).

## Relevance to the brief

Inferences, separated from the code facts above:

- RQ2 (harness components: extensibility): OpenCode's extensibility is unusually broad and unusually in-process. Where the brief's other systems expose declarative surfaces (Claude Code hooks as external scripts per its docs; Codex MCP config), OpenCode lets arbitrary TypeScript run inside the server with a richly typed hook set covering message intake, LLM request params/headers, tool definitions, tool execution, compaction, and even text completion. For a harness taxonomy, OpenCode is the case where "plugins" are a first-class runtime layer, not a peripheral integration point.
- RQ2 (skills): OpenCode deliberately interoperates with Claude Code's skill layout by scanning `.claude/skills` unless disabled (`skill/index.ts:186-203`), plus the vendor-neutral `.agents` layout. This is direct evidence of cross-harness ecosystem borrowing and belongs in the comparison matrix's extensibility row.
- RQ1 (genuine differences): three concrete contrasts to test against the Codex and Claude Code notes: (1) hooks mutate a shared output object sequentially (`plugin/index.ts:282-295`), an interceptor-chain model; (2) MCP prompts, skills, config markdown, and built-ins all unify into one slash-command namespace with explicit `source` tracking (`command/index.ts:22-32`); (3) agents are data (permissions rulesets plus prompts), definable at runtime and even LLM-generated (`agent.ts:267-294`, `368-435`), rather than fixed binaries.
- RQ3 (capability vs safety): extensibility widens the trust surface. Plugins get the SDK client and can register workspace adapters (`plugin/index.ts:151-166`); MCP tools are permission-asked with wildcard patterns `["*"]` by default (`session/tools.ts:408`); remote skills enter prompts unsigned (`skill/discovery.ts`). The counters are env kill switches, the permission ruleset applied to skills and subagents, `enabled: false` MCP entries, and `OPENCODE_PURE`. The permission/OS-sandbox note (opencodePermissions) should own the enforcement side; this note establishes what is being gated.
- Open questions for synthesis: whether the unused `permission.ask` hook signals a regression or migration toward the v2 plugin system (`packages/plugin/src/v2/`); whether the missing MCP server is temporary in the TypeScript rewrite (the Go-era opencode reportedly exposed one, but that is out of scope per coverage limits); and how Codex's hooks/skills compare in granularity once codexExtensibility is noted.
