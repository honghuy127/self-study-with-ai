## Purpose and role in the harness

This repository is the public distribution and extension surface of Claude Code, "an agentic coding tool that lives in your terminal" (`README.md:7`). It does not contain the harness; it contains the officially sanctioned extension material through which the closed harness is configured and extended:

- A plugin marketplace manifest bundling 13 official plugins (`.claude-plugin/marketplace.json:3-10`).
- Worked implementations of each extension type the harness supports: slash commands, subagents, skills, hooks, and MCP tool references (see Mechanism).
- Example settings, MDM policy templates, and a firewalled devcontainer that show the enterprise permission/sandbox boundary (`examples/settings/README.md:3`, `examples/mdm/README.md:3`, `.devcontainer/devcontainer.json:2`).
- A 5610-line changelog (versions `0.2.21` through `2.1.235`) that is the only dated record of when harness mechanisms shipped (`CHANGELOG.md:5610`, `CHANGELOG.md:3`).

## Mechanism

### Marketplace and plugin manifests

The repo root is itself a plugin marketplace: `.claude-plugin/marketplace.json` declares `"name": "claude-code-plugins"` with `"$schema": "https://json.schemastore.org/claude-code-marketplace.json"` and lists 13 plugins by `name`, `description`, `version`, `author`, `source` (a relative path such as `"./plugins/agent-sdk-dev"`), and `category` (`development`, `productivity`, `learning`, `security`) (`.claude-plugin/marketplace.json:2-149`).

Each plugin lives under `plugins/<name>/` with metadata in `.claude-plugin/plugin.json`. Manifests are minimal JSON: `name` is required; `version`, `description`, `author{name,email}`, `homepage` are optional (compare `plugins/agent-sdk-dev/.claude-plugin/plugin.json:1-9`, minimal, with `plugins/security-guidance/.claude-plugin/plugin.json:1-10`, which adds `homepage`). The in-repo skill documentation for the format states that `.claude-plugin/plugin.json` "MUST be in the `.claude-plugin/` directory" or "Claude Code will not recognize plugins" (`plugins/plugin-dev/skills/plugin-structure/references/manifest-reference.md:6-9`), defines `name` as kebab-case matching `/^[a-z][a-z0-9]*(-[a-z0-9]+)*$/` (`manifest-reference.md:33-36`), and gives component-path defaults: `commands` → `["./commands"]`, `agents` → `["./agents"]`, `hooks` → `"./hooks/hooks.json"`, `mcpServers` → `"./.mcp.json"` (`manifest-reference.md:211-301`).

Anomaly at the pinned commit: `plugins/plugin-dev/` has no `.claude-plugin/plugin.json` (directory contains only `agents/`, `commands/`, `README.md`, `skills/`; glob `**` over the plugin finds no manifest), yet the marketplace lists it (`plugins/plugin-dev` entry at `.claude-plugin/marketplace.json:105-115`) and its own documentation calls the manifest required. Also, `security-guidance`'s marketplace entry says `"version": "1.0.0"` (`.claude-plugin/marketplace.json:141`) while its manifest says `"version": "2.0.0"` (`plugins/security-guidance/.claude-plugin/plugin.json:3`), and `plugins/README.md:27` still describes it as monitoring "9 security patterns" while its manifest says "25+ other vulnerability classes". These drifts show the extension material is not self-consistent at this commit.

### Extension component types, as evidenced by the bundled plugins

`plugins/README.md:7` states the mental model: "plugins are extensions that enhance Claude Code with custom commands, agents, hooks, and MCP servers", and `plugins/README.md:51-61` gives the canonical layout (`commands/`, `agents/`, `skills/`, `hooks/`, `.mcp.json`). The bundlings per plugin are tabulated at `plugins/README.md:13-27`.

Commands (Markdown with YAML frontmatter):
- Frontmatter keys in use: `description`, `allowed-tools`, `argument-hint`, `hide-from-slash-command-tool` (`plugins/commit-commands/commands/commit.md:1-4`, `plugins/ralph-wiggum/commands/ralph-loop.md:1-6`, `plugins/pr-review-toolkit/commands/review-pr.md:1-5`).
- `allowed-tools` carries permission-rule syntax with the same grammar as settings rules: plain tool names (`"Bash", "Glob", "Grep", "Read", "Task"` at `plugins/pr-review-toolkit/commands/review-pr.md:4`), prefixes with `:*` (`Bash(git add:*), Bash(git status:*), Bash(git commit:*)` at `plugins/commit-commands/commands/commit.md:2`), script-scoped rules (`Bash(${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh:*)` at `plugins/ralph-wiggum/commands/ralph-loop.md:4`), and MCP tool names with the `mcp__<server>__<tool>` convention (`mcp__github_inline_comment__create_inline_comment` at `plugins/code-review/commands/code-review.md:2`).
- Command bodies support inline shell execution with bang-backtick context lines (`!`git status`` at `plugins/commit-commands/commands/commit.md:8-11`) and a ` ```! ` fenced block that runs a script at expansion time (`plugins/ralph-wiggum/commands/ralph-loop.md:12-14`), plus `$ARGUMENTS` substitution (`plugins/ralph-wiggum/commands/ralph-loop.md:13`, `plugins/feature-dev/commands/feature-dev.md:24`).

Subagents (Markdown with YAML frontmatter):
- Frontmatter keys in use: `name`, `description`, `tools`, `model`, `color` (`plugins/feature-dev/agents/code-explorer.md:1-7`). `tools` appears both as a comma-separated string (`plugins/feature-dev/agents/code-explorer.md:4`: `Glob, Grep, LS, Read, NotebookRead, WebFetch, TodoWrite, WebSearch, KillShell, BashOutput`) and as a JSON list (`plugins/hookify/agents/conversation-analyzer.md:6`: `["Read", "Grep"]`). `model` takes `sonnet` (`plugins/feature-dev/agents/code-explorer.md:5`) or `inherit` (`plugins/pr-review-toolkit/agents/type-design-analyzer.md:4`). `color` takes values including `yellow`, `green`, `red` (feature-dev agents) and `pink` (`plugins/pr-review-toolkit/agents/type-design-analyzer.md:5`); the agent-development skill lists `blue/cyan/green/yellow/magenta/red` as the palette (`plugins/plugin-dev/skills/agent-development/examples/agent-creation-prompt.md:48`).
- Omitting `tools` means no restriction is declared (`plugins/pr-review-toolkit/agents/type-design-analyzer.md:1-6` has no `tools` key). The subagent body is a system prompt; descriptions embed `<example>` blocks as triggering hints (`plugins/pr-review-toolkit/agents/type-design-analyzer.md:3`).
- Workflow commands orchestrate model-specified subagents in prose: the `/code-review` command launches "a haiku agent" for triage, "a sonnet agent" to summarize, "4 agents in parallel" (2 CLAUDE.md-compliance sonnet agents, 2 "Opus bug agent"s), then per-issue Opus/sonnet validation subagents, and gates GitHub commenting behind a `--comment` argument (`plugins/code-review/commands/code-review.md:14-67`). `/feature-dev` is a 7-phase workflow that launches 2-3 `code-explorer`, `code-architect`, and `code-reviewer` subagents with explicit human approval gates between phases (`plugins/feature-dev/commands/feature-dev.md:20-124`).

Skills (directories with `SKILL.md`):
- Skills are frontmatter Markdown: `name` and `description` (`plugins/frontend-design/skills/frontend-design/SKILL.md:1-3`, `plugins/claude-opus-4-5-migration/skills/claude-opus-4-5-migration/SKILL.md:1-3`), optionally `version` (`plugins/plugin-dev/skills/hook-development/SKILL.md:4`) and `license` (`plugins/frontend-design/skills/frontend-design/SKILL.md:4`). Descriptions are written as trigger conditions ("This skill should be used when the user asks to..."), i.e. the description is the routing signal for model-driven invocation (`plugins/plugin-dev/skills/hook-development/SKILL.md:3`, `plugins/hookify/skills/writing-rules/SKILL.md:3`).
- Skills may carry `references/`, `examples/`, and `scripts/` subdirectories loaded on demand (e.g. `plugins/plugin-dev/skills/hook-development/scripts/` and `plugins/claude-opus-4-5-migration/skills/claude-opus-4-5-migration/references/` file trees).

Hooks (`hooks/hooks.json` + handler scripts):
- Plugin hook manifests wrap events under `{"description": ..., "hooks": {...}}` (`plugins/hookify/hooks/hooks.json:1-48`). Event keys observed: `PreToolUse`, `PostToolUse`, `Stop`, `UserPromptSubmit` (hookify, `hooks.json:4-47`), `SessionStart`, `UserPromptSubmit`, `PostToolUse`, `Stop` (security-guidance, `plugins/security-guidance/hooks/hooks.json:4-69`), `SessionStart` (both output-style plugins, `plugins/explanatory-output-style/hooks/hooks.json:4-13`), `Stop` (ralph-wiggum, `plugins/ralph-wiggum/hooks/hooks.json:4-13`).
- Each event lists matcher groups containing a `hooks` array of `{"type": "command", "command": ..., "timeout": N}`; `matcher` filters by tool name regex (`"Edit|Write|MultiEdit|NotebookEdit"` at `plugins/security-guidance/hooks/hooks.json:33`, `"Bash"` at `hooks.json:54`), and an `if` field reuses permission-rule syntax (`"if": "Bash(git commit:*)"` and `"if": "Bash(git push:*)"` at `plugins/security-guidance/hooks/hooks.json:40,48`).
- Three fields not documented in the in-repo skill docs appear in `security-guidance`: `"asyncRewake": true` with `"rewakeMessage"` and `"rewakeSummary"` strings, which let a background review re-wake the session with findings (`plugins/security-guidance/hooks/hooks.json:41-43,49-51,63-65`).
- `${CLAUDE_PLUGIN_ROOT}` is the portability anchor in every hook command (`plugins/hookify/hooks/hooks.json:9,20,31,42`, `plugins/security-guidance/hooks/hooks.json:9,20,30,39,47,62`).

The hook transport protocol (stdin/stdout JSON + exit codes), evidenced by shipped handlers:
- PreToolUse hooks receive JSON on stdin with at least `tool_name` and `tool_input`; the canonical example checks `tool_name == "Bash"` and reads `tool_input.command` (`examples/hooks/bash_command_validator_example.py:58-72`). Its comments define the exit-code contract: "Exit code 1 shows stderr to the user but not to Claude" (`:61`) and "Exit code 2 blocks tool call and shows stderr to Claude" (`:78`); exit 0 silently passes (`:66,72`).
- Stop hooks receive stdin JSON with a `transcript_path` field (`plugins/ralph-wiggum/hooks/stop-hook.sh:9-10,58`). The transcript is JSONL, one JSON object per line, with assistant messages keyed `"role":"assistant"` and text blocks under `.message.content` selected by `.type == "text"` (`plugins/ralph-wiggum/hooks/stop-hook.sh:69-95`).
- To keep iterating instead of stopping, a Stop hook prints `{"decision": "block", "reason": <prompt to re-inject>, "systemMessage": ...}` and exits 0 (`plugins/ralph-wiggum/hooks/stop-hook.sh:165-177`); ralph-wiggum uses this to re-submit the original prompt each iteration, tracking state in `.claude/ralph-loop.local.md` (`plugins/ralph-wiggum/hooks/stop-hook.sh:13-23,130-156`).
- SessionStart hooks inject context by printing `{"hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": ...}}` (`plugins/explanatory-output-style/hooks-handlers/session-start.sh:6-13`, same shape in `plugins/learning-output-style/hooks-handlers/session-start.sh:6-12`).
- PreToolUse denial via JSON: hookify's rule engine emits `{"hookSpecificOutput": {"hookEventName": "PreToolUse"|"PostToolUse", "permissionDecision": "deny"}, "systemMessage": ...}` for blocking rules and `{"decision": "block", "reason": ..., "systemMessage": ...}` for the `Stop` event (`plugins/hookify/core/rule_engine.py:61-94`). Hookify deliberately fails open: any exception path prints a `systemMessage` and exits 0 ("ALWAYS exit 0 - never block operations due to hook errors", `plugins/hookify/hooks/pretooluse.py:61-70`).
- The in-repo hook authoring skill enumerates nine hook events (`PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `SessionStart`, `SessionEnd`, `PreCompact`, `Notification`) with use cases (`plugins/plugin-dev/skills/hook-development/SKILL.md:3,632-644`), documents the common stdin fields `session_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name` plus event-specific `tool_name`/`tool_input`/`tool_result`, `user_prompt`, `reason` (`SKILL.md:300-320`), standard output keys `continue`, `suppressOutput`, `systemMessage` (`SKILL.md:280-292`), exit codes 0/2/other (`SKILL.md:294-298`), environment variables `$CLAUDE_PROJECT_DIR`, `$CLAUDE_PLUGIN_ROOT`, `$CLAUDE_ENV_FILE` (SessionStart only), `$CLAUDE_CODE_REMOTE` (`SKILL.md:322-331`), parallel execution of matched hooks with nondeterministic ordering (`SKILL.md:495-517`), and session-start loading with no hot swap ("Changes to hook configuration require restarting Claude Code", `SKILL.md:574-582`; `/hooks` shows loaded hooks, `SKILL.md:598`). It also documents a `"type": "prompt"` LLM-evaluated hook variant supported on `Stop`, `SubagentStop`, `UserPromptSubmit`, `PreToolUse` (`SKILL.md:22-34`). These skill-doc statements describe the closed core and can drift from it; treat as semi-official docs bundled with the surface [EVIDENCE NEEDED against the core].

Hookify as a case study in building policy on the hook surface:
- Hookify registers command hooks on four events (`plugins/hookify/hooks/hooks.json:4-47`), each spawning `python3 ${CLAUDE_PLUGIN_ROOT}/hooks/<event>.py` with `timeout: 10` (`:10`). The PreToolUse handler classifies `tool_name` into virtual events `bash` (for `Bash`) and `file` (for `Edit`, `Write`, `MultiEdit`) (`plugins/hookify/hooks/pretooluse.py:43-49`), loads user rules from `.claude/hookify.*.local.md` files (`pretooluse.py:2-6`), and evaluates them in a regex rule engine with 128-pattern LRU cache (`plugins/hookify/core/rule_engine.py:13-24`). Rules are Markdown with frontmatter `name`, `enabled`, `event`, `pattern`, `action`, optional `conditions` (`plugins/hookify/examples/dangerous-rm.local.md:1-7`; a `stop` rule with `conditions: field: transcript, operator: not_contains` at `plugins/hookify/examples/require-tests-stop.local.md:1-10`), and the rule body is the warning text shown on match.

Security-guidance as a case study in hooks doing LLM-in-the-loop review:
- Two layers per its module docstring: (1) regex pattern rules on every `PostToolUse` edit, injecting warnings; (2) a Stop-hook `git diff` review against a baseline SHA captured at `UserPromptSubmit` via `git stash create`, running "two Haiku analyses" and exiting with code 2 to force Claude to address findings (`plugins/security-guidance/hooks/security_reminder_hook.py:8-36`). The baseline advances after each Stop review so only new changes are re-reviewed (`:29-35`).
- It defines 25 built-in patterns in `SECURITY_PATTERNS` with `ruleName` keys including `github_actions_workflow`, `child_process_exec`, `eval_injection`, `innerHTML_xss`, `pickle_deserialization`, `os_system_injection`, `python_subprocess_shell`, `torch_unsafe_load` (counted from the 25 `"ruleName":` entries at `plugins/security-guidance/hooks/patterns.py:32,72,96,101,109,114,119,124,133,140,158,179,184,189,194,199,204,209,214,219,224,229,241,248,255`), plus user-extensible `user:<name>` rules (`plugins/security-guidance/hooks/extensibility.py:219`).
- Its SessionStart hook bootstraps a Python venv at `~/.claude/security/agent-sdk-venv` and pip-installs `claude_agent_sdk` for its agentic commit reviewer, skipping Windows (`plugins/security-guidance/hooks/ensure_agent_sdk.py:6-9,63-78`); hooks.json grants it `timeout: 180` (`plugins/security-guidance/hooks/hooks.json:9-11`).
- It calls the Anthropic API from inside a hook, honoring `ANTHROPIC_BASE_URL` ("the convention the Anthropic SDK and CC itself use", `plugins/security-guidance/hooks/llm.py:90-99`), and relies on Claude Code passing `ANTHROPIC_AUTH_TOKEN` into hook environments for OAuth users: "Claude Code passes this automatically for OAuth-authenticated users" (`plugins/security-guidance/hooks/security_reminder_hook.py:51-52`, `llm.py:36-38`). OAuth subscriber tokens require an exact system prompt prefix, hardcoded as `"You are a Claude agent, built on Anthropic's Claude Agent SDK."` (`plugins/security-guidance/hooks/llm.py:66-70`).

### Settings and managed-policy surface

The three example settings files define the permission/sandbox configuration schema by example:
- `examples/settings/settings-strict.json:1-28`: `permissions.disableBypassPermissionsMode: "disable"`, `permissions.ask: ["Bash"]`, `permissions.deny: ["WebSearch", "WebFetch"]`, `allowManagedPermissionRulesOnly: true`, `allowManagedHooksOnly: true`, `strictKnownMarketplaces: []`, and a `sandbox` object with `autoAllowBashIfSandboxed`, `excludedCommands`, `network.{allowUnixSockets, allowAllUnixSockets, allowLocalBinding, allowedDomains, httpProxyPort, socksProxyPort}`, `enableWeakerNestedSandbox`.
- `examples/settings/settings-bash-sandbox.json:1-18`: `allowManagedPermissionRulesOnly: true` plus `sandbox.enabled: true`, `sandbox.autoAllowBashIfSandboxed: false`, `sandbox.allowUnsandboxedCommands: false`.
- `examples/settings/settings-lax.json:1-6`: just `permissions.disableBypassPermissionsMode: "disable"` and `strictKnownMarketplaces: []`.
- The settings README warns that `strictKnownMarketplaces`, `allowManagedHooksOnly`, `allowManagedPermissionRulesOnly` "only take effect if specified in enterprise settings" (`examples/settings/README.md:5`) and, most importantly for the scope of sandboxing, that "The `sandbox` property only applies to the `Bash` tool; it does not apply to other tools (like Read, Write, WebSearch, WebFetch, MCPs), hooks, or internal commands" (`examples/settings/README.md:27`).
- MDM distribution: templates for Jamf, Iru (Kandji), Intune, and Group Policy (`examples/mdm/README.md:3`); the macOS preference domain is `com.anthropic.claudecode` (`examples/mdm/README.md:16`), Windows policy lives at `HKLM\SOFTWARE\Policies\ClaudeCode\Settings` as single-line JSON (`examples/mdm/README.md:19`), and the Intune script writes to `C:\Program Files\ClaudeCode\` (`examples/mdm/README.md:18`). "Settings deployed this way sit at the top of the precedence order and cannot be overridden by users" (`examples/mdm/README.md:24`). The minimal managed payload is `{"permissions": {"disableBypassPermissionsMode": "disable"}}` (`examples/mdm/managed-settings.json:1-5`).

### Sandboxed execution beyond settings: devcontainer and gateway

- `.devcontainer/devcontainer.json:2` names the container "Claude Code Sandbox". It runs with `--cap-add=NET_ADMIN` and `--cap-add=NET_RAW` (`:12-15`), mounts `~/.claude` as a named volume with `CLAUDE_CONFIG_DIR=/home/node/.claude` (`:44-51`), and gates container start on `postStartCommand: sudo /usr/local/bin/init-firewall.sh` with `waitFor: postStartCommand` (`:55-56`).
- `init-firewall.sh` builds an egress allowlist: an ipset named `allowed-domains` (`:41`) populated from `https://api.github.com/meta` ranges (`:44-64`) plus DNS-resolved `registry.npmjs.org`, `api.anthropic.com`, `sentry.io`, `statsig.com`, `marketplace.visualstudio.com`, `vscode.blob.core.windows.net`, `update.code.visualstudio.com` (`:67-74`), then sets `iptables -P OUTPUT DROP` (`:107-109`) and REJECTs all other egress (`:119`), verifying `https://example.com` is unreachable while `https://api.github.com/zen` is reachable (`:123-135`). The firewall script is sudoers-granted to the `node` user (`Dockerfile:86-90`) and Claude Code itself is installed via `npm install -g @anthropic-ai/claude-code@${CLAUDE_CODE_VERSION}` (`Dockerfile:81-82`). `Script/run_devcontainer_claude_code.ps1:29-34,140-148` automates bringing this container up under Docker or Podman and execing `claude` inside it.
- `examples/gateway/` provides reference deployments of a "Claude apps gateway" (a `claude gateway` binary with its own config: `listen`, `oidc`, `session`, `store`, `upstreams`) on AWS with Bedrock upstream and on GCP (`examples/gateway/aws/README.md:1-19`). The config template shows enterprise RBAC pushing CLI policy by IdP group: `availableModels: [claude-opus-4-8, claude-sonnet-4-6, claude-haiku-4-5]` and `permissions: { deny: ["Read(./.env)", "Read(./secrets/**)"] }` under `managed.policies[].cli` (`examples/gateway/aws/gateway.yaml.example:131-142`), confirming the rule grammar `Read(<glob>)` used by the closed permission engine.

## Relevance to the brief

Inference, separated from repo facts:

- RQ1/RQ4: for Claude Code, this surface is the closest thing to primary evidence about harness design philosophy. The extension system is declarative and file-based (Markdown + JSON frontmatter), discovers components by convention (`plugins/plugin-dev/skills/plugin-structure/SKILL.md:24-44`), and keeps all logic user-supplied scripts; the core stays closed while exposing a rich event bus (at least nine hook events documented, plus `Setup`, `MessageDisplay`, `WorktreeCreate` family, `PermissionRequest`/`PermissionDenied`, `Elicitation` events per changelog). If Codex and OpenCode expose extension points, Claude Code's are unusually deep: hooks can inject model context, rewrite or deny tool inputs, block stops to create agent loops, and even re-wake finished sessions.
- RQ2: the component list implied by this surface is: turn control (Stop/PreCompact/Notification hooks), tools (permission-rule grammar over named tools), context management (SessionStart/UserPromptSubmit additionalContext, `PreCompact` preservation hooks, skill on-demand loading evidenced by the `claude-api` skill token drop at `CHANGELOG.md:65`), permissions (ask/allow/deny rules, managed-settings hierarchy), extensibility (plugins/marketplaces/hooks/skills/MCP). This maps cleanly onto the brief's five harness dimensions, with memory (CLAUDE.md, auto-memory) and rollout covered only by docs-tier sources.
- RQ3: capability-vs-safety here is layered and explicitly asymmetric. In-process controls (permission rules, Bash-only sandbox setting, `disableBypassPermissionsMode`) are policy, while the reference hard confinement is out-of-process (devcontainer firewall, `CHANGELOG.md`-recorded bubblewrap paths `sandbox.bwrapPath`). The settings README's statement that the sandbox excludes Read/Write/MCP/hooks (`examples/settings/README.md:27`) is the single most important sentence for comparing Claude Code's safety story against Codex's repo-level sandbox crate and OpenCode's permission rulesets. The changelog's steady stream of permission-bypass fixes (e.g. `CHANGELOG.md:116-118,1404,1567,2920`) indicates the in-process layer is treated as an actively attacked surface.
- Left open by this source: how hooks and permissions interact inside the core (priority, caching, the "auto mode classifier" referenced at `CHANGELOG.md:2932,2935`), how compaction is triggered beyond the 80% threshold note (`CHANGELOG.md:5201`), and what `permission_mode` values exist beyond "ask|allow" (`plugins/plugin-dev/skills/hook-development/SKILL.md:309`). These are docs-tier or teardown-tier questions.
