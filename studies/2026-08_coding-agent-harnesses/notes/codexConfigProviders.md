## Purpose and role in the harness

- This component defines how Codex assembles its effective configuration before and during a session, and how it abstracts the model backends that the turn loop (see `notes/codexTurnLoop.md`) samples. Configuration is a layered TOML stack: `load_config_layers_state` builds a `ConfigLayerStack` whose `effective_config()` is the merged view every other subsystem consumes (`codex-rs/config/src/loader/mod.rs:128-135`, `codex-rs/config/src/state.rs:455-461`).
- The loader README states the module's charter: it is "the canonical place to load and describe Codex configuration layers (user config, CLI/session overrides, cloud-managed config, managed config, and MDM-managed preferences) and to produce: An effective merged TOML config. Per-key origins metadata (which layer 'wins' for a given key). Per-layer versions (stable fingerprints) used for optimistic concurrency / conflict detection." (`codex-rs/config/src/loader/README.md:3-7`).
- Model providers are data, not code plugins: a `ModelProviderInfo` value fully describes one backend (base URL, auth wiring, wire protocol, retries), and the runtime dispatches on it (`codex-rs/model-provider-info/src/lib.rs:95-150`, `codex-rs/model-provider/src/provider.rs:293-303`). Built-in providers ship in the binary; user-defined providers extend them via the `[model_providers]` table in `config.toml` (`codex-rs/model-provider-info/src/lib.rs:3-6`).
- Credential plumbing at the provider boundary is the `AuthProvider` trait implementations that turn a `CodexAuth` (ChatGPT login, API key, agent identity, AWS SigV4, command-fetched token) into request headers (`codex-rs/model-provider/src/auth.rs:303-320`, `codex-rs/model-provider/src/bearer_auth_provider.rs:31-47`). The interactive login machinery itself (`codex-login`, `auth.json` storage, keyring) is outside this component and is referenced only at its boundary.
- Inference about role: this is the config/providers dimension of RQ1/RQ2 for Codex, and it is where enterprise governance (system files, MDM, cloud bundles, requirements) enters the harness, which touches RQ3 (capability vs safety) because managed layers can constrain approval policy, sandbox mode, and login methods without the user being able to override them. Stated as inference; the code facts below are what the source establishes.

### Layer model and precedence

- Each layer has a provenance `ConfigLayerSource`: `PackagedDefaults { file }`, `Mdm { domain, key }`, `System { file }`, `EnterpriseManaged { id, name }`, `User { file, profile }`, `Project { dot_codex_folder }`, `SessionFlags`, `LegacyManagedConfigTomlFromFile { file }`, `LegacyManagedConfigTomlFromMdm` (`codex-rs/config/src/config_layer_source.rs:6-28`).
- Numeric precedence (`codex-rs/config/src/config_layer_source.rs:33-51`): `PackagedDefaults` -10, `Mdm` 0, `System` 10, `EnterpriseManaged` 15, `User` 20 (21 when `profile` is `Some`), `Project` 25, `SessionFlags` 30, `LegacyManagedConfigTomlFromFile` 40, `LegacyManagedConfigTomlFromMdm` 50. "A setting from a layer with a higher precedence overrides a setting from a layer with a lower precedence." (`config_layer_source.rs:31-32`).
- The loader README's precedence list ("top overrides bottom"): LegacyManagedConfigTomlFromMdm, LegacyManagedConfigTomlFromFile, SessionFlags, Project, User profile, User, EnterpriseManaged, System (`codex-rs/config/src/loader/README.md:26-36`). The stack stores layers in the opposite order, lowest first, "so later layers override earlier layers when folded" (`README.md:37-40`).
- Push order in `load_config_layers_state` matches the README: packaged defaults (`loader/mod.rs:271`), system (`loader/mod.rs:292-307`), cloud enterprise-managed layers (`loader/mod.rs:308`), base user (`loader/mod.rs:313-345`), profile-v2 user layer when it differs from the base file (`loader/mod.rs:347-358`), project layers (`loader/mod.rs:415-424`), session flags (`loader/mod.rs:431-436`), thread config layers inserted by precedence (`loader/mod.rs:438-440`, `loader/mod.rs:546-554`), legacy managed file (`loader/mod.rs:452-468`), legacy managed from MDM (`loader/mod.rs:469-487`). (Interpretation: the two legacy managed sources deliberately sit above session flags so an admin-pinned `managed_config.toml` beats `--config` overrides for the fields it sets; the README documents exactly this ranking.)
- Discrepancy inside the source: the doc comment on `load_config_layers_state` lists a different construction order ending in "runtime e.g., --config flags, model selector in UI" (`loader/mod.rs:105-117`), which omits the legacy managed layers that the code pushes after session flags. The README (`loader/README.md:26-36`) and the actual push order agree with each other and contradict that doc comment on the position of legacy managed config; I follow the README plus code.
- `ConfigLayerStack::new` rejects malformed stacks: `validate_enabled_config_layers` (shell-environment policy shape, `codex-rs/config/src/state.rs:511-524`) and `verify_layer_ordering`, which requires layers sorted by precedence and project layers ordered root-to-cwd (`state.rs:527-569`).
- Layers can be constructed disabled with `ConfigLayerEntry::new_disabled(source, config, reason)` (`state.rs:164-178`); disabled layers are skipped by `effective_config()` and `origins()` because `layers_low_to_high()` filters `!layer.is_disabled()`, but they stay visible for UI via `all_layers_low_to_high()` (`state.rs:455-499`, `loader/README.md:48-50`). Project layers are the primary disabled case: when the project is untrusted they carry the message "To load project-local config, hooks, and exec policies, add {trust_key} as a trusted project in {user_config_file}." or, when explicitly untrusted, "{trust_key} is marked as untrusted in the effective configuration..." (`loader/mod.rs:1056-1074`).

### Merge rules

- `merge_toml_values(base, overlay)` merges recursively with overlay winning: two tables merge key-by-key, any other combination replaces base wholesale (`codex-rs/config/src/merge.rs:57-121`, especially the trailing `else` at `merge.rs:118-120`). (Interpretation: arrays and scalars from a higher layer replace, they never union; the only additive behaviors are special-cased below.)
- Special merge cases:
  - `features.multi_agent_v2` tolerates bool/table forms in either layer and merges a bool into the table's `enabled` key (`merge.rs:61-92`).
  - Switching between the `filters` and legacy `exclude`/`include_only` representations of `shell_environment_policy` removes the displaced fields instead of reconciling them (`merge.rs:6-54`, `merge.rs:131-155`).
  - `permissions.*.network.domains` keys are normalized through `normalize_host` before merging (`merge.rs:100-103`, `merge.rs:177-190`); shell-environment filter keys are lower-cased (`merge.rs:104-107`, `merge.rs:192-197`).
  - Key aliases are normalized on both sides before table merge (`merge.rs:97-99`).
- Relative path fields are resolved per layer against that layer's own base directory before merging, "so multiple config layers can be merged together correctly even if they were loaded from different directories" (`loader/mod.rs:1244-1274`).
- Per-key `origins()` records the winning layer metadata for every dotted path (`state.rs:466-476`); each `ConfigLayerEntry` also carries a stable `version` fingerprint computed at construction (`state.rs:131-142`).

### Layer discovery and files

- `CONFIG_TOML_FILE` is `"config.toml"` (`codex-rs/config/src/lib.rs:36`).
- `CODEX_HOME` resolution (outside component, anchored here because every user-layer path hangs off it): `find_codex_home` honors the `CODEX_HOME` env var (must exist and be a directory; value is canonicalized, otherwise `NotFound`/`InvalidInput` errors) and otherwise returns `~/.codex` without checking existence (`codex-rs/utils/home-dir/src/lib.rs:13-63`).
- Packaged defaults are compiled into the binary via `include_str!("../../defaults.toml")` (`loader/mod.rs:169-183`); the layer source is `ConfigLayerSource::PackagedDefaults` with the current executable path. A `LoaderOverrides::packaged_defaults_path` override replaces the embedded file and errors when missing (`loader/mod.rs:141-167`).
- System layer: `/etc/codex/config.toml` on Unix (`loader/mod.rs:61-62`, `loader/mod.rs:783-786`); `%ProgramData%\OpenAI\Codex\config.toml` on Windows, resolving `ProgramData` via `SHGetKnownFolderPath` with a `C:\ProgramData` fallback (`loader/mod.rs:64-65`, `loader/mod.rs:802-824`). A missing file yields an empty table rather than an error (`loader/mod.rs:563-573`, `loader/mod.rs:614-616`).
- System requirements: `/etc/codex/requirements.toml` on Unix (`loader/mod.rs:728-731`), `%ProgramData%\OpenAI\Codex\requirements.toml` on Windows (`loader/mod.rs:814-818`), loaded as a requirements layer (`loader/mod.rs:680-726`).
- Legacy managed config: `/etc/codex/managed_config.toml` on Unix (`codex-rs/config/src/loader/layer_io.rs:19-20`, `layer_io.rs:210-221`); on Windows the old `CODEX_HOME/managed_config.toml` location is only checked to emit a deprecation warning ("Ignoring deprecated managed config file at ...; CODEX_HOME/managed_config.toml is no longer supported on Windows. Use %ProgramData%\OpenAI\Codex\requirements.toml for enforced settings or config.toml for defaults.", `layer_io.rs:72-94`).
- macOS managed preferences read the managed preferences domain `com.openai.codex`, keys `config_toml_base64` (config layer) and `requirements_toml_base64` (requirements layer) (`codex-rs/config/src/loader/macos.rs:20-22`, `macos.rs:30-42`, `macos.rs:72-81`, `macos.rs:115-120`); this is the only MDM source and is macOS-only (`loader/mod.rs:212-226`).
- Project layers: project root is found by walking `cwd` ancestors for `project_root_markers` (default `[".git"]`, `codex-rs/config/defaults.toml:14`; resolution at `loader/mod.rs:376-388` and `loader/mod.rs:1305-1328`), then `.codex/config.toml` layers are discovered between project root and cwd (`loader/mod.rs:1373-1396`) and gated by project trust from the `projects` table of the merged non-project config (`loader/mod.rs:982-1008`, `loader/mod.rs:1144-1193`).
- Project-local config cannot set provider/auth-related keys. `PROJECT_LOCAL_CONFIG_DENYLIST` lists `openai_base_url`, `chatgpt_base_url`, `apps_mcp_product_sku`, `responses_api_metadata`, `model_provider`, `model_providers`, `notify`, `profile`, `profiles`, `experimental_realtime_webrtc_call_base_url`, `experimental_realtime_ws_base_url`, `otel` (`loader/mod.rs:71-84`), with the comment "Project-local config comes from repository contents, so it should not get to choose where a user's credentials are sent or which local commands are run." (`loader/mod.rs:67-70`). `sanitize_project_config` strips these plus `features.respect_system_proxy` and collects the removed keys for a startup warning (`loader/mod.rs:1107-1142`).
- CLI/session overrides: `-c/--config` style dotted-path overrides become one `SessionFlags` layer via `build_cli_overrides_layer` (`loader/mod.rs:273-288`, `loader/mod.rs:431-436`); `apply_toml_override` walks each dotted path creating intermediate tables (`codex-rs/config/src/overrides.rs:9-15`, `overrides.rs:18-99`). Under `strict_config`, unknown fields in overrides are rejected ("unknown configuration field `{ignored_path}` in -c/--config override", `loader/mod.rs:657-678`), and unknown fields in any config file fail loading (`loader/mod.rs:604-611`, `loader/mod.rs:635-655`).
- `has_local_managed_configuration` probes managed sources (legacy managed file, system requirements, macOS managed preferences) without parsing, so callers can "conservatively avoid assuming that administrator-controlled configuration is absent" on I/O errors (`loader/mod.rs:747-781`).

### Profiles

- Legacy profiles: `ConfigToml` has `profile: Option<String>` ("Profile to use from the `profiles` map", `codex-rs/config/src/config_toml.rs:311-312`) and `profiles: HashMap<String, ConfigProfile>` (`config_toml.rs:314-316`). `ConfigProfile` is a `deny_unknown_fields` schema of per-profile overrides including `model`, `service_tier`, `model_provider`, `approval_policy`, `approvals_reviewer`, `sandbox_mode`, `model_reasoning_effort`, `model_catalog_json`, `chatgpt_base_url`, `tools`, `features`, `oss_provider`, among others (`codex-rs/config/src/profile_toml.rs:22-71`).
- Profile-v2: a `--profile <name>` flag resolves to `$CODEX_HOME/<name>.config.toml`. "Validated plain profile-v2 name used to select `$CODEX_HOME/<name>.config.toml`." (`codex-rs/protocol/src/config_types.rs:98-100`); names must be non-empty ASCII alphanumerics plus `_` and `-`, so no path traversal (`config_types.rs:125-141`). When selected, the loader stacks the base user layer (precedence 20) and the profile file as a second `User` layer (precedence 21, `config_layer_source.rs:39-45`), so "the profile only needs to contain overrides" (`loader/mod.rs:310-312`, `loader/mod.rs:347-358`).
- Legacy and profile-v2 are mutually exclusive per profile name: selecting `--profile X` while `config.toml` still has `profile = "X"` or `[profiles.X]` is an `InvalidData` error directing the user to move settings into `<name>.config.toml` (`loader/mod.rs:323-344`).
- `get_active_user_layer` returns the topmost `User` layer, so profile-aware config edits write to the profile file rather than the base config (`state.rs:309-328`, comment `state.rs:310-314`).

### Requirements (admin-enforced constraints)

- Requirements are a separate stack composed lowest-to-highest: system `requirements.toml`, cloud bundle requirements, legacy `managed_config.toml` reinterpreted as requirements, and macOS managed preferences (`loader/mod.rs:90-103`, `loader/mod.rs:240-250`). They live alongside, not inside, the config stack: `ConfigLayerStack` stores `requirements` and `requirements_toml` separately (`state.rs:246-259`, `state.rs:504-508`).
- Legacy backfill: a legacy `managed_config.toml` `approval_policy` becomes `allowed_approval_policies = [policy]`, `approvals_reviewer` becomes `allowed_approvals_reviewers` (with `user` appended when `auto_review` is required), and `sandbox_mode` becomes `allowed_sandbox_modes` with read-only always appended because "Allowing read-only is a requirement for Codex to function correctly." (`loader/mod.rs:939-976`, quotes at `loader/mod.rs:964-965`).
- Remote app servers can opt out of local login restrictions: when `ignore_login_requirements` is set, `allowed_login_methods` and `allowed_chatgpt_workspaces` are nulled out of the composed requirements ("Remote app servers enforce auth policy for their workspaces", `loader/mod.rs:254-259`).
- `ManagedAuthPolicy` evaluates those restrictions: `allowed_login_methods` intersected with `forced_login_method`, and ChatGPT login additionally requires a non-empty effective workspace allowlist (`codex-rs/config/src/auth_policy.rs:10-39`, `auth_policy.rs:41-60`).

### Enterprise cloud config bundle

- The `codex-cloud-config` crate owns transport, caching, and refresh; "Parsing and composition remain in `codex-config`." (`codex-rs/cloud-config/src/lib.rs:1-4`).
- Eligibility: the bundle is fetched only when auth uses the Codex backend and the plan is business-like, education-like, or Enterprise (`codex-rs/cloud-config/src/service.rs:48-56`).
- Startup path: identity-matched cache first, backend only on miss (`service.rs:174-197`). Cache file is `$CODEX_HOME/cloud-config-bundle-cache.json` (`codex-rs/cloud-config/src/cache.rs:24`, `cache.rs:39-43`), TTL 60 minutes (`cache.rs:25`), version 1 (`cache.rs:23`), HMAC-SHA256 signed with a fixed embedded key (`cache.rs:26-29`); load verifies signature, version, user/account identity match, and expiry, failing to `CacheLoadStatus` variants such as `CacheSignatureInvalid`, `CacheIdentityMismatch`, `CacheExpired` (`cache.rs:49-107`).
- Remote fetch: up to 5 attempts with backoff, unauthorized responses routed through `AuthManager` recovery (permanent failure errors out with "Your authentication session could not be refreshed automatically. Please log out and sign in again.", transient ones retry) (`service.rs:35`, `service.rs:230-301`, messages at `service.rs:37-42`); whole startup load is capped at 15 seconds (`service.rs:34`, `codex-rs/cloud-config/src/bundle_loader.rs:42-56`). Bundles are validated before caching, and cache write failures only warn (`service.rs:303-344`).
- A background task refreshes the cache every 15 minutes and updates the in-memory "latest bundle" observed by future config loads (`service.rs:36`, `service.rs:460-510`, `bundle_loader.rs:62-85`).
- Bundle shape: `CloudConfigBundle { config_toml: { enterprise_managed: Vec<CloudConfigFragment> }, requirements_toml: { enterprise_managed: Vec<CloudRequirementsFragment> } }` (`codex-rs/config/src/cloud_config_bundle.rs:24-62`). Fragments arrive highest-precedence first; config layers are reversed into stack order ("Bundle fragments arrive highest-priority first, while ConfigLayerStack folds lowest-priority to highest-priority.", `codex-rs/config/src/cloud_config_layers.rs:117-120`) and requirements fragments are reversed into merge order (`cloud_config_bundle.rs:128-130`).
- The loader hook is a closure trait object `CloudConfigBundleLoader` injected through `ConfigLoadOptions` (`cloud_config_bundle.rs:178-228`, `state.rs:24-29`); its `Default` returns `Ok(None)` (no cloud config) (`cloud_config_bundle.rs:224-228`), and a bundle-fetch error propagates out of `load_config_layers_state` (`loader/mod.rs:196-210`).

### Provider selection and runtime dispatch (model-provider)

- Core builds the final provider map as `merge_configured_model_providers(built_in_model_providers(openai_base_url), cfg.model_providers)` where `openai_base_url` is the effective `openai_base_url` config value filtered for emptiness (`codex-rs/core/src/config/mod.rs:3624-3631`; `openai_base_url` is a top-level `ConfigToml` field documented as "Base URL override for the built-in `openai` model provider.", `config_toml.rs:376-377`). The provider id is the caller-supplied provider parameter, else the `model_provider` config value, else the literal default `"openai"` (`core/src/config/mod.rs:3633-3635`); an unknown id raises "Model provider `{model_provider_id}` not found" (`core/src/config/mod.rs:3636-3646`).
- The runtime trait is `ModelProvider` (`codex-rs/model-provider/src/provider.rs:130-278`): `info`, `capabilities`, `approval_review_preferred_model`, `auth_manager`, `auth`, `account_state`, `api_provider`, `runtime_base_url`, `api_auth`, `api_auth_for_scope`, `models_manager*`. `create_model_provider` dispatches to `AmazonBedrockModelProvider` when `info.is_amazon_bedrock()` and otherwise to the generic `ConfiguredModelProvider` (`provider.rs:293-303`).

### Auth and credential plumbing

- `auth_provider_from_auth` maps first-party auth snapshots to header providers (`codex-rs/model-provider/src/auth.rs:303-320`): `CodexAuth::AgentIdentity` to `AgentIdentityAuthProvider`, `CodexAuth::Headers` to `HeaderAuthProvider` (predefined header set), `ApiKey`/`Chatgpt`/`ChatgptAuthTokens`/`PersonalAccessToken` to `BearerAuthProvider`; `BedrockApiKey` is `unreachable!` there with the message "Bedrock API key auth is only supported by the Amazon Bedrock model provider" (`auth.rs:26-27`).
- `BearerAuthProvider::add_auth_headers` inserts `Authorization: Bearer {token}`, optionally `ChatGPT-Account-ID`, and `X-OpenAI-Fedramp: true` for FedRAMP accounts (`codex-rs/model-provider/src/bearer_auth_provider.rs:31-47`).
- `resolve_provider_auth` resolution order (`auth.rs:197-219`, `auth.rs:289-301`): provider `env_key` value from the environment (empty values treated as missing, `model-provider-info/src/lib.rs:331-347`), then `experimental_bearer_token`, then unauthenticated when `requires_openai_auth == false` and no command auth, then first-party auth. Custom providers never inherit ambient auth headers (tests `custom_provider_does_not_inherit_ambient_auth_headers`, `auth.rs:476-494`; `custom_provider_does_not_inherit_ambient_bedrock_auth`, `auth.rs:497-509`).
- A provider with command auth (`auth = { command = ... }`) replaces the base auth manager with `AuthManager::external_bearer_only(config)` (`auth.rs:187-195`), and providers without custom auth keep the caller-supplied manager (`auth.rs:191-194`).
- `AuthManagerAuthProvider` pins an expected auth identity so token refreshes are followed but account switches are not: "Request headers always come from the current AuthManager snapshot below." while "Startup auth is only the account-scoped identity anchor." (`auth.rs:126-131`); on mismatch it yields no headers (`auth.rs:148-154`). Behavior pinned by test `auth_manager_provider_follows_refreshes_but_not_account_switches` (`auth.rs:612-672`).
- Agent identity auth emits an `AgentAssertion ` authorization header plus `ChatGPT-Account-ID` and, for FedRAMP accounts, `X-OpenAI-Fedramp: true` (`auth.rs:87-113`, tests `auth.rs:674-734`). When the policy is ChatGPT-based bootstrap and registration fails as `BootstrapUnavailable`, the session falls back once to ChatGPT bearer auth via `AgentIdentitySessionFallback` (`auth.rs:221-287`, tests `auth.rs:736-848`).
- Bedrock auth has its own source ladder (`codex-rs/model-provider/src/amazon_bedrock/auth.rs:49-70`): `CommandBearerToken` (provider `auth`), `ManagedBearerToken` (`CodexAuth::BedrockApiKey` cached in the AuthManager), `EnvBearerToken` (`AWS_BEARER_TOKEN_BEDROCK`), `EnvAwsCredentials` (`AWS_ACCESS_KEY_ID` + `AWS_SECRET_ACCESS_KEY`), else `AwsSdk`. Resolution turns the first three into bearer tokens and otherwise loads an `AwsAuthContext` for SigV4 signing (`amazon_bedrock/auth.rs:72-115`). Bearer-token auth additionally requires a region from `aws.region`, `AWS_REGION`, or `AWS_DEFAULT_REGION` (`amazon_bedrock/auth.rs:139-151`). Refreshable failures recover by re-running the `aws` refresh command, restricted by validation to exactly `aws` (`amazon_bedrock/mod.rs:218-246`, `model-provider-info/src/lib.rs:222-230`); recovery state is shared per configuration via `process_shared_state().aws_auth_recovery(&aws)` (`amazon_bedrock/mod.rs:85-92`).
- Endpoints: Mantle base URL is `https://bedrock-mantle.{region}.api.aws/openai/v1`, restricted to a 12-region allowlist ("us-east-2", "us-east-1", "us-west-2", "ap-southeast-3", "ap-south-1", "ap-northeast-1", "eu-central-1", "eu-west-1", "eu-west-2", "eu-south-1", "eu-north-1", "sa-east-1"), unsupported regions failing with "Amazon Bedrock Mantle does not support region `{region}`" (`amazon_bedrock/mantle.rs:10-24`, `mantle.rs:43-55`); the Runtime endpoint has the shape `https://bedrock-runtime.{region}.amazonaws.com/openai/v1` (observed in test `runtime_managed_auth_resolves_runtime_endpoint`, `amazon_bedrock/mod.rs:504-524`). An explicit provider `base_url` always wins over derived endpoints (`amazon_bedrock/mod.rs:141-155`).
- Which login UI users see is provider data: `requires_openai_auth = true` shows the login screen on first run and stores the result in `auth.json`; `false` skips login and expects `env_key` (`model-provider-info/src/lib.rs:138-143`, docs at `lib.rs:138-141`). Storage backend choice is config: `cli_auth_credentials_store` with values file/keyring/auto (`codex-rs/config/src/config_toml.rs:252-257`) and `mcp_oauth_credentials_store` with values keyring/file/auto (`config_toml.rs:265-271`); the file implementations live in `codex-login`, outside this component.

### Model catalog management (models-manager)

- `ModelsManager` trait owns refresh policy, cache behavior, and catalog merging; it calls a provider-owned `ModelsEndpointClient` only when it decides to refresh (`codex-rs/models-manager/src/manager.rs:32-50`, `manager.rs:84-209`). `RefreshStrategy`: `Online` (always fetch), `Offline` (cache only), `OnlineIfUncached` (cache then fetch) (`manager.rs:54-63`).
- Three implementations: `OpenAiModelsManager` (bundled models + file cache + remote `/models`), `StaticModelsManager` (authoritative in-process catalog, used for static catalogs and hosted callers whose default "uses an authoritative in-memory catalog so hosted callers cannot accidentally write to disk", `codex-rs/model-provider/src/provider.rs:252-262`), and the endpoint client `OpenAiModelsEndpoint` (`manager.rs:216-231`, `codex-rs/model-provider/src/models_endpoint.rs:41-124`).
- The bundled catalog ships as `models.json` loaded via `include_str!("../models.json")` (`codex-rs/models-manager/src/lib.rs:12-16`); slugs in the pinned tree include `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-5.5`, `gpt-5.4`, `gpt-5.4-mini`, `gpt-5.2`, `codex-auto-review` (`codex-rs/models-manager/models.json:4,118,230,338,444,548,647,743`).
- Remote refresh: `OpenAiModelsManager` fetches only when `should_refresh_models()` holds, i.e. auth uses the Codex backend or the provider has command auth (`manager.rs:437-439`); fetches go through the provider's `/models` endpoint (`MODELS_ENDPOINT = "/models"`) with a 5-second timeout (`MODELS_REFRESH_TIMEOUT`, `models_endpoint.rs:38-39`). Successful fetches update memory, ETag, and the cache entry (`manager.rs:412-435`).
- Merge with bundled models (`apply_remote_models`, `manager.rs:446-475`): the remote list replaces bundled entirely only when it has at least one `visibility == List` model and auth is ChatGPT-account-backed; otherwise remote entries overwrite matching slugs and append the rest.
- Disk cache: file `models_cache.json` in `codex_home` (`manager.rs:29`, `manager.rs:240-244`), TTL 300 seconds (`manager.rs:30`); cache entries must match the whole client version (`manager.rs:484-506`). A TODO acknowledges the cache is not provider-scoped: "Include provider identity in cache eligibility so switching providers does not reuse a fresh models_cache.json entry from another provider." (`manager.rs:486-487`).
- Model metadata lookup (`construct_model_info_from_candidates`, `manager.rs:654-673`): longest-prefix match against the catalog, then a narrowly scoped retry for one-segment namespaced slugs like `custom/gpt-5.3-codex` (`manager.rs:617-652`), else the fallback descriptor `model_info_from_slug`, which warns "Unknown model {slug} is used. This will use fallback model metadata." and supplies `context_window: Some(272_000)`, `max_context_window: Some(272_000)`, byte truncation 10000, `used_fallback_model_metadata: true` (`codex-rs/models-manager/src/model_info.rs:139-186`; BASE_INSTRUCTIONS text is `prompt.md` included at `model_info.rs:17`).
- Config overrides on resolved metadata (`with_config_overrides`, `model_info.rs:25-101`; input struct `ModelsManagerConfig`, `codex-rs/models-manager/src/config.rs:5-13`): `model_context_window` is capped by `max_context_window`, `model_auto_compact_token_limit` applies directly, `tool_output_token_limit` maps to the truncation policy (bytes or tokens per the model's mode), and `base_instructions` replaces the instructions template (the config field's docs warn users are "STRONGLY DISCOURAGED", `config_toml.rs:235-239`).
- Default model selection: an explicitly configured `model` is kept as-is by `OpenAiModelsManager::get_default_model` (`manager.rs:159-183`); `StaticModelsManager` may substitute the provider default when `allow_provider_model_fallback` is set and the requested model is unavailable (`manager.rs:519-554`); otherwise the default is the first preset marked `is_default`, else the first available (`manager.rs:597-604`). Presets are sorted by `priority` and filtered by auth visibility (`manager.rs:126-138`).

## Limitations and unknowns

- Login machinery is out of scope by component boundary: `AuthManager`, `CodexAuth`, `auth.json` file store, keyring backends, and OAuth flows live in `codex-login`, which is not in this component. I describe credential storage only at the config-key level (`cli_auth_credentials_store`, `mcp_oauth_credentials_store`), and `CodexAuth` variants only as consumed by the provider layer. The docs comment says credentials "are stored in auth.json" (`codex-rs/model-provider-info/src/lib.rs:138-141`), but the write/read code is unverified here.
- Internal source inconsistency: the `load_config_layers_state` doc comment's layer order ("package, admin, system, cloud, user, profile, cwd, tree, repo, runtime", `codex-rs/config/src/loader/mod.rs:105-117`) conflicts with the loader README and the code's push order regarding where legacy managed config and MDM sit (top, per `codex-rs/config/src/loader/README.md:26-36` and `codex-rs/config/src/loader/mod.rs:447-487`). I trust README + code; a reader citing the doc comment would reach a different conclusion.
- Runtime behavior that cannot be observed statically and was not run (brief forbids live API runs): actual enterprise cloud bundle contents and ordering, keyring availability effects of `cli_auth_credentials_store = "auto"`, real SigV4 signing behavior, and whether the remote `/models` catalog diverges from the bundled `models.json`.
- The models cache is known by its own TODO to be shared across providers (`codex-rs/models-manager/src/manager.rs:486-487`); behavior when switching providers within the TTL window is stale-by-design.
- Bedrock Runtime region/endpoint derivation was verified through the provider test (`codex-rs/model-provider/src/amazon_bedrock/mod.rs:504-524`) rather than a full read of `amazon_bedrock/runtime.rs`; the exact supported-region list for the Runtime endpoint is not extracted here (only the 12-region Mantle list at `amazon_bedrock/mantle.rs:11-24`).
- The cloud bundle HMAC key is a fixed string embedded in the binary (`codex-rs/cloud-config/src/cache.rs:26-29`); (interpretation) this protects against accidental corruption, not against a local attacker with write access to `$CODEX_HOME`, since the key is public in the source.
- `codex-rs/config/examples/` turned out to hold only `generate-proto.rs`; the registry entry's mention of `examples/` does not correspond to documented sample configs at this commit.
- `thread_config` layers (per-thread remote config, e.g. model selector in UI) are inserted by translated precedence (`codex-rs/config/src/loader/mod.rs:438-440`), but the remote thread-config loader implementation belongs to the interfaces/state dimensions, so I did not trace it here.

## Relevance to the brief

My own inference, separated from the code facts above.

- RQ1/RQ2 (config dimension of the harness comparison): Codex's configuration is the most stratified of the three systems I have seen so far in this study. Ten distinct layer provenances with numeric precedence, a separate admin-enforced "requirements" stack that constrains rather than sets values, MDM support on macOS, and a plan-gated enterprise cloud bundle with signed local caching (`codex-rs/config/src/config_layer_source.rs:6-51`; `codex-rs/config/src/state.rs:246-259`; `codex-rs/cloud-config/src/service.rs:48-56`) is materially more elaborate than OpenCode's file-based config (to be grounded in the `opencodeConfigProviders` note) and than anything verifiable for Claude Code's closed core. The comparison matrix cell "config precedence" should record this structural gap explicitly.
- RQ2 (provider abstraction): the provider is a declarative record (`ModelProviderInfo`) plus a runtime trait (`ModelProvider`) with exactly two implementation families (`ConfiguredModelProvider`, `AmazonBedrockModelProvider`, `codex-rs/model-provider/src/provider.rs:293-303`). - RQ3 (capability vs safety): two mechanisms here are directly safety-relevant. Second, trust gating disables project config, hooks, and exec policy layers until the user trusts the project (`loader/mod.rs:1056-1074`). Both couple configuration to the permissions dimension covered by `codexSandboxPermissions`; synthesis should cross-reference them.
- What this leaves open: how `Config::load` in `codex-rs/core/src/config/mod.rs` applies the requirements constraints to runtime decisions (approvals, sandbox mode enforcement) belongs to the permissions note; how the TUI surfaces layers/origins belongs to the interfaces note (`codexInterfaces`, status to-read); and the OpenCode/Claude Code side of every comparison row awaits those notes.
