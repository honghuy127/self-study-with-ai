## Problem and motivation

The article addresses a labeling problem: every Claude Code extension feature gets described as "instructions for the agent," which "is too broad to be useful," because a `CLAUDE.md` file, an output style, a skill, a hook, a subagent, a plugin, and an MCP server "all change what happens in a Claude Code session, but they do it at different points in the harness" (opening paragraphs, L3). Its stated purpose is to separate the layers: "This article separates official documentation, first-party Agiflow traces, third-party analysis, community claims, and practical inference so the implementation facts do not blur together" (opening paragraphs, L4). The practical thesis: "use the smallest layer that owns the job" (opening paragraphs, L5). A debugging motivation is also given: when behavior is wrong, the fix depends on which layer caused it, "a project memory file, an output style left on from yesterday, a skill that loaded automatically, a hook that changed the tool path, a subagent with its own context, or an MCP server schema" (opening paragraphs, L7). The article is also a content-marketing piece for Agiflow's MCP-connected project-state product (Section "Where Agiflow fits", L147-L160; page meta keywords, L1), see Limitations.

## Method or core idea

The article combines three methods:

1. First-party network-trace analysis. "The original October 2025 post was built from instrumented Claude Code network traffic. That trace work is still the article's first-party value." (Section "Claude Code Internals: What changed since the original analysis", L9). The traces were published at `AgiFlow/claude-code-prompt-analysis` (Section "Network trace notes and version boundaries", L67, ref [20]). The article bounds their authority itself: "Keep reading those traces as observed behavior, not as a stable Anthropic API contract." (L67).
2. A refreshed mapping against official documentation. The July 2026 refresh "keeps the original network-trace analysis, but updates the mental model for current Claude Code docs" (blockquote "Updated July 2026", L2). Official and spec sources are cited as captured 2026-07-04 (Section "The confidence model for this article", L12-L13; Section "References", L167-L218). The refresh registers five corrections: custom commands merged into skills, hooks covering more lifecycle events, subagent context behavior having important exceptions, plugins entering the extension story, and MCP needing a clearer security and state boundary (blockquote, L2). The correction table's first row is fully visible: the older model "Slash commands and skills are separate categories" is corrected to "Claude Code skills docs now say custom commands are merged into skills," with `.claude/commands/` files still working and `.claude/skills/<name>/SKILL.md` also creating slash invocation, refs [5][6] (same section, L10).
3. An explicit confidence model. "I use five source labels throughout the rest of the post" (Section "The confidence model for this article", L12). Two label rows are fully visible: "Official" means "Current Claude Code or MCP documentation captured on July 4, 2026," readable as "Highest confidence for supported behavior"; "Observed" means "Agiflow network traces from the public prompt-analysis repository," readable as "High confidence for that trace set, medium confidence for current internals" (L13). The remaining labels are visible through the per-reference tags in the References section: Official, Spec, First-party trace, Official changelog, Third-party analysis, Community claim, Community listening (L167-L218).

The harness model the article asserts: "Claude Code is an agentic coding tool that can read code, edit files, run commands, and integrate with development tools across terminal, IDE, desktop app, and browser surfaces [1]. The extension system sits around that agent loop. Each mechanism changes a different part of the run." (Section "The extension layer map", L16). The extension layer map table (L17) characterizes each mechanism by Source confidence, Trigger, Control point, and Best use; the updated decision matrix (Section "Updated decision matrix", L64) adds Determinism, Context cost, Security posture, and Failure mode. The article's "Quick answer" summarizes the assembly: "`CLAUDE.md` contributes persistent project and user context, output styles adjust response behavior through the system-prompt layer, skills and slash invocation add reusable procedures when invoked manually or when Claude decides they are relevant, hooks run at lifecycle events and can enforce deterministic policy, subagents delegate work into separate context windows, plugins package shareable extension sets, and MCP connects Claude Code to external tools, resources, prompts, and durable systems." (opening paragraphs, L4).

## Key claims with anchors

Organized by the article's own source labels. Everything below is the blog's assertion; "Official" and "Spec" items are the blog's secondhand reports of cited documentation, not documentation this note read directly (except where cross-verified, see Evaluation and evidence).

First-party trace observations ("Observed", refs [20]):

- Claim T1 (Section "Observed: CLAUDE.md appeared in message-level context", L70-L83): in the trace set, project memory arrived as a `role: "user"` message whose text content was wrapped in a `<system-reminder>` tag: `"text": "<system-reminder>... Contents of /path/to/CLAUDE.md ...</system-reminder>"`. The article states this "historical observation lines up with current memory docs saying `CLAUDE.md` is delivered as user-message context after the system prompt [2][20]" (L83).
- Claim T2 (Section "Observed: output styles changed the system-prompt layer", L84-L92; also L24): the trace set showed the API `system` field as an array of two text blocks, `{ "type": "text", "text": "You are Claude Code..." }` and `{ "type": "text", "text": "# Output Style: software-architect\n..." }`, with empty `messages`, i.e. "output style content appeared as an additional system-prompt block [20]" (L24).
- Claim T3 (Section "Observed: skills used a tool-call flow", L93-L104): skill use appeared as an assistant `tool_use` block, `"name": "Skill"`, `"input": { "command": "example-skill" }`.
- Claim T4 (Section "Observed: subagents delegated into separate conversations", L105-L119; also L50): subagent delegation appeared as an assistant `tool_use` block, `"name": "Task"`, `"input": { "subagent_type": "Explore", "prompt": "Analyze auth flows..." }`; "The original trace set showed subagent delegation as a separate conversation, which remains the useful architectural point [20]" (L50).
- Claim T5 (Section "Network trace notes and version boundaries", L67-L68): the trace value is "the difference between context added to message arrays, output-style behavior added around the system prompt, skill use through tool calls, and subagent delegation as a separate conversation," which "explains why two mechanisms that feel similar in the UI can have different cost, latency, and debugging properties" (L68).

Official-documentation content as reported by the article (refs [1]-[19], captured 2026-07-04):

- Claim O1 (Section "The extension layer map", L16, ref [1]): Claude Code spans "terminal, IDE, desktop app, and browser surfaces."
- Claim O2 (same section, L18, ref [2]): memory docs describe `CLAUDE.md` as persistent instructions with "managed, user, project, and local memory" scopes; "Subdirectory `CLAUDE.md` files can load lazily when Claude reads files in those directories."
- Claim O3 (same section, L19, ref [2]): "The memory docs say `CLAUDE.md` content is delivered as a user message after the system prompt, not as the system prompt itself."
- Claim O4 (Section "Output styles change how Claude responds", L23, ref [4]): "Output styles change how Claude responds rather than what it knows, and they modify system-prompt behavior to set role, tone, and output format."
- Claim O5 (Section "Skills and slash invocation are now a merged mental model", L27, refs [5][6]): skills "use a `SKILL.md` file, can be invoked directly with `/skill-name`, can be used automatically when relevant, and load their body only when used"; "custom commands have been merged into skills"; "A legacy `.claude/commands/deploy.md` file and a `.claude/skills/deploy/SKILL.md` file can both create `/deploy`, while existing `.claude/commands/` files keep working."
- Claim O6 (same section, L28, refs [5][7]): "skills are folders with metadata, instructions, supporting files, invocation controls, and progressive disclosure."
- Claim O7 (Section "Hooks are lifecycle policy, not polite suggestions", L37, refs [8][9]): "Hooks are user-defined commands at Claude Code lifecycle points. They provide deterministic control for rules, automation, and tool integration." Current events "include `SessionStart`, `UserPromptSubmit`, `UserPromptExpansion`, `PreToolUse`, `PostToolUse`, `PostToolBatch`, `SubagentStart`, `SubagentStop`, `InstructionsLoaded`, `ConfigChange`, and more."
- Claim O8 (same section, L38, ref [9]): "A `PreToolUse` hook can block tool execution"; "Hook handlers can also be command, HTTP, MCP tool, prompt, or agent hooks, with MCP tool hooks depending on connected MCP servers."
- Claim O9 (Section "Skills and slash invocation are now a merged mental model", L35, ref [10]): "`UserPromptExpansion` covers direct slash command or skill paths that bypass `PreToolUse` on the Skill tool, and... this hook can block expansion or add context."
- Claim O10 (Section "Subagents are separate work contexts with exceptions", L49, refs [11][13]): "Subagents are specialized assistants with their own context window, custom system prompt, tool access, and independent permissions"; "The main conversation is still better for quick changes, latency-sensitive work, and tasks that need frequent back-and-forth."
- Claim O11 (same section, L50, ref [12]): "Built-in Explore and Plan skip `CLAUDE.md` files and parent-session git status, while every other built-in and custom subagent loads both."
- Claim O12 (Section "Plugins package capabilities for sharing", L54, refs [14][15]): "plugins as bundles for feature sets, including skills, hooks, subagents, and MCP servers"; "The settings docs also place project settings in the team-shared layer for permissions, hooks, MCP servers, and plugins."
- Claim O13 (Section "MCP is the external tool and state boundary", L58-L59, refs [17][18]): "MCP standardizes JSON-RPC communication between hosts, clients, and servers. Servers can expose resources, prompts, and tools; clients can expose capabilities such as sampling, roots, and elicitation"; the MCP spec "names security principles around user consent, data privacy, tool safety, and the fact that tool descriptions from untrusted servers should not automatically be trusted." Spec revision cited: 2025-11-25 (References, L197-L200).

Community claims relayed with the article's own warning labels:

- Claim C1 (Section "Plugins package capabilities for sharing", L56, ref [23]): a community GitHub issue "has alleged namespace impersonation risk around skill paths that look official"; the article says to "treat that as a community security claim, not a confirmed Anthropic finding, but the review habit is still sound."
- Claim C2 (Section "Security and context cost trade-offs", L125, refs [24]-[27]): "Practitioners ask whether hooks, skills, slash commands, subagents, plugins, and MCP are overlapping features or distinct control points."

Author interpretation and advice (the article's own reasoning, not implementation facts):

- Interpretation I1 (opening paragraphs, L5; figure captions L15, L63; Section "Start with the smallest owner of the job", L128): the placement rule "use the smallest layer that owns the job," sequenced as plain prompt, then slash-invoked skill, then automatic skill, then hook (L128).
- Interpretation I2 (Section "The extension layer map", L21): "That is a useful bright line: `CLAUDE.md` guides. Hooks execute.", the author's distillation of the memory docs' hooks recommendation [3].
- Interpretation I3 (Section "Hooks are lifecycle policy, not polite suggestions", L47): "Do not overstate hooks as a complete security boundary. They can enforce rules inside the Claude Code lifecycle, but the surrounding environment still matters: trusted hook code, permissions, shell behavior, configured tools, and what the user can override."
- Interpretation I4 (Section "Security and context cost trade-offs", L121-L124): a two-cost model. "Context cost is the amount of instruction, schema, memory, or intermediate result the model has to carry" and "Control cost is how hard it is to guarantee behavior." Applied: "do not pay persistent context cost for a rule that only matters at one lifecycle event, and do not ask the model to remember a policy that a hook can enforce" (L124). The article borrows a third-party preprint's framing of MCP, plugins, skills, and hooks "as different context-cost tiers [22]" while hedging: "I find that framing directionally useful, but I would not treat it as official Anthropic doctrine" (L124).
- Interpretation I5 (Section "Start with the smallest owner of the job", L129): the failure mode of "extension sprawl," "where every workflow has a `CLAUDE.md` rule, a skill, a hook, a subagent, and an MCP tool all trying to own the same behavior."
- Interpretation I6 (Section "Use hooks when behavior must not depend on the model", L134-L140): "If a behavior is a preference, put it in memory or style. If it is a policy, put it in a hook or external enforcement layer", with examples including compliance context injection at `UserPromptExpansion` (L140).
- Interpretation I7 (Section "Use subagents for context isolation, not as a decoration", L143): delegation prompts should read "as a handoff contract: goal, scope, allowed tools, required evidence, and output shape."
- Interpretation I8 (Section "Where Agiflow fits", L147-L160; Section "Final mental model", L165): "Claude Code can shape one run. It does not, by itself, give a team a durable system of record..." (L145); durable state should move to MCP-connected external systems, which the article identifies with Agiflow's product ("durable project context for AI-assisted work, exposed to agents through MCP-native and CLI-accessible workflows", L158). This section is a product pitch; see Limitations.
- Interpretation I9 (Section "Final mental model", L163): the ownership summary: "`CLAUDE.md` owns stable context. Output styles own response behavior. Skills own reusable procedures. Slash invocation owns explicit user-triggered workflows. Hooks own deterministic lifecycle policy. Subagents own isolated work. Plugins own distribution. MCP owns external tools, resources, prompts, and durable system boundaries."

## Limitations

- Unverifiable third-party teardown. This is reverse engineering by an outside party with no access to Anthropic's source. Per the study's sourcing constraints, it can only support hedged, contextual statements about the closed Claude Code core; it cannot carry any strong claim in the report. Every trace observation is an assertion by the author about captures this study cannot inspect.
- Traces are author-curated excerpts. All four payloads are truncated with literal `...` inside string values (L77, L88, L100, L114), and the underlying repository `AgiFlow/claude-code-prompt-analysis` [20] is not included in this study's snapshots, so the raw captures, their completeness, and their selection cannot be checked.
- No version pin on observations. The traces come from October 2025 instrumentation; the article itself instructs readers to treat them as "observed behavior, not as a stable Anthropic API contract" (L67). Observed payload shapes may already differ from current releases, and the article applies the "current supported claim is narrower" correction to its own older observations (L24, L104).
- Secondhand official content. References [1]-[19] are citations of Anthropic docs and the MCP spec captured 2026-07-04, quoted or paraphrased by the blog, not reproduced. This study holds its own snapshots for the memory, hooks, subagents, plugins, and MCP doc areas (used for cross-verification above), but not for the output-styles, settings, skills, or features-overview pages, so claims O1, O4, O5, O6, and O12's settings portion rest on the blog's citation alone here.
- Commercial conflict of interest. The page's meta keywords are product marketing ("AI project board, AI project management...", L1), and the closing sections pitch Agiflow's MCP-connected state product (L147-L160, L165). The article's normative thrust, especially "move durable state outside the harness when the work has to survive beyond one run" (L165), terminates at the vendor's own offering. Its descriptive content is usable; its prescriptive arc should be read as motivated.
- Speculation marked as such by the author. The context-cost-tier framing is borrowed from a third-party preprint [22] the author explicitly declines to treat "as official Anthropic doctrine" (L124); the namespace-impersonation risk [23] is explicitly "a community security claim, not a confirmed Anthropic finding" (L56); the community-confusion evidence [24]-[27] is anecdotal forum listening (L125).
- Reading gaps in this snapshot extraction. The following table cells exceed the per-line read limit and are not quoted in this note: the "what changed" table beyond its first row (L10), the confidence table beyond "Official" and "Observed" (L13), the extension layer map rows after the `CLAUDE.md` row (L17), the decision-matrix cells beyond the `CLAUDE.md` trigger cell (L64), and the jobs-to-mechanism rows after the first three (L65). No claim in this note depends on those cells.
- Scope gaps relative to the brief. The article covers extension layers and context injection only. It says nothing about the turn loop, context compaction, session or rollout persistence, or permissions and sandboxing machinery, except hooks; it provides no evidence for those dimensions of Claude Code.

## Relevance to the brief

My inference, separated from the article's claims:

- RQ4 (closed core through teardowns): this is one of the study's three blog-tier windows on the closed core, and its distinctive contribution is the four trace payload shapes (Claims T1-T4). Even hedged, they give the report a concrete, citable-as-teardown picture of Claude Code's context assembly: the system prompt is an array of text blocks (T2), memory files enter the message stream after the system prompt as `<system-reminder>`-wrapped user content (T1, and corroborated by official docs, see Evaluation), skills execute through a `Skill` tool call (T3), and subagents spawn through a `Task` tool call into separate conversations (T4). Only the memory-delivery shape is doc-corroborated; the other three remain blog-attested observations.
- RQ2 (harness components): the article supplies a clean enumeration of Claude Code's extension machinery, `CLAUDE.md` memory, output styles, skills (with commands merged in), hooks, subagents, plugins, MCP, organized by control point (where each mechanism intercepts a run: system prompt, message stream, tool invocation, lifecycle event, protocol boundary). The control-point framing is directly usable vocabulary for the report's harness-component taxonomy, attributed to the teardown.
- RQ3 (capability versus safety): the article's control-cost gradient (memory and styles advise; hooks enforce deterministically and can block tool execution; MCP requires consent and distrust of untrusted tool descriptions, L123, L59) maps onto the brief's safety question, and two specifics are worth carrying with hedges: the `UserPromptExpansion` gate on slash/skill expansion paths (O9, partially corroborated here) and the explicit warning that hooks are "not a complete security boundary" (I3).
- RQ1 (genuine differences): candidate divergence points to verify against the primary codebase and docs notes, not to assert from this blog: Claude Code merges slash commands into skills; built-in subagents are asymmetric about context loading (Explore and Plan skip CLAUDE.md and git status); hooks expose a wider lifecycle surface than the event lists this study recorded for Codex and OpenCode. Each must be checked against the corresponding primary notes before entering the comparison matrix.
- Gate flag for `depth: full`: this source cannot fill any closed-core comparison-matrix cell on its own because the brief restricts blog-tier teardowns to hedged contextual claims. Where the matrix has Claude Code cells, the admissible evidence is the official docs notes and the plugin-surface note; this note contributes only corroborating context, and the uncorroborated items above (output styles, skills mechanics, trace payload shapes) stay gap-marked unless another source picks them up. The two `[CITATION NEEDED]` items (trace versioning, original post content) are source-level gaps but do not block a literature gate verdict, since the gate can rest on the primary tier.
