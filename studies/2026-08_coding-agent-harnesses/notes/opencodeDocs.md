## Problem and motivation

- OpenCode positions itself as "an open source AI coding agent. It's available as a terminal-based interface, desktop app, or IDE extension." (`packages/web/src/content/docs/index.mdx`, opening paragraph, line 10)
- The docs are organized around configuring and extending that agent: providers and models (`providers.mdx`), project rules via `AGENTS.md` (`rules.mdx`, "You can provide custom instructions to opencode by creating an `AGENTS.md` file. This is similar to Cursor's rules.", line 6), agents and modes (`agents.mdx`), tools (`tools.mdx`), permissions (`permissions.mdx`), and extensibility through MCP, plugins, custom tools, skills, and commands (`mcp-servers.mdx`, `plugins.mdx`, `custom-tools.mdx`, `skills.mdx`, `commands.mdx`).
- The docs also cover collaboration and integration surfaces: session sharing (`share.mdx`), editor integration via ACP (`acp.mdx`), and a headless HTTP server plus JS/TS SDK (`server.mdx`, `sdk.mdx`).

## Method or core idea

(The harness machinery as documented. All claims below are doc statements at the pinned commit.)

### Agentic model: primary agents, subagents, hidden system agents

- Two agent types: "primary agents and subagents" (`agents.mdx`, § "Types", line 18). Primary agents handle the main conversation and are cycled with the Tab key or `switch_agent` keybind; tool access is configured via permissions, "for example, Build has all tools enabled while Plan is restricted" (§ "Primary agents", line 24).
- Built-ins: two primary agents, **Build** ("the **default** primary agent with all tools enabled", § "Use build", line 53) and **Plan** ("A restricted agent designed for planning and analysis" with `file edits` and `bash` "set to `ask`" by default, § "Use plan", lines 61-66); three subagents, **General** ("full tool access (except todo)... Use this to run multiple units of work in parallel", § "Use general", line 75), **Explore** ("A fast, read-only agent for exploring codebases. Cannot modify files.", § "Use explore", line 83), and **Scout** ("A read-only agent for external docs and dependency research", § "Use scout", line 91).
- Three hidden system agents, all `mode: primary`: **compaction** ("Hidden system agent that compacts long context into a smaller summary. It runs automatically when needed and is not selectable in the UI.", § "Use compaction", line 99), **title** ("generates short session titles", § "Use title", line 107), **summary** ("creates session summaries", § "Use summary", line 115).
- Subagents are invoked automatically by primary agents "based on their descriptions" or manually by `@` mention; subagents create child sessions navigable via `session_child_first` (default `<Leader>+Down`), `session_child_cycle` (Right), `session_child_cycle_reverse` (Left), `session_parent` (Up) (§ "Usage", lines 121-136).
- Agent definition: JSON under the `agent` key of `opencode.json`, or markdown files in `~/.config/opencode/agents/` (global) or `.opencode/agents/` (project), where "The markdown file name becomes the agent name" (§ "Configure" and § "Markdown", lines 190-216).
- Agent options: `description` (marked "required", § "Description", line 240); `temperature` (default "typically 0 for most models, 0.55 for Qwen models", § "Temperature", line 287); `steps` ("the maximum number of agentic iterations an agent can perform before being forced to respond with text only"; when reached "the agent receives a special system prompt instructing it to respond with a summarization of its work and recommended remaining tasks"; legacy `maxSteps` deprecated, § "Max steps", lines 291-313); `disable`; `prompt` (`{file:...}` supported, relative to the config file, § "Prompt", line 347); `model` ("subagents will use the model of the primary agent that invoked the subagent" unless overridden, § "Model", line 356); `tools` (deprecated in favor of `permission`, § "Tools (deprecated)", line 375); `permission` per agent; `mode` (`primary`, `subagent`, or `all`, default `all`, § "Mode", line 574); `hidden` (hides subagent from `@` autocomplete but "Hidden agents can still be invoked by the model via the Task tool if permissions allow", § "Hidden", lines 580-593); `permission.task` glob patterns controlling which subagents the Task tool may invoke, with "the **last matching rule wins**" and denied subagents "removed from the Task tool description entirely" (§ "Task permissions", lines 601-626); `top_p`; and any additional keys "passed through directly to the provider as model options" (e.g. `reasoningEffort: "high"` for `openai/gpt-5`, § "Additional", lines 673-696).
- `opencode agent create` interactively generates a markdown agent file (§ "Create agents", lines 700-714).
- Global config also exposes `default_agent` (must be a primary agent; fallback to `"build"` with a warning; applies across all interfaces) and `subagent_depth` ("The default is `1`, which allows primary agents to launch subagents but prevents those subagents from launching additional subagents"; `0` prevents all subagent launches) (`config.mdx`, § "Default agent" lines 530-543, § "Subagent depth" lines 547-558).

### Tools

- "By default, all tools are **enabled** and don't need permission to run." (`tools.mdx`, line 8)
- Built-in tools documented: `bash` (executes shell commands, § "bash"), `edit` ("Modify existing files using exact string replacements... It's the primary way the LLM modifies code.", § "edit", line 78), `write` (controlled by the `edit` permission, § "write", lines 97-99), `read` ("supports reading specific line ranges", § "read"), `grep` (§ "grep"), `glob` ("sorted by modification time", § "glob"), `apply_patch`, `skill` (loads a `SKILL.md` into the conversation, § "skill"), `todowrite` ("This tool is disabled for subagents by default", § "todowrite", line 233), `webfetch`, `websearch`, `question` (interactive questions with options; users "can select from the provided options or type a custom answer", § "question"), and experimental `lsp` (§ "Tools" sections, `tools.mdx`).
- `lsp` tool: "only available when `OPENCODE_EXPERIMENTAL_LSP_TOOL=true` (or `OPENCODE_EXPERIMENTAL=true`)"; operations include `goToDefinition`, `findReferences`, `hover`, `documentSymbol`, `workspaceSymbol`, `goToImplementation`, `prepareCallHierarchy`, `incomingCalls`, `outgoingCalls` (`tools.mdx`, § "lsp (experimental)", lines 154-173).
- `websearch`: "only available when using the OpenCode or OpenCode Go provider, or when the `OPENCODE_ENABLE_EXA` environment variable is set to any truthy value"; it "Performs web searches using Exa AI" and "connects directly to Exa AI's hosted MCP service without authentication" (`tools.mdx`, § "websearch", lines 259-281).
- `apply_patch` hook details: hooks should check `input.tool === "apply_patch"` (not `"patch"`); input uses `output.args.patchText`, with paths embedded in marker lines such as `*** Add File: src/new-file.ts`, `*** Update File: src/existing.ts`, `*** Move to: src/renamed.ts`, `*** Delete File: src/obsolete.ts` (`tools.mdx`, § "apply_patch", lines 192-194).
- Implementation note: "tools like `grep` and `glob` use [ripgrep] under the hood" and respect `.gitignore`; a root `.ignore` file with `!path` entries re-includes paths (`tools.mdx`, § "Internals" and § "Ignore patterns", lines 329-345).
- Custom tools: TS/JS files in `.opencode/tools/` (project) or `~/.config/opencode/tools/` (global); "The **filename** becomes the **tool name**"; multiple exports become `<filename>_<exportname>`; args defined with Zod (`tool.schema`); a custom tool with a built-in name "takes precedence" (can replace built-in `bash`); execute context exposes `agent`, `sessionID`, `messageID`, `directory`, `worktree` (`custom-tools.mdx`, § "Location" lines 18-21, § "Structure" lines 27-44, § "Multiple tools per file" lines 48-78, § "Name collisions with built-in tools" lines 82-100, § "Context" lines 137-156).

### Rules / AGENTS.md

- `AGENTS.md` content "will be included in the LLM's context to customize its behavior" (`rules.mdx`, line 6). `/init` "scans the important files in your repo, may ask a couple of targeted questions when the codebase cannot answer them, and then creates or updates `AGENTS.md`" covering build/lint/test commands, architecture, conventions, and references to existing instruction sources (`rules.mdx`, § "Initialize", lines 18-28).
- Locations: project `AGENTS.md` in the project root; global `~/.config/opencode/AGENTS.md` (§ "Types", lines 67-75).
- Claude Code compatibility: uses `CLAUDE.md` in the project "if no `AGENTS.md` exists", `~/.claude/CLAUDE.md` as global fallback, and reads skills from `~/.claude/skills/`; disable via `OPENCODE_DISABLE_CLAUDE_CODE=1`, `OPENCODE_DISABLE_CLAUDE_CODE_PROMPT=1`, or `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS=1` (`rules.mdx`, § "Claude Code Compatibility", lines 77-91).
- Precedence: (1) local files by traversing up from the current directory (`AGENTS.md`, `CLAUDE.md`); (2) global file; (3) Claude Code global file. "The first matching file wins in each category." (`rules.mdx`, § "Precedence", lines 97-103).
- `instructions` config accepts paths, globs, and remote URLs; "Remote instructions are fetched with a 5 second timeout"; all instruction files are combined with `AGENTS.md` files (`rules.mdx`, § "Custom Instructions", lines 107-131; also `config.mdx` § "Instructions", lines 814-826).
- "opencode doesn't automatically parse file references in `AGENTS.md`"; the recommended alternatives are the `instructions` field or teaching the agent to lazy-load references itself (`rules.mdx`, § "Referencing External Files", lines 135-184).

### Permissions

- Model: "OpenCode uses the `permission` config to decide whether a given action should run automatically, prompt you, or be blocked." Actions resolve to `"allow"`, `"ask"`, or `"deny"` (`permissions.mdx`, lines 6-18). "As of `v1.1.1`, the legacy `tools` boolean config is deprecated and has been merged into `permission`.", kept for backwards compatibility (line 8).
- Auto mode: `opencode --auto` and `opencode run --auto` "automatically approve permission requests that are not explicitly denied"; "Explicit `\"deny\"` rules are still enforced." (`permissions.mdx`, § "Auto mode", lines 22-38).
- Configuration: global `"*"` key plus per-permission overrides; all permissions can be set with a single string (`permissions.mdx`, § "Configuration", lines 42-64). Granular object rules map patterns to actions, "with the **last matching rule winning**"; wildcards: `*` zero or more characters, `?` exactly one character (§ "Granular Rules (Object Syntax)" and § "Wildcards", lines 68-99). `~`/`$HOME` expansion in patterns (§ "Home Directory Expansion", lines 101-107).
- `external_directory`: gates any tool touching paths outside the working directory where OpenCode started; "Any directory allowed here inherits the same defaults as the current workspace", so reads are allowed unless overridden (§ "External Directories", lines 109-144).
- Permission keys: `read`, `edit` ("all file modifications (covers `edit`, `write`, `patch`)"), `glob`, `grep`, `bash` ("matches parsed commands like `git status --porcelain`"), `task` ("matches the subagent type"), `skill`, `lsp` ("currently non-granular"), `question`, `webfetch`, `websearch`, `external_directory`, and `doom_loop` ("triggered when the same tool call repeats 3 times with identical input") (`permissions.mdx`, § "Available Permissions", lines 148-164).
- Defaults: "Most permissions default to `\"allow\"`."; "`doom_loop` and `external_directory` default to `\"ask\"`."; `read` allows all but denies `.env` files by default (`*.env: deny`, `*.env.*: deny`, `*.env.example: allow`) (`permissions.mdx`, § "Defaults", lines 168-187).
- Ask flow outcomes: `once`, `always` ("approve future requests matching the suggested patterns (for the rest of the current OpenCode session)"), `reject`; the suggested patterns are provided by the tool ("bash approvals typically whitelist a safe command prefix like `git status*`") (`permissions.mdx`, § "What \"Ask\" Does", lines 191-199).
- Agent permissions are merged with the global config, "and agent rules take precedence" (`permissions.mdx`, § "Agents", line 205; see also `agents.mdx` § "Permissions", lines 422-556, including bash glob rules and `*` precedence examples).

### Policies (experimental)

- Separate layer from permissions: "Permissions control what tools can do during a session, while policies control whether OpenCode may use a resource such as an LLM provider." Configured via `experimental.policies` (`policies.mdx`, lines 6-8).
- Statement fields: `effect` (`"allow"` | `"deny"`), `action`, `resource` (wildcard-capable). Currently one action: `provider.use` (`policies.mdx`, § "Configuration" and § "Available Policies", lines 14-49).
- Semantics: last matching statement wins; "If no policy matches a provider, provider use is allowed by default."; global policy takes priority over project policy, "This prevents a repository from re-enabling a provider that you deny globally." (`policies.mdx`, § "Rule Order", lines 76-104). Policies supersede the older `disabled_providers`/`enabled_providers` settings (§ "Provider Lists", lines 110-136; see also `config.mdx` § "Policies", lines 402-421, and `config.mdx` § "Disabled providers" which notes `disabled_providers` takes priority over `enabled_providers`, lines 830-870).

### MCP

- Both local and remote servers are supported; "MCP tools are automatically available to the LLM alongside built-in tools." (`mcp-servers.mdx`, lines 6-8).
- Context cost caveat: "When you use an MCP server, it adds to the context... Certain MCP servers, like the GitHub MCP server, tend to add a lot of tokens and can easily exceed the context limit." (`mcp-servers.mdx`, § "Caveats", lines 12-21).
- Local server options: `type: "local"`, `command` (required), `cwd` ("Relative paths resolve from the workspace"), `environment`, `enabled`, `timeout` (ms, "Defaults to 5000 (5 seconds)") (§ "Local" options table, lines 117-127). Remote options: `type: "remote"`, `url`, `enabled`, `headers`, `oauth`, `timeout` 5000 ms default (§ "Remote" options table, lines 156-163).
- Organizational defaults: MCP servers can ship disabled-by-default via `.well-known/opencode` remote config; users opt in with `enabled: true` (§ "Overriding remote defaults", lines 47-66; see also `config.mdx` § "Remote", lines 63-95).
- OAuth: automatic; "Detect the 401 response and initiate the OAuth flow", "Use **Dynamic Client Registration (RFC 7591)** if supported", store tokens "securely in `~/.local/share/opencode/mcp-auth.json`"; CLI: `opencode mcp auth <server-name>`, `opencode mcp list`, `opencode mcp logout <server-name>`, `opencode mcp auth list`, `opencode mcp debug <server-name>` (§ "OAuth", lines 167-289; token path at line 242).
- Tool management: MCP servers are managed like other tools via glob patterns (`"my-mcp*": false`); "MCP server tools are registered with server name as prefix", e.g. `"mymcpservername_*": false`; per-agent enablement is recommended for many servers (§ "Manage" and § "Glob patterns", lines 293-394).

### Plugins and hooks

- Loading: local JS/TS in `.opencode/plugins/` or `~/.config/opencode/plugins/` (auto-loaded at startup), or npm packages via the `plugin` config array; "npm plugins are installed automatically using Bun at startup. Packages and their dependencies are cached in `~/.cache/opencode/node_modules/`." (`plugins.mdx`, § "Use a plugin" and § "How plugins are installed", lines 12-50).
- Load order: global config, project config, global plugin dir, project plugin dir; "all hooks run in sequence" (`plugins.mdx`, § "Load order", lines 54-63).
- Plugin shape: a module exporting async functions receiving context `{ project, client, $, directory, worktree }` and returning a hooks object; `$` is Bun's shell API (`plugins.mdx`, § "Basic structure", lines 104-122). Dependencies come from a `package.json` in the config directory; "OpenCode runs `bun install` at startup" (§ "Dependencies", lines 74-100).
- Documented event surface: `command.executed`; `file.edited`, `file.watcher.updated`; `installation.updated`; `lsp.client.diagnostics`, `lsp.updated`; `message.part.removed`, `message.part.updated`, `message.removed`, `message.updated`; `permission.asked`, `permission.replied`; `server.connected`; `session.created`, `session.compacted`, `session.deleted`, `session.diff`, `session.error`, `session.idle`, `session.status`, `session.updated`; `todo.updated`; `shell.env`; `tool.execute.after`, `tool.execute.before`; `tui.prompt.append`, `tui.command.execute`, `tui.toast.show` (`plugins.mdx`, § "Events", lines 142-208).
- Plugin tools: defined with the `tool()` helper and Zod schema; "If a plugin tool uses the same name as a built-in tool, the plugin tool takes precedence." (`plugins.mdx`, § "Custom tools", lines 278-313).
- Compaction hook: `experimental.session.compacting` "fires before the LLM generates a continuation summary"; plugins can push into `output.context` or fully replace the prompt via `output.prompt` (then `output.context` is ignored) (`plugins.mdx`, § "Compaction hooks", lines 338-389).
- Hooks can also gate or rewrite tool calls: the `.env` protection example throws in `tool.execute.before` when `input.tool === "read"` and the path includes `.env`; `shell.env` injects env vars into "all shell execution (AI tools and user terminals)" (`plugins.mdx`, § ".env protection" lines 243-257, § "Inject environment variables" lines 261-274).

### Skills

- Discovery: one `SKILL.md` per `<name>/` folder, searched in `.opencode/skills/`, `~/.config/opencode/skills/`, `.claude/skills/`, `~/.claude/skills/`, `.agents/skills/`, `~/.agents/skills/`; for project paths OpenCode "walks up from your current working directory until it reaches the git worktree" (`skills.mdx`, § "Place files" and § "Understand discovery", lines 11-30).
- Frontmatter: `name` (required), `description` (required), `license`, `compatibility`, `metadata`; "Unknown frontmatter fields are ignored."; name must be 1-64 characters, lowercase alphanumeric with single hyphens, match the directory name, regex `^[a-z0-9]+(-[a-z0-9]+)*$`; description must be 1-1024 characters (§ "Write frontmatter" through § "Follow length rules", lines 34-70).
- Loading is on-demand via the native `skill` tool: "OpenCode lists available skills in the `skill` tool description" as an XML `<available_skills>` block; the agent loads via `skill({ name: "git-release" })` (§ "Recognize tool description", lines 103-121).
- Permission control: `permission.skill` patterns with `allow`/`deny`/`ask`; `deny` hides the skill "from agent, access rejected"; per-agent overrides; disabling the skill tool omits `<available_skills>` entirely (§ "Configure permissions" through § "Disable the skill tool", lines 125-211; see also `tools.mdx` § "skill" and `agents.mdx` permission table).

### Commands

- Custom commands are markdown files in `.opencode/commands/` / `~/.config/opencode/commands/` or JSON under `command`; frontmatter supports `description`, `agent`, `model`; built-ins include `/init`, `/undo`, `/redo`, `/share`, `/help`; "Custom commands can override built-in commands." (`commands.mdx`, lines 12, 18-41, 80-101, 315-323).
- Template features: `$ARGUMENTS` and positional `$1`..`$N`; shell output injection with !`command` ("Commands run in your project's root directory and their output becomes part of the prompt."); file references with `@path` included automatically (§ "Prompt config", lines 107-211).
- `agent` option routes the command to a specific agent; if it is a subagent the command triggers a subagent invocation; `subtask: true` forces subagent execution "even if `mode` is set to `primary`", keeping work out of the primary context (§ "Agent" and § "Subtask", lines 257-293).

### LSP integration

- Purpose: "integrate with Language Server Protocol (LSP) servers to use diagnostics as feedback for the agent." (`lsp.mdx`, line 6). LSP is disabled by default ("If `lsp` is omitted, all LSP servers are disabled", § "Disabling LSP servers", line 163); enable with `lsp: true` or configure per server (`disabled`, `command`, `extensions`, `env`, `initialization`) (§ "Configure", lines 76-108).
- Built-in server table lists ~34 servers (astro, bash, clangd, csharp, clojure-lsp, dart, deno, elixir-ls, eslint, fsharp, gleam, gopls, hls, jdtls, julials, kotlin-ls, lua-ls, nixd, ocaml-lsp, oxlint, php intelephense, prisma, pyright, razor, ruby-lsp, rust, sourcekit-lsp, svelte, terraform, tinymist, typescript, vue, yaml-ls, zls) with extension mappings and install requirements ("Auto-installs" for several) (`lsp.mdx`, § "Built-in" table, lines 12-49). Downloads can be disabled with `OPENCODE_DISABLE_LSP_DOWNLOAD=true` (line 54).
- The docs themselves counsel restraint: "Language servers can get out of sync, use significant memory, vary by version or project, and slow down agent workflows. In many projects it is better to have the agent run lint, typecheck, or other diagnostic CLI tools directly" and document those commands in `AGENTS.md` or skills (`lsp.mdx`, § "Best Practices", lines 68-72).

### Config system

- JSON/JSONC, schema at `https://opencode.ai/config.json`; TUI config uses `opencode.ai/tui.json` (`config.mdx`, § "Format" lines 10-23, § "Schema" lines 254-260).
- "Configuration files are **merged together**, not replaced." (`config.mdx`, § "Locations", lines 32-38). Precedence order, later overrides earlier: (1) Remote config (`.well-known/opencode`), (2) Global (`~/.config/opencode/opencode.json`), (3) Custom (`OPENCODE_CONFIG`), (4) Project (`opencode.json` in project), (5) `.opencode` directories (agents, commands, plugins), (6) Inline (`OPENCODE_CONFIG_CONTENT`), (7) Managed config files (`/Library/Application Support/opencode/` on macOS, `/etc/opencode/` on Linux, `%ProgramData%\opencode` on Windows), (8) macOS managed preferences (`.mobileconfig` via MDM), "highest priority, not user-overridable" (`config.mdx`, § "Precedence order", lines 42-55; managed paths table lines 162-167).
- Project config lookup: "it first looks for a config file in the current directory, then traverses up to the nearest Git directory." (`config.mdx`, § "Per project", line 119). `OPENCODE_CONFIG_DIR` designates an alternate config directory searched for agents/commands/modes/plugins (`config.mdx`, § "Custom directory", lines 138-150).
- MDM: macOS managed preferences read from the `ai.opencode.managed` domain at `/Library/Managed Preferences/<user>/ai.opencode.managed.plist` and `/Library/Managed Preferences/ai.opencode.managed.plist`; plist keys "map directly to `opencode.json` fields"; verify with `opencode debug config`; managed keys "cannot be overridden by user or project configuration" (`config.mdx`, § "macOS managed preferences", lines 170-250).
- `.opencode` and `~/.config/opencode` directories use plural subdirectory names: `agents/`, `commands/`, `modes/`, `plugins/`, `skills/`, `tools/`, `themes/` (singular names supported for backwards compatibility) (`config.mdx`, line 58).
- Models: `provider`, `model`, `small_model` ("a separate model for lightweight tasks like title generation"); provider options `timeout` (ms, "default: 300000", `false` disables), `chunkTimeout`, `setCacheKey` (`config.mdx`, § "Models", lines 362-397).
- Image attachments normalized before provider requests: resized when exceeding `2000x2000` pixels or `5242880` base64 bytes; `auto_resize: false` rejects instead; oversized tool-result images are omitted, oversized user images fail (`config.mdx`, § "Image attachments", lines 425-450).
- Snapshots: "OpenCode uses snapshots to track file changes during agent operations, enabling you to undo and revert changes within a session. Snapshots are enabled by default."; uses "an internal git repository"; disable with `snapshot: false`, at the cost "changes made by the agent cannot be rolled back through the UI" (`config.mdx`, § "Snapshot", lines 628-641). Undo/redo UX: `/undo` reverts changes and restores the original message, runnable multiple times; `/redo` reapplies (`index.mdx`, § "Undo changes", lines 301-333).
- Compaction config: `auto` ("Automatically compact the session when context is full", default `true`), `prune` ("Remove old tool outputs to save tokens", default `false`), `reserved` ("Token buffer for compaction") (`config.mdx`, § "Compaction", lines 744-761).
- Share config: `"manual"` (default), `"auto"`, `"disabled"` (`config.mdx`, § "Sharing", lines 562-579).
- Other options: `shell` (default discovery per OS), `watcher.ignore` globs, `formatter`, `autoupdate` (`true`/`false`/`"notify"`), `instructions`, `disabled_providers`/`enabled_providers`, `experimental` ("not stable. They may change or be removed without notice.") (`config.mdx`, § "Shell" lines 329-340, § "Watcher" lines 765-778, § "Formatters" lines 661-692, § "Autoupdate" lines 645-657, § "Experimental" lines 874-887).
- Variable substitution: `{env:VARIABLE_NAME}` (empty string if unset) and `{file:path}` relative to the config dir or absolute (`config.mdx`, § "Variables", lines 891-947).

### Providers

- "OpenCode uses the AI SDK and Models.dev to support **75+ LLM providers** and it supports running local models." (`providers.mdx`, line 9). Credentials added via `/connect` "are stored in `~/.local/share/opencode/auth.json`" (§ "Credentials", lines 20-21). `baseURL` override, `blacklist`/`whitelist` for the `/models` picker (§ "Config", lines 25-83). OpenCode Zen and OpenCode Go are the vendor's own curated providers (§ "OpenCode Zen" lines 87-119, § "OpenCode Go" lines 123-151).

### Interfaces: ACP, HTTP server, SDK

- ACP: "OpenCode supports the Agent Client Protocol"; editors run `opencode acp`, which "starts OpenCode as an ACP-compatible subprocess that communicates with your editor over JSON-RPC via stdio"; examples for Zed, JetBrains (`acp.json`), Avante.nvim, CodeCompanion.nvim (`acp.mdx`, lines 6-20, § "Configure", lines 26-141). Feature claim: "OpenCode works the same via ACP as it does in the terminal. All features are supported" with the caveat "Some built-in slash commands like `/undo` and `/redo` are currently unsupported."; the supported list includes built-in tools, custom tools and slash commands, MCP servers, `AGENTS.md` project rules, formatters/linters, and the "Agents and permissions system" (§ "Support", lines 143-156).
- HTTP server: `opencode serve` runs a "headless HTTP server that exposes an OpenAPI endpoint"; defaults `--port 4096`, `--hostname 127.0.0.1`, plus `--mdns` and `--cors`; basic auth via `OPENCODE_SERVER_PASSWORD` (username default `opencode`, override `OPENCODE_SERVER_USERNAME`); applies to `opencode serve` and `opencode web` (`server.mdx`, lines 9-43).
- Architecture: "When you run `opencode` it starts a TUI and a server. Where the TUI is the client that talks to the server. The server exposes an OpenAPI 3.1 spec endpoint." This design "lets opencode support multiple clients and allows you to interact with opencode programmatically." (`server.mdx`, § "How it works", lines 47-60).
- Session API surface (`server.mdx`, § "Sessions" table, lines 148-167): create/list/get/delete/patch; `/session/:id/children`; `/session/:id/todo`; `/session/:id/init` ("Analyze app and create `AGENTS.md`"); `/session/:id/fork` (body `{ messageID? }`); `/session/:id/abort`; `/session/:id/share` and `DELETE /session/:id/share`; `/session/:id/diff` (query `messageID?`); `/session/:id/summarize`; `/session/:id/revert` (body `{ messageID, partID? }`) and `/session/:id/unrevert`; `/session/:id/permissions/:permissionID` ("Respond to a permission request", body `{ response, remember? }`).
- Message API (`server.mdx`, § "Messages" table, lines 173-180): `POST /session/:id/message` ("Send a message and wait for response"; body includes `model?`, `agent?`, `noReply?`, `system?`, `tools?`, `parts`), `POST /session/:id/prompt_async` (async, returns `204 No Content`), `POST /session/:id/command` (execute slash command), `POST /session/:id/shell` (run a shell command).
- Other endpoints: file listing/search (`/file`, `/file/content`, `/find`, `/find/file`, `/find/symbol`; `limit` 1-200), experimental tool listing (`/experimental/tool/ids`, `/experimental/tool?provider=&model=`), `/lsp`, `/formatter`, `/mcp` (GET status, POST to add a server dynamically), `/agent`, `/event` SSE stream ("First event is `server.connected`, then bus events"), `/doc` OpenAPI 3.1, TUI control endpoints (`server.mdx`, § "Files" through § "Docs", lines 192-287).
- SDK: `@opencode-ai/sdk` on npm; `createOpencode()` "starts both a server and a client" (defaults hostname `127.0.0.1`, port `4096`, timeout `5000`); `createOpencodeClient` connects to an existing server; "All types are generated from the server's OpenAPI specification" (`sdk.mdx`, lines 9-102). Structured output: request `format: { type: "json_schema", schema }` and "The model will use a `StructuredOutput` tool to return validated JSON"; `retryCount` default `2`; failures surface as `StructuredOutputError` (`sdk.mdx`, § "Structured Output", lines 120-188).

### Share

- Sharing creates "a unique public URL", syncs history to OpenCode's servers, and is reachable at `opncd.ai/s/<share-id>`; "Shared conversations are publicly accessible to anyone with the link." (`share.mdx`, lines 6-20). Three modes: manual (default), auto-share (`"auto"`), disabled (`"disabled"`) (§ "Sharing", lines 26-77). `/unshare` "remove[s] the share link and delete[s] the data related to the conversation" (§ "Un-sharing", lines 81-89). Retention: "Shared conversations remain accessible until you explicitly unshare them", including "Full conversation history", "All messages and responses", "Session metadata" (§ "Data retention", lines 99-106). Enterprise: can be disabled, restricted to SSO, or self-hosted (§ "For enterprises", lines 120-128). In the TUI: "Conversations are not shared by default." (`index.mdx`, line 349).

## Limitations

- Vendor documentation, not specification or code. Every statement describes intended behavior; the pinned TypeScript implementation may diverge (e.g., exact pattern-matching semantics for bash permissions, the exact set of tools gated by each key, and whether the hidden agents' prompts are as described can only be confirmed in `packages/opencode/src/`, covered by the opencode codebase notes of this study).
- Internal inconsistencies within the docs at the pinned commit:
  - `agents.mdx` (§ "Permissions" table, lines 432-448) lists a `list` permission key gating a `list` tool, but `tools.mdx` (§ "Built-in") has no `list` tool and `permissions.mdx` (§ "Available Permissions") omits `list` from its key list. The existence and name of a list tool need code confirmation.
  - `permissions.mdx` says `edit` "covers `edit`, `write`, `patch`" while `tools.mdx` warns hooks must check `input.tool === "apply_patch"` (not `"patch"`); the canonical tool name is `apply_patch` per `tools.mdx` § "apply_patch", but the permissions page uses `patch`.
  - Example model IDs differ across pages (`agents.mdx` uses `anthropic/claude-sonnet-4-20250514` while `commands.mdx` uses `anthropic/claude-3-5-sonnet-20241022`), a cosmetic drift sign the docs are not version-locked to one release.
- The docs document no OS-level sandboxing for shell or file access. The safety model described is approval-based (allow/ask/deny rules, `--auto`, `.env` deny-by-default, `external_directory` ask-by-default) plus workspace boundaries; there is no doc page describing seatbelt/bubblewrap/landlock-style confinement. (The independent observation that no such machinery was found in the pinned tree is recorded in the `opencodePermissions` codebase entry of this study's registry; I do not assert it from docs.)
- `lsp` permission is "currently non-granular" (`permissions.mdx`, § "Available Permissions"), so LSP queries cannot be gated per path.
- ACP support is claimed complete except built-in slash commands: "Some built-in slash commands like `/undo` and `/redo` are currently unsupported." (`acp.mdx`, § "Support").
- Security-relevant defaults documented but not independently audited: `--auto` auto-approves everything not denied; `permission: "allow"` sets every permission globally; a managed-config example shows `rm -rf *` deny but only as a deployer's choice, not a default. Websearch requires no API key and "connects directly to Exa AI's hosted MCP service" (`tools.mdx` § "websearch"), an external dependency not pinned to a version.
- MCP context cost is acknowledged by the vendor itself as a real hazard ("can easily exceed the context limit", `mcp-servers.mdx` § "Caveats") but no quantified budget or guardrail is documented.
- Share/privacy: shared sessions are public by URL, retained until unshared, and synced to vendor servers (`share.mdx`); no retention window is documented (`[CITATION NEEDED]`: I looked in `share.mdx` § "Privacy" and § "Data retention" for a retention period and found none stated).
- This note anchors to doc files at commit `d545d8fba57283528db69281f59c803c646eb7e9`; the floating mirror https://opencode.ai/docs/ may already differ, and the docs carry no per-page dates, so "as of when" a statement became true is not recoverable from the corpus.

## Relevance to the brief

My own inferences, separated from source claims:

- RQ1/RQ2 (harness components, genuine differences): this note supplies the OpenCode column for most of the eight brief dimensions at the documented level: turn-loop bounds (`steps`, `subagent_depth`), context management (hidden compaction agent + `compaction` config with `auto`/`prune`/`reserved` + `experimental.session.compacting` plugin hook), tools and apply-patch (`edit`/`write`/`apply_patch` with marker-line patch format; ripgrep-backed search tools), permissions (allow/ask/deny, per-agent merge, auto mode), extensibility (two distinct layers: plugins/hooks with a rich event taxomony, and declarative surfaces, skills/commands/agents/MCP), configuration (merged eight-layer precedence with MDM enforcement, unusual among the three), state/rollout (snapshots on an internal git repository, session fork/revert/share endpoints), and interfaces (TUI-as-client over an OpenAPI HTTP server, ACP subprocess mode, SDK).
- RQ3 (capability vs safety trade-off): documented OpenCode posture is permissive-by-default with opt-in friction (`tools.mdx` line 8; `permissions.mdx` § "Defaults"), in contrast to whatever Codex and Claude Code docs state; the comparison matrix should pair this with the note that the docs surface contains no OS sandbox, so the approval layer is the documented boundary. The `doom_loop` and `external_directory` ask-by-default rules and the `.env` deny rule are the few built-in friction points.
- RQ4 (what closed systems reveal through docs): OpenCode is open, but its Claude Code compatibility surface (`CLAUDE.md` fallbacks, `~/.claude/skills/`, `OPENCODE_DISABLE_CLAUDE_CODE*` env vars, `rules.mdx` § "Claude Code Compatibility") documents the de facto conventions Claude Code established, useful as cross-system evidence.
- Distinctive mechanisms worth highlighting in the report: hidden system agents as the compaction/title/summary implementation (`agents.mdx`); undo/redo as a first-class harness feature built on snapshotting (`index.mdx`, `config.mdx` § "Snapshot"); plugin-compaction interception (`plugins.mdx` § "Compaction hooks"); policies as a resource-level layer separate from session permissions (`policies.mdx`); and share/sync with public URLs as session-state distribution (`share.mdx`, `server.mdx` fork/revert endpoints).
- Left open (must be answered by the opencode codebase notes, not this one): actual default permission values in code, the true built-in tool list and names, how bash command strings are parsed for pattern matching, where and how snapshots are stored, compaction trigger thresholds, and the real contents of system prompts.
