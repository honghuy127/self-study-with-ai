## Purpose and role in the harness

This component is OpenCode's durable-state layer. At the pinned commit it has four cooperating pieces:

1. A single SQLite database (drizzle ORM) holding operational tables for sessions, messages, parts, todos, and share credentials (`packages/opencode/src/storage/schema.ts:1-5`, `packages/core/src/session/sql.ts:22-138`, `packages/core/src/share/sql.ts:5-13`).
2. A durable, per-aggregate event log in the same database (`event`, `event_sequence` tables) that implements single-writer event sourcing; projectors replay events into the operational tables (`packages/core/src/event/sql.ts:4-25`, `packages/core/src/session/projector.ts:210-453`, `packages/opencode/src/sync/README.md:29-33`).
3. A git-based filesystem snapshot store: one shadow git repository per project+worktree capturing worktrees as git tree objects, giving the agent per-step undo, per-message revert, and diff computation (`packages/opencode/src/snapshot/index.ts:36-45`, `:318-347`).
4. A remote share/export pipeline that mirrors session, message, part, diff, and model records to an opencode-hosted endpoint (`packages/opencode/src/share/share-next.ts:25-79`, `:310-336`).

A legacy JSON-file store (`data/storage/**/*.json`) remains as a generic key/value layer with two migrations from older on-disk layouts; at this commit its only non-test write site is `session_diff/<sessionID>.json` (`packages/opencode/src/storage/storage.ts:81-211`, `packages/opencode/src/session/revert.ts:77`).

## Mechanism

### Persistence stack: SQLite plus event log plus projectors

The database is a single file resolved by `Database.path()`: `join(Global.Path.data, "opencode.db")` unless the installation channel adds a suffix (`opencode-<channel>.db`) or `Flag.OPENCODE_DB` overrides it, with `:memory:` supported (`packages/core/src/database/database.ts:43-55`). `Global.Path.data` is `path.join(xdgData, "opencode")` (`packages/core/src/global.ts:10-11`). The service opens WAL mode with `PRAGMA journal_mode = WAL`, `PRAGMA synchronous = NORMAL`, `PRAGMA busy_timeout = 5000`, `PRAGMA cache_size = -64000`, `PRAGMA foreign_keys = ON`, then applies migrations (`packages/core/src/database/database.ts:27-33`). On Node the driver is `node:sqlite` (`DatabaseSync`) wrapped by `drizzle-orm/node-sqlite` (`packages/core/src/database/sqlite.node.ts:1-2`, `:166-171`).

Writes do not go to tables directly. Session code publishes events (`packages/opencode/src/session/session.ts:535`(Created), `:631`(MessageUpdated), `:637-641`(PartUpdated), `:746`(Updated)), and global projectors apply them to SQLite: `SessionV1.Event.Created` inserts a `SessionTable` row with `onConflictDoNothing` and dies with `SessionAlreadyProjected` on duplicates (`packages/core/src/session/projector.ts:214-233`); `MessageUpdated` upserts `MessageTable` (`:260-273`); `PartUpdated` upserts `PartTable` and adjusts session cost/token counters via SQL increments (`applyUsage`, `packages/core/src/session/projector.ts:89-109`, `:310-328`). This matches the design documented in `packages/opencode/src/sync/README.md:41`: "events are sent _before_ the mutation happens, and 'projectors' handle the effects and perform the mutations."

Durable events are appended to `EventTable` keyed by `(aggregate_id, seq)` with a unique index `event_aggregate_seq_idx`, and the current sequence per aggregate lives in `event_sequence` (`packages/core/src/event/sql.ts:4-8`, `:10-25`). The event engine assigns `seq = latest + 1`, rejects stale or replayed sequences ("Replay diverged at aggregate ... sequence ..."), inserts the event with a versioned type, and runs local commit hooks atomically with the append (`packages/core/src/event.ts:294-349`, `:262-287`, `:122-123`). The sync README states the ordering model: one writer device, total order via "a simple sequence id (a number)" incremented by one per event, replayed by other devices (`packages/opencode/src/sync/README.md:29-33`). Sync events re-publish as bus events for backwards compatibility (`packages/opencode/src/sync/README.md:91`, `:97`, `:103-105`); the `sync/` directory itself holds only the README and an `EventID` brand (`Schema.isStartsWith("evt")`, ascending identifiers) (`packages/opencode/src/sync/schema.ts:6-10`).

Service state is per instance directory: `InstanceState.make` is a `ScopedCache` keyed by the instance `directory` (`packages/opencode/src/effect/instance-state.ts:26-50`), and bootstrap initializes `shareNext` and `snapshot` among `[lsp, shareNext, format, vcs, snapshot, project]` (`packages/opencode/src/project/bootstrap.ts:41-45`).

### Legacy JSON storage and migrations

`Storage` is a JSON document store rooted at `path.join(Global.Path.data, "storage")` where key arrays map to `<root>/<key...>.json` (`packages/opencode/src/storage/storage.ts:224`, `:63-65`). Every key gets a `TxReentrantLock` from an `RcMap` (`:218-221`); `read` takes the read lock, `write`/`update`/`remove` take the write lock, and `list` globs `**/*`, strips the 5-char `.json` suffix, and sorts with `localeCompare` (`:272-313`). A `migration` marker file records the applied count and steps run `MIGRATIONS[i]` then write `String(i + 1)` (`:225-239`).

- Migration 1 (`Storage.migration.1`, `packages/opencode/src/storage/storage.ts:81-181`): converts a legacy per-project tree `storage/session/{info,message,part}/...` into `project/<projectID>.json`, `session/<projectID>/...`, `message/<sessionID>/...`, `part/<messageID>/...`. The new project ID is the repo's root commit: `git rev-list --max-parents=0 --all`, sorted, first entry (`:109-119`), so a project is identified by its git history, not its path. The `"global"` project skips git lookup (`:96`).
- Migration 2 (`packages/opencode/src/storage/storage.ts:182-210`): splits a legacy inline `summary.diffs` out of session JSON into `session_diff/<id>.json` and replaces it with summed `additions`/`deletions`.

`storage/schema.ts` exports only re-exported drizzle tables (`AccountTable`, `ProjectTable`, `SessionTable`, `MessageTable`, `PartTable`, `TodoTable`, `SessionShareTable`, `WorkspaceTable`) (`packages/opencode/src/storage/schema.ts:1-5`): the SQLite schema surface of the storage component.

### Snapshot machinery (git-based, per project+worktree)

`Snapshot` keeps a dedicated git directory per project and worktree: `gitdir = path.join(Global.Path.data, "snapshot", ctx.project.id, Hash.fast(ctx.worktree))` with `Hash.fast` = SHA-1 hex (`packages/opencode/src/snapshot/index.ts:71`, `packages/core/src/util/hash.ts:4-6`). All commands run as `git --git-dir <gitdir> --work-tree <worktree> ...` against the user's real worktree (`packages/opencode/src/snapshot/index.ts:75`). Snapshots are git *tree objects*, not commits: `track()` stages changes and returns `write-tree` output (`:341-344`).

`track()` behavior (`packages/opencode/src/snapshot/index.ts:318-347`): no-op unless `project.vcs === "git"` and config `snapshot !== false` (`enabled()`, `:167-170`); on first use runs `git init` with `GIT_DIR`/`GIT_WORK_TREE` env and sets `core.autocrlf=false`, `core.longpaths=true`, `core.symlinks=true`, `core.fsmonitor=false`, `feature.manyFiles=true`, `index.version=4`, `index.threads=true`, `core.untrackedCache=true` "for very large worktrees so the first add stays bounded" (`:324-337`). It then seeds the shadow repo from the source repository's object store: writes `objects/info/alternates` pointing at the source `objects` plus the source's own chained alternates, and copies the source `index` so already-hashed entries are reused (`:198-233`); the code comment explains motivation on "huge repos like chromium checkout" (`:195-197`).

Candidate selection (`add()`, `packages/opencode/src/snapshot/index.ts:235-298`): runs `git diff-files --name-only -z` (modified tracked) and `git ls-files --full-name --others --exclude-standard -z` (untracked) in parallel (`:239-247`), resolves the source repo's ignore rules with `git check-ignore --no-index --stdin -z` (`ignore()`, `:102-130`), drops newly-ignored files from the snapshot index (`:268-272`), and blocks untracked files larger than `limit = 2 * 1024 * 1024` bytes by adding them to the shadow `info/exclude` (`:24`, `:277-297`, `sync()` `:182-193`). Staging uses `git add --all --sparse --pathspec-from-file=- --pathspec-file-nul` with NUL-separated `:(top,literal)` pathspecs (`:77-79`, `:146-154`).

Ops on snapshots (all serialized behind a per-gitdir semaphore, `packages/opencode/src/snapshot/index.ts:55-64`, `:165`):

- `patch(hash)` (`:349-380`): re-stages, then `git diff --cached --no-ext-diff --name-only <hash>`; returns `{ hash, files: [...] }` with ignored-file removals filtered out.
- `restore(snapshot)` (`:382-406`): `git read-tree <snapshot>` then `git checkout-index -a -f`. Files absent from the snapshot tree are left in place (restore only overwrites tree entries; deletion is handled separately by `revert`).
- `revert(patches)` (`:408-524`): for each file in each patch (deduplicated by path), `git checkout <hash> -- <file>`; if checkout fails and `ls-tree` shows the file did not exist in that snapshot, deletes the file (`:425-443`). Files with the same snapshot hash are batched into runs of up to 100 unless paths collide (`clash` checks prefix nesting, `:445-458`).
- `diff(hash)` / `diffFull(from, to)` (`:526-544`, `:546-759`): full unified diff or structured per-file diffs; `diffFull` uses `git diff --name-status --no-renames` plus `--numstat`, fetches blob contents via one `git cat-file --batch` invocation per 100 files with fallback to per-file `git show` (`:604-620`, `:735-745`), and builds patches with the `diff` package and `context: Number.MAX_SAFE_INTEGER` (`:736-737`).
- `cleanup()` (`:300-316`): `git gc --prune=7.days` (`prune = "7.days"`, `:23`), scheduled hourly with a 1-minute initial delay (`:761-766`).

How the turn loop records snapshots (`packages/opencode/src/session/processor.ts`): before the LLM stream starts, `const initialSnapshot = yield* snapshot.track()` with the comment "Pre-capture snapshot before the LLM stream starts. The AI SDK may execute tools internally before emitting start-step events, so capturing inside the event handler can be too late." (`:99-102`); on `step-start` it tracks if needed and stores a `step-start` part with `snapshot: ctx.snapshot` (`:424-433`); on `step-finish` it tracks again, stores a `step-finish` part with that snapshot, then `snapshot.patch(ctx.snapshot)` and, if files changed, stores a `patch` part `{ hash, files }` (`:435-470`); cleanup repeats the patch capture for interrupted streams (`:539-553`). Part schemas carry these fields: `StepStartPart.snapshot` and `StepFinishPart.snapshot` (`packages/schema/src/v1/session.ts:233-237`, `:240-244`), and a legacy part type literal `"snapshot"` (`packages/schema/src/v1/session.ts:89-90`). Session-level diff summaries derive from these hashes: `SessionSummary.computeDiff` takes the first `step-start` snapshot as `from` and the last `step-finish` snapshot as `to` per user-message group and calls `snapshot.diffFull(from, to)` (`packages/opencode/src/session/summary.ts:82-100`), storing results on the user message's `summary.diffs` (`:119-127`).

A second, newer snapshot service exists in core (`@opencode/v2/Snapshot`) with the same gitdir layout `path.join(global.data, "snapshot", location.project.id, Hash.fast(worktree))` (`packages/core/src/snapshot.ts:98`) but Location-scoped capture/restore over relative paths, `maximumUntrackedFileBytes: 2 * 1024 * 1024` (`:138`), enablement via config key `"snapshots"` (`:124-127`), and a `checkout` for whole-tree restore (`:219-224`). The v2 session runner captures `snapshots.capture()` at step start (`packages/core/src/session/runner/llm.ts:224`) and step end with a `snapshots.files({from, to})` changed-file list (`:325-341`); assistant messages persist `snapshot: { start, end, files }` (`packages/schema/src/session-message.ts:171-175`).

### Session restore, revert, unrevert, fork

v1 flow (`packages/opencode/src/session/revert.ts`): `revert({sessionID, messageID, partID})` walks all messages, collects every `type: "patch"` part after the boundary (`:46-66`), captures the pre-revert state with `snap.track()` (reusing `session.revert?.snapshot` if already staged) (`:70`), restores a previously staged snapshot if present (`:71`), applies `snap.revert(patches)` (`:72`), records `rev.diff = snap.diff(rev.snapshot)` (`:73`), writes computed diffs to the JSON store (`storage.write(["session_diff", input.sessionID], diffs)`, `:77`), publishes `Session.Event.Diff` (`:78`), and persists revert state plus summary counts via `sessions.setRevert` (`:79-87`). Revert state shape is `SessionRevert = { messageID, partID?, snapshot?, diff? }` (`packages/schema/src/v1/session.ts:530-535`) persisted in `SessionTable.revert` (`packages/core/src/session/sql.ts:49`). `unrevert` restores the staged snapshot (`packages/opencode/src/session/revert.ts:91-99`); `cleanup` permanently deletes messages (and trailing parts) after the boundary (`:101-124`).

v2 flow (`packages/core/src/session/revert.ts`): `stage` builds a selective per-file restore map from assistant `SessionMessageTable` rows with `seq` after the boundary message, mapping each recorded file to that message's `snapshot.start` tree (`plan`, `:27-58`), restores files (`:71-76`), and publishes `SessionEvent.RevertEvent.Staged` (`:90-94`); `clear` restores originals (`:98-111`); `commit` publishes `RevertEvent.Committed` (`:113-121`), whose projector deletes `SessionMessageTable` rows with `seq` greater than the boundary's and clears inputs and revert state (`packages/core/src/session/projector.ts:413-451`). v2 revert state adds per-file diffs: `Revert.State = { messageID, partID?, snapshot?, diff?, files? }` (`packages/schema/src/revert.ts:17-23`).

Fork (`packages/opencode/src/session/session.ts#fork`, `:691-732`): creates a new top-level session (no `parentID`; title becomes `<title> (fork #N)` via `getForkedTitle`, `:162-168`, `:694`), then copies all messages up to the optional `messageID` boundary with fresh `MessageID`s, remapping assistant `parentID`s (`:704-716`) and cloning parts with fresh IDs, including remapping compaction `tail_start_id` (`:718-729`). Forks copy conversation records only; there is no filesystem fork or branch here (worktrees are a separate mechanism, see `opencodePermissions` component). Parent/child sessions (`SessionTable.parent_id`, `children()` `:596-604`) are the subagent linkage, not the fork linkage.

### Share / export

`SessionShare` (`packages/opencode/src/share/session.ts`): `share` refuses when config `share === "disabled"` (`:28`), calls `ShareNext.create` and records the URL on the session (`:29-30`); `create` auto-shares newly created sessions only for top-level sessions (`if (result.parentID) return result`, `:41`) when the `OPENCODE_AUTO_SHARE` runtime flag or config `share === "auto"` is set (`:43`, `packages/opencode/src/effect/runtime-flags.ts:17`), fire-and-forget (`:44`).

`ShareNext` (`packages/opencode/src/share/share-next.ts`): disabled globally by `OPENCODE_DISABLE_SHARE` `"true"`/`"1"` (`:23`). Share credentials `{ id, url, secret }` come from `POST /api/share` (or authenticated `POST /api/shares` for org accounts) and are upserted into `SessionShareTable` keyed by `session_id` (`:38-42`, `:85-95`, `:310-328`, `packages/core/src/share/sql.ts:5-13`). Without an active account/org, the base URL defaults to `https://opncd.ai`, overridable via config `enterprise.url` (`:210`, `packages/core/src/v1/config/config.ts:133-135`); with an account it sends `Authorization: Bearer <token>` and `x-org-id` (`:214-221`). After creation, a full sync pushes `session`, all `message`s, all `part`s, `session_diff` (via `session.diff(sessionID)`, `:277`), and deduplicated `model` records (`full`, `:274-299`). Incremental sync subscribes to session/message/part/diff/deleted events (`:179-200`) and funnels them through a per-session queue keyed by `key(item)` (`session`, `message/<id>`, `part/<messageID>/<partID>`, `session_diff`, `model`, `:97-110`) with a 1000 ms debounce (`:141-145`); `flush` POSTs `{ secret, data: [...] }` to `/api/share/<shareID>/sync` and only logs on `status >= 400` (`:247-272`). `remove` DELETEs the remote share with the secret and deletes the table row (`:338-359`).

## Key facts with anchors

- Snapshots are git tree objects in a shadow repo `~/<XDG_DATA>/opencode/snapshot/<projectID>/<sha1(worktree)>`, never commits: `write-tree` returns the hash (`packages/opencode/src/snapshot/index.ts:71`, `:341-344`).
- Untracked files above `2 * 1024 * 1024` bytes are excluded from snapshots by writing them into the shadow repo's `info/exclude` (`packages/opencode/src/snapshot/index.ts:24`, `:277-297`).
- Shadow git gc runs hourly with `--prune=7.days` (`packages/opencode/src/snapshot/index.ts:23`, `:305`, `:761-766`).
- The turn loop captures a snapshot before the stream, at every `step-start`, and at every `step-finish`, emitting a `patch` part `{hash, files}` per step (`packages/opencode/src/session/processor.ts:99-102`, `:424-433`, `:435-470`).
- Revert applies saved patches by `git checkout <hash> -- <file>`, deleting files absent from the snapshot, batched up to 100 files per hash (`packages/opencode/src/snapshot/index.ts:425-443`, `:447-458`).
- Sessions, messages, and parts live in SQLite (`session`, `message`, `part` tables) written exclusively by event projectors (`packages/core/src/session/sql.ts:22-98`, `packages/core/src/session/projector.ts:214-328`); messages/parts store their payload as JSON blobs in `data` columns (`packages/core/src/session/sql.ts:77`, `:92`).
- Durable events append to `event`/`event_sequence` with unique `(aggregate_id, seq)`; the engine enforces contiguous per-aggregate sequence numbers (`packages/core/src/event/sql.ts:4-25`, `packages/core/src/event.ts:294-299`).
- Storage migrations identify a project by its git root commit via `git rev-list --max-parents=0 --all` (`packages/opencode/src/storage/storage.ts:109-119`).
- Share state persists as one row per session (`session_share.session_id` primary key) holding remote `id`, `secret`, `url` (`packages/core/src/share/sql.ts:5-13`); sync payloads are debounced 1000 ms and deduplicated by key (`packages/opencode/src/share/share-next.ts:97-110`, `:141-145`).
- `Session.fork` copies the conversation prefix into a new top-level session titled `... (fork #N)` with fresh IDs; it does not branch files (`packages/opencode/src/session/session.ts:691-732`, `:162-168`).
- Database pragmas: WAL, `synchronous = NORMAL`, `busy_timeout = 5000`, `cache_size = -64000`, `foreign_keys = ON` (`packages/core/src/database/database.ts:27-31`).

## Limitations and unknowns

- The `sync/` component directory contains only a README and an ID schema at this commit (`packages/opencode/src/sync/README.md`, `packages/opencode/src/sync/schema.ts:6-10`); the actual event engine (`packages/core/src/event.ts`) is outside the registered component, so claims about event sourcing here are anchored to that file and to sql tables, not verified end-to-end (e.g., how remote devices fetch and replay the log is not visible in this component).
- `Session.diff` is a stub returning `[] as Snapshot.FileDiff[]` (`packages/opencode/src/session/session.ts:823-826`), yet `ShareNext.full` sends its result as the `session_diff` payload (`packages/opencode/src/share/share-next.ts:277`, `:296`). At this commit, creating a share appears to upload an empty diff set; whether this is a transient state of the dev branch or intended (diffs arriving later via `Session.Event.Diff`) is not verifiable from the code.
- No non-test reader of the JSON `session_diff/<sessionID>.json` file was found in `packages/opencode/src` at the pinned commit (searched `storage.read`/`Storage.Service` usages; only write at `packages/opencode/src/session/revert.ts:77`). The UI side consumes diffs through the event stream (`packages/app/src/context/global-sync/event-reducer.ts:258`), so the JSON write looks vestigial or server-side only; unverified.
- Snapshot restore semantics: `restore` (`read-tree` + `checkout-index -a -f`) does not delete files created after the snapshot; deletion happens only through `revert`'s per-file handling. Whether anything cleans shadow-repo growth beyond hourly `gc --prune=7.days` (`packages/opencode/src/snapshot/index.ts:305`) is not shown.
- Two parallel stack generations coexist (v1 `@opencode/Snapshot` + `SessionTable`/`MessageTable`/`PartTable` path, and v2 `@opencode/v2/Snapshot` + `SessionMessageTable` path). Which surfaces (TUI, server, ACP) route to which generation at runtime was not traced here and belongs to the session-loop and interface notes.
- Share server behavior (retention, access control for `https://opncd.ai` links, the `/data` endpoint's consumers) is remote and not inspectable from the repo.
- `enabled()` requires `project.vcs === "git"` (`packages/opencode/src/snapshot/index.ts:168`), so non-git projects get no snapshot tracking at all; failure behavior in that case is silent no-op (observed code path returns `undefined`).

## Relevance to the brief

Inference, separated from the facts above.

- Direct evidence for the "state/rollout/session persistence" dimension of RQ1/RQ2: OpenCode's state story is a hybrid, event-sourced SQLite core (durable per-aggregate event log plus projectors rebuilding operational tables), a JSON-file legacy store kept only for diffs and migrations, and a git-object store for filesystem history. Compared to a rollout-file design (Codex), OpenCode reconstructs session state from an event log in the same DB that also holds denormalized read tables, and it treats file undo as first-class per-step state via shadow git trees.
- For RQ3 (capability vs safety): snapshots give users strong undo guarantees without restricting the agent; the safety investment here is recoverability rather than prevention, consistent with the permissions note's finding of no OS-level sandbox. Snapshot capture silently skips non-git worktrees and files over 2 MB, which bounds cost but means reverts can be incomplete for large/binary files (inference from `:24`, `:168`).
- For the comparison matrix: the fork mechanism clones message history with fresh IDs and remaps cross-references, but file state is shared with the parent session's worktree at fork time (no tree branch), which differs from designs that fork the workspace itself (inference from absence of any snapshot/worktree operation in `Session.fork`, `packages/opencode/src/session/session.ts:691-732`).
- Open questions for synthesis: whether the v2 `SessionMessageTable` event-sourced path fully replaces v1 tables, and how multi-device sync resolves the README's single-writer assumption in practice (README says sync replays events; the replay client is outside this component).
